# 从 `startup` 初始化新项目清单

本文用于从 `startup` 分支快速拉起一个新项目时的操作参考。目标是尽快完成“可运行、可开发、可继续定制”的第一阶段初始化。

## 推荐使用方式

根据项目形态，选择以下其中一种：

### 方式一：在当前仓库内拉新分支

适合短期验证、孵化新方向、暂时不拆仓库的情况。

```bash
git checkout startup
git pull origin startup
git checkout -b feature/<new-project-name>
```

### 方式二：基于 `startup` 派生独立仓库

适合已经确定要长期独立维护的新项目。

```bash
git checkout startup
git pull origin startup
git checkout -b bootstrap/<new-project-name>
```

随后将代码推到新仓库，再继续初始化。

## 初始化前检查

开始改名前，先确认以下几点：

- 当前基线来自 `startup`，不是 `main`
- 工作区干净，没有混入其他业务改动
- `.env`、域名、存储、短信、邮件等配置不会误用旧项目环境
- 新项目不需要的演示模块、试验目录、临时脚本已经列入清理计划

## 第一阶段：项目身份替换

这一步先完成“看起来已经是一个新项目”。

- 替换项目名、显示名、站点标题
- 替换域名、前后端回调地址、环境变量默认值
- 替换品牌文案、Logo、导航名称、页脚信息
- 检查 `package.json`、`pyproject.toml`、Docker 配置中的命名
- 检查 Django settings 中是否仍保留旧项目标识

## 第二阶段：配置隔离

这一步确保新项目不会误连旧环境。

- 生成新的 `.env`
- 更换 `SECRET_KEY`
- 更换数据库名、Redis 名称或连接配置
- 更换对象存储 bucket、endpoint、访问域名
- 更换邮件、短信、OAuth、微信等第三方凭据
- 检查 Celery、日志、上传目录等路径配置

## 第三阶段：模块取舍

这一步决定新项目到底保留哪些基础能力。

建议逐项判断以下模块是否保留：

- 账号认证与注册流程
- 组织 / 团队 / 多租户脚手架
- 通知系统
- 对象存储与媒体管理
- Admin 后台
- 小程序端
- 第三方登录、短信验证、支付或其他扩展能力

判断原则：

- 新项目短期不会用到的模块，可以先不接入业务
- 如果某模块会显著增加理解成本，优先降级为“保留代码，不接入口”
- 不要在项目启动第一天就做大规模删除，先保证项目能跑起来

## 第四阶段：验证基线可用

完成基本替换后，至少验证以下内容：

```bash
just test
just lint
```

如果当前环境主要通过 Docker 开发，再补充：

```bash
just start
```

建议人工确认：

- 首页或 SPA 壳子能正常打开
- 登录流程可用
- 数据库迁移正常
- 静态资源正常加载
- 核心接口没有明显命名残留

## 第五阶段：建立新项目约束

新项目基线可用后，尽快补齐这些仓库级约束：

- 更新 `AGENTS.md` 或团队协作说明
- 更新 README / 项目简介文档
- 确认分支策略
- 确认部署环境命名
- 确认 CI/CD、测试与发布流程

## 推荐提交节奏

为了后续更容易回看和复用，建议至少拆成这几类提交：

1. 初始化分支与项目命名替换
2. 环境变量与第三方配置隔离
3. 品牌素材与前端文案替换
4. 模块开关与路由入口调整
5. 首轮验证与文档更新

## 不建议一开始做的事

- 不要第一天就把大量“可能以后会用”的基础模块删掉
- 不要把 `main` 的业务代码直接拷回新项目
- 不要混用旧项目生产配置
- 不要在还没验证基线前就开始大规模重构

## 完成标志

满足以下条件后，可以认为“新项目初始化完成”：

- 新项目已经从 `startup` 成功拉起
- 项目身份和环境配置已经替换
- 基础功能可运行
- 文档和协作约束已更新
- 后续业务开发可以直接开始
