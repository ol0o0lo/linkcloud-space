# 小程序静默登录与轻量账号合并设计

**日期：** 2026-09-06
**状态：** 已确认，待实施

## 1. 设计基线与替代关系

本设计建立在以下现有能力之上：

- 小程序端已有 `sessionStore`、`appContextStore`、统一请求封装和模式解析；
- 后端已有 allauth app 端会话、`X-Session-Token`、`wechat_miniprogram` provider 和微信手机号绑定；
- 公开房源接口允许匿名访问，个人与组织接口继续要求认证；
- H5 与微信小程序共用业务代码，但认证入口和会话持久化策略可以按编译平台区分。

本设计只替代《小程序完整产品外壳与公开找房链路设计》中以下旧规则：

- “本地没有会话时保持游客，不自动创建账号”；
- “游客触发收藏等受限操作时再按需登录”；
- 会话失效后一律进入游客或手动登录。

公开房源、模式隔离、组织上下文和模块注册表等其他规则保持不变。

## 2. 目标

- 微信小程序首次冷启动时静默调用 `uni.login`，已有微信账号直接登录，首次访问自动创建轻量用户；
- 自动登录完成前保持稳定的启动状态，避免游客界面先出现再切换个人模式；
- H5 保留游客模式和现有手动登录方式；
- 用户主动退出后，当前设备后续启动不再自动登录，直到用户再次主动登录；
- 会话运行期失效时静默恢复，并只安全重试一次原请求；
- 微信轻量账号绑定到已有手机号账号时，在低风险条件下完整合并个人数据；
- 复杂业务身份、组织关系或财务数据存在时阻止自动合并，避免破坏权限和账务审计；
- 行为事件可以在保留匿名设备标识的同时关联已登录用户，但统计建设不是本次重点。

## 3. 非目标

- 不改变 H5 游客浏览和公开房源接口；
- 不要求用户首次进入时立即补充手机号、头像、姓名或实名认证；
- 不新增独立于 allauth 的移动端登录协议；
- 不建设通用工作流、人工审核后台或复杂账号合并管理平台；
- 不自动合并组织、团队、房东、员工、收益分配或其他业务身份；
- 不自动迁移钱包、提现、支付、收益分配等财务数据；
- 不建设新的分析报表，不回填或重写历史行为事件。

## 4. 已确认的产品决策

1. 微信小程序默认跳过游客态；首次打开即静默登录或注册。
2. 自动登录失败时，本次运行降级游客，下次冷启动再尝试；同一次运行不在每次 `onShow` 重试。
3. 首屏等待自动登录完成后再进入首页，避免身份与导航闪烁。
4. 已有 Session 校验遇到网络或服务异常时保留 Session，并显示可重试状态；只有明确的 `401/410` 才清除。
5. 用户主动退出后跨启动保持游客，用户再次主动登录成功后恢复自动登录。
6. 运行期 `401/410` 触发全局单例的静默登录恢复，安全请求最多重试一次。
7. 微信手机号授权视为充分的账号归属证明；即使目标账号启用 MFA，也不追加 MFA 验证。
8. 轻量账号合并时，已有手机号账号作为主账号；主账号资料优先，只用轻量账号填补空字段。
9. 只允许无组织、无业务身份、无敏感记录的轻量账号自动合并。
10. 来源或目标账号存在财务数据时停止自动合并，转人工处理。
11. 历史审计记录保留原始操作者，不批量改写为主账号。
12. 行为采集保留匿名设备标识，并在认证有效时附加用户身份；该能力保持最小范围。

## 5. 总体架构

采用现有架构的最小扩展，不引入新的全局认证状态机或后端聚合启动接口。

### 5.1 `sessionStore`

只负责认证生命周期：

- 保存和清除 `sessionToken`；
- 持久化微信自动登录禁用标记；
- 执行微信、手机号和邮箱登录；
- 校验当前会话；
- 管理单次运行的微信自动登录尝试；
- 管理运行期全局单例的会话恢复任务；
- 执行主动退出并撤销远端会话；
- 保存登录后待恢复的页面和动作。

`sessionStore` 不加载组织能力，不生成导航，也不直接决定应用模式。

### 5.2 `appContextStore`

负责应用启动编排和身份上下文：

- 获取公开应用配置；
- 调用 `sessionStore` 解析或恢复认证状态；
- 登录后加载当前用户、组织列表和房东关系；
- 解析个人、房东和组织模式；
- 加载当前组织能力；
- 在全部上下文稳定后将应用置为 `ready`。

### 5.3 请求层

统一请求层负责：

- 附加 Session 和组织请求头；
- 区分 `401/410`、`403`、网络错误和业务错误；
- 在允许重试的请求上调用全局认证恢复任务；
- 保证原请求最多自动重放一次；
- 禁止支付、提现、审批提交等敏感写操作自动重放。

### 5.4 后端账号合并服务

账号合并从手机号绑定 API 中抽离成独立服务，分为三个步骤：

1. 构建并校验合并计划；
2. 在事务和行锁内执行安全数据迁移；
3. 写入合并审计、撤销来源会话并切换当前登录态。

手机号绑定 API 只负责微信手机号换取、调用合并服务和序列化结果。

## 6. 会话状态与持久化

### 6.1 持久化状态

- `sessionToken`：小程序跨启动保存；H5 延续当前标签页级保存。
- `wechatAutoLoginDisabled`：只影响微信小程序。用户主动退出时设为 `true`，任何主动登录成功后设为 `false`。
- 待恢复页面和动作：沿用现有一次性消费规则。

普通的 Session 清理不能修改 `wechatAutoLoginDisabled`。只有用户明确点击退出才禁用自动登录。

### 6.2 运行期状态

- `bootstrapTask`：避免 `onLaunch` 与 `onShow` 并发初始化；
- `autoLoginAttempted`：同一次小程序运行周期最多自动调用一次微信登录；
- `authRecoveryTask`：运行期间所有认证失效请求共享同一个恢复任务。

这些状态不持久化。小程序冷启动后重新允许一次自动登录尝试。

## 7. 冷启动流程

### 7.1 微信小程序

1. 进入稳定的启动加载状态，不提前渲染游客导航。
2. 获取公开应用配置并读取本地 Session。
3. 存在 Session 时调用 allauth session 端点校验：
   - 成功：进入认证上下文加载；
   - `401/410`：清除 Token，继续执行微信自动登录；
   - 网络错误或 `5xx`：保留 Token，进入可重试启动状态。
4. 不存在 Session，且 `wechatAutoLoginDisabled=true`：进入游客模式。
5. 不存在有效 Session，且允许自动登录：
   - 若本次运行尚未尝试，则调用 `uni.login({ provider: 'weixin' })`；
   - 将 code 发送到 allauth app provider token 端点；
   - 已有 `openid` 登录原账号，新 `openid` 自动创建轻量账号；
   - 保存响应中的 `meta.session_token`；
   - 加载认证上下文并进入个人模式。
6. 微信自动登录失败：清除无效认证状态，静默降级游客，本次运行不再自动尝试。
7. 上下文加载完成后再恢复目标路由。

自动登录成功或自动注册成功不显示“登录成功”Toast。自动登录失败也不弹阻塞提示，只有用户主动触发受限动作时才提示需要登录。

### 7.2 H5

H5 不执行微信自动登录：

- 无 Session 时进入游客模式；
- 有 Session 时按现有规则恢复；
- 手机验证码和邮箱密码继续由用户主动发起；
- 公开房源仍不需要认证。

### 7.3 公开深链

从分享卡片或二维码进入公开房源时，也先完成上述启动身份解析。登录成功后仍以个人视角访问公开接口，不携带组织上下文，不自动切换到组织模式。

## 8. 主动退出与主动登录

### 8.1 主动退出

1. 先将 `wechatAutoLoginDisabled` 设为 `true`；
2. 立即清除本地 Session；
3. 尝试撤销远端 Session，失败时不恢复本地状态；
4. 清除用户和业务上下文，进入游客模式；
5. 后续冷启动不再自动登录。

因此，小程序中的“退出登录”语义是“在这台设备上停止自动登录”。清除小程序数据或重新安装后，该标记自然消失。

### 8.2 主动登录

用户在退出后仍可从“我的”或受限操作进入登录页。微信、手机号或邮箱登录成功后：

- 保存新 Session；
- 将 `wechatAutoLoginDisabled` 设为 `false`；
- 刷新个人上下文；
- 恢复目标页面和待执行动作。

只有登录成功后才清除主动退出标记，登录失败不改变用户选择。

## 9. 运行期认证恢复与请求重放

### 9.1 恢复触发

业务 API 返回明确的 `401/410` 时：

- H5 延续手动登录流程；
- 微信小程序在未主动退出时调用全局 `authRecoveryTask`；
- 并发请求等待同一个恢复结果，不分别调用 `uni.login`；
- 恢复成功后刷新应用上下文。

网络错误、`403` 和普通业务错误不触发微信重登录。

### 9.2 重放策略

请求选项增加明确的认证重试策略，而不是仅按 HTTP method 猜测：

- 默认 GET 查询允许重试一次；
- 收藏、取消收藏等业务上幂等的操作显式标记为允许重试；
- 支付、提现、审批、创建订单及其他可能产生不可逆结果的写操作显式禁止重放；
- 已重试请求再次返回认证失败时立即结束，不形成循环。

恢复失败时：

- 清除无效 Session；
- 进入游客模式；
- 原请求返回失败；
- 不显示虚假的成功状态；
- 需要登录的页面或动作再引导用户主动登录。

## 10. 微信轻量账号定义

轻量账号以真实身份关系判断，不依赖 `wx_` 用户名前缀。

允许自动合并的来源账号必须满足：

- 当前通过 `wechat_miniprogram` 登录；
- 没有组织成员关系；
- 没有团队成员关系、角色绑定或权限绑定；
- 没有房东、员工、联系人或其他业务身份；
- 没有实名认证记录；
- 没有订阅订单、支付、退款、发票等业务财务记录；
- 没有收益分配、应计收益、提现或钱包流水；
- 没有待办、任务负责人等需要保留责任主体的业务记录；
- 没有其他账号合并记录指向不一致的主账号。

钱包账户空行本身不构成阻断。只有非零余额、非零累计值、钱包流水或提现记录才属于财务阻断项。

目标主账号可以具有组织和业务身份，但只要来源或目标任一账号存在财务数据，自动合并就必须停止。

## 11. 账号合并计划与事务

### 11.1 合并触发

当前微信轻量账号调用微信手机号绑定接口，微信返回的已验证手机号属于另一个有效账号时，构建合并计划：

- `source_user`：当前微信轻量账号；
- `target_user`：已有手机号账号；
- `canonical_user`：最终主账号，默认等于 `target_user`。

目标账号即使启用 MFA，微信手机号授权仍视为充分证明，直接进入合并资格检查，不追加 MFA 流程。

### 11.2 前置检查

所有检查必须在写入前完成，并在事务内使用行锁重新确认：

- 锁定来源用户、目标用户、手机号占用关系和微信 SocialAccount；
- 确认来源仍是当前登录用户；
- 确认手机号仍属于同一目标账号；
- 确认来源符合轻量账号条件；
- 确认双方没有财务阻断项；
- 确认不存在冲突的账号合并关系；
- 构建完整迁移摘要。

任何检查失败都不执行部分绑定、SocialAccount 迁移或用户停用。

### 11.3 自动迁移范围

| 数据类型 | 规则 |
|---|---|
| `wechat_miniprogram` SocialAccount | 迁移到主账号；目标已有同 provider 冲突时停止自动合并 |
| 收藏 | 合并集合，按目标类型与目标 ID 去重，保留较早创建时间 |
| 用户设置 | 主账号同 key 优先，来源仅补充主账号缺失项 |
| 通知偏好 | 主账号同分类优先，来源仅补充缺失分类 |
| 个人通知 | 接收人迁移到主账号，保留已读和过期状态 |
| 姓名、头像等资料 | 主账号非空值不覆盖，只填补空字段 |
| 个人媒体 | 在引用迁移成功后迁移所有权，保持媒体引用有效 |
| 推荐关系 | 单方存在时迁移；双方存在或违反唯一约束时停止自动合并 |
| 登录身份 | 可安全迁移的 SocialAccount 归入主账号；主账号邮箱、手机号和密码不覆盖 |

历史操作人、审核人、创建人、收益受益人、资金流水操作人等审计字段不改写。允许自动合并的来源账号按定义不应存在业务责任记录；若检查发现此类记录，改为人工处理。

### 11.4 合并记录

新增持久化账号合并记录，至少保存：

- 唯一的来源账号；
- 目标主账号；
- 合并原因和身份来源；
- 合并时间；
- 迁移项目及数量摘要；
- 触发方式；
- 成功结果。

来源和目标使用保护性外键，不允许物理删除导致审计链断裂。服务必须解析规范主账号，避免形成多级合并链。

### 11.5 合并完成

事务内完成数据迁移和合并记录后：

1. 将来源账号设为不可登录，但不物理删除；
2. 撤销来源账号全部 Session；
3. 保留历史审计记录中的来源用户 ID；
4. 为当前设备建立目标主账号的新 Session；
5. 保留目标账号其他设备的有效 Session；
6. 返回已合并的手机号和主账号上下文。

再次使用同一微信 `openid` 登录时，必须解析到目标主账号，不得重新创建来源账号。

## 12. 自动合并阻断与人工处理

以下任一情况返回“需要人工合并”，不做任何写入：

- 来源账号不是轻量账号；
- 来源账号存在组织、团队、角色、房东或业务身份；
- 任一账号存在财务数据；
- 来源账号存在实名或业务责任记录；
- 推荐关系、登录身份或其他唯一数据发生冲突；
- 目标账号已停用；
- 合并关系存在循环、分叉或目标不一致；
- 并发操作后手机号或 SocialAccount 归属已变化。

手机号绑定 API 使用 HTTP `409` 返回稳定业务码，例如 `ACCOUNT_MERGE_REVIEW_REQUIRED`，并提供不包含敏感明细的阻断分类。前端提示用户该手机号已有无法自动合并，需要人工处理。人工处理功能本身不在本次范围内。

## 13. 行为分析的最小兼容

行为分析不是本次主要目标，只做自动登录需要的最小一致性处理：

- 采集接口继续允许匿名请求；
- Session 有效时同时记录匿名设备哈希和用户；
- Session 缺失或失效时允许降级匿名采集，不阻塞业务；
- 不回写历史事件；
- 不新增统计页面、报表或复杂账号别名聚合；
- 账号合并记录为以后按规范用户聚合提供依据。

客户端现有批量队列、失败回队和匿名 ID 持久化继续使用。行为采集失败不能影响找房、收藏和登录。

## 14. 用户体验与错误处理

| 场景 | 行为 |
|---|---|
| 首次微信小程序启动 | 显示短暂启动状态，静默注册或登录后进入首页 |
| 自动登录成功 | 不显示登录成功提示，直接进入个人模式 |
| 自动登录失败 | 本次运行进入游客，下次冷启动再尝试 |
| 用户主动退出 | 进入游客，并在后续启动保持游客 |
| 主动重新登录成功 | 清除退出标记并恢复自动登录 |
| 已有 Session 网络校验失败 | 保留 Session，显示可重试启动状态 |
| 已有 Session 返回 `401/410` | 清除 Token，微信端尝试一次静默恢复 |
| 运行期认证失效 | 单例恢复，安全请求重试一次 |
| 自动账号合并成功 | 刷新为主账号，不要求再次登录 |
| 自动账号合并被阻断 | 不部分迁移，提示需要人工处理 |

启动、自动登录和运行期恢复必须分别记录可诊断日志，但日志不得包含微信 code、Session Token、手机号明文或微信 session key。

## 15. 测试设计

### 15.1 前端单元测试

- 无 Session 且允许自动登录时调用一次微信登录；
- 自动登录成功后保存 Session 并进入个人模式；
- 同一次运行多次 `onShow` 不重复自动登录；
- 自动登录失败后本次运行保持游客；
- 主动退出标记跨启动生效；
- 主动登录成功后清除退出标记；
- H5 不执行微信自动登录；
- Session `401/410` 清除并触发恢复；
- Session 网络错误保留 Token；
- 并发认证失败只创建一个恢复任务；
- 允许重试的请求只重放一次；
- 敏感写操作不自动重放；
- 恢复失败不产生虚假成功状态。

### 15.2 后端账号合并测试

- 微信新 `openid` 自动创建轻量用户并返回 Session；
- 已有 `openid` 登录原用户，不重复创建；
- 安全轻量账号可以合并到已有手机号账号；
- 主账号资料优先，来源只填补空字段；
- 收藏去重且不丢失；
- 用户设置和通知偏好按主账号优先合并；
- 通知及个人媒体迁移后仍可访问；
- 来源账号停用且 SocialAccount 指向主账号；
- 来源 Session 全部撤销，当前设备切换到主账号；
- 目标账号启用 MFA 时仍允许直接合并；
- 来源存在组织、团队、权限或业务身份时返回 `409`；
- 任一账号存在非零钱包、流水、提现、收益分配或其他财务记录时返回 `409`；
- 空钱包账户本身不阻止合并；
- 实名、推荐关系冲突和登录身份冲突正确阻断；
- 事务中任一步骤异常时全部回滚；
- 同一手机号并发合并只能成功一次；
- 已合并 `openid` 后续登录解析到规范主账号。

### 15.3 集成与环境验证

- 复用 mock `jscode2session` 的后端集成测试，不在自动测试中调用真实微信接口；
- 使用 Node 22 运行小程序端测试、类型检查和构建；
- 分别构建微信小程序和 H5，确认条件编译边界；
- 在微信开发者工具中验证首次启动、已有 Session、主动退出、自动登录失败和真实手机号授权；
- H5 浏览器验证游客访问与手动登录不受影响。

## 16. 完成标准

- 微信小程序无 Session 时可以静默注册或登录，并在身份稳定后进入首页；
- 自动登录失败不会阻塞公开浏览；
- 用户主动退出后不会在后续启动被自动登录；
- 运行期 Session 失效可以单例恢复，且不会重复敏感写操作；
- H5 游客和手动登录流程保持不变；
- 只有严格定义的轻量账号能够自动合并；
- 安全个人数据完整合并，主账号资料优先；
- 组织、业务、实名冲突和财务数据能够可靠阻断自动合并；
- 来源账号及历史审计链被保留，不发生物理删除；
- 账号合并具备事务、并发和会话撤销测试；
- 后端目标测试、前端测试、类型检查和双端构建具有最新验证结果；
- 未完成微信开发者工具真实环境验证时，不宣称真机链路已验证。
