# 个人负责房源与待勘察视图设计

日期：2026-08-29
状态：设计已确认并完成实现

## 1. 背景

当前房源列表已经能够通过实时条件识别当前员工负责且需要勘察的房源，但入口仍主要表现为“待勘察”视图。员工缺少一个稳定的“我的房源”范围，无法先查看自己负责的全部房源，再继续收窄到其中需要补充资料或重新核对的房源。个人工作台也尚未形成能够直接看到待勘察数量和具体房源的闭环入口。

本设计不把勘察扩展为独立任务系统，而是在现有房源列表和个人工作台中建立“负责范围 → 待勘察子集”的信息层级。

## 2. 已确认决策

- 采用“范围 + 任务双层”结构。
- 房源列表一级范围为“全部房源 / 我的房源”。
- “我的房源”内二级视图为“全部 / 待我勘察”。
- 待勘察仍由房源当前事实实时派生，不创建勘察任务记录。
- 不做手机端、小程序或 H5 页面。
- 不做抢占、放弃、勘察奖励、审核或独立完成流程。
- 资料满足条件或完成有效性确认后，房源自动退出待勘察视图。

## 3. 目标

- 让员工在房源模块内快速查看自己负责的全部房源。
- 让员工从个人负责房源中继续查看需要自己勘察的房源。
- 清楚解释每套房源为什么需要勘察，并提供与原因对应的资料维护入口。
- 在个人工作台展示待勘察总数和优先房源，并能直接进入完整列表。
- 复用现有房源、职责和设置能力，不新增业务模型或独立应用。
- 页面状态可刷新、可复制链接，并兼容现有待勘察链接。

## 4. 非目标

- 不建设勘察任务生命周期。
- 不记录员工抢占、领取、放弃、完成或奖励。
- 不记录独立的勘察历史、勘察批次或勘察结果审核。
- 不读取照片或视频文件自身的更新时间。
- 不增加各勘察原因的汇总统计卡。
- 不改造小程序、H5 或专门的现场采集页面。
- 不调整现有职责分配规则。

## 5. 待勘察派生规则

待勘察房源必须同时满足：

```text
当前员工负责该房源
AND
（缺少照片 OR 缺少视频 OR 房源更新时间超过租户配置周期）
```

具体规则：

- 当前员工负责范围继续复用 `PropertyResponsibility` 和现有负责房源过滤逻辑。
- 缺少照片、缺少视频可以同时成立，并同时展示原因。
- 资料过期使用 `House.updated_at` 判断，不读取媒体文件更新时间。
- 过期周期使用组织通用设置 `property_rental.inspection_max_age_days`。
- 默认周期为 180 天，允许组织在通用设置中调整。
- 勘察原因只表示当前资料状态，不创建持久化任务状态。

## 6. 页面信息架构

继续使用现有房源列表页面：

```text
/dashboard/rental/properties/list
```

页面范围分为两层：

```text
全部房源

我的房源
├─ 全部
└─ 待我勘察
```

### 6.1 一级范围

房源列表顶部增加：

- 全部房源。
- 我的房源。

“全部房源”保持现有组织房源列表语义和默认行为。“我的房源”只展示当前员工承担职责的房源，同时继续支持小区、楼栋、房态和关键词筛选。

默认仍进入“全部房源”，避免改变管理人员现有使用习惯。没有查看全部房源权限但允许查看负责房源的账号，应直接进入“我的房源”，且不展示不可用的“全部房源”入口。

### 6.2 二级视图

选择“我的房源”后显示：

- 全部：当前员工负责的全部房源。
- 待我勘察：当前员工负责且命中任一待勘察条件的房源。

“待我勘察”不是与“我的房源”并列的第三类范围，而是个人负责房源的业务子集。

## 7. URL 与状态同步

前端继续使用现有 `view` 查询参数表达稳定视图：

```text
无 view 参数       -> 全部房源
view=mine          -> 我的房源 / 全部
view=inspection    -> 我的房源 / 待我勘察
```

规则：

- 现有 `/rental/properties/list?view=inspection` 链接保持有效。
- 一级和二级切换必须同步更新 URL。
- 小区、楼栋、房态、关键词、排序和分页参数继续与视图状态共同保留。
- 切换一级或二级视图时回到第一页，并清除跨范围保留后会产生误解的已选房源。
- 刷新页面、浏览器前进后退和复制链接后应恢复相同视图。
- 工作台“查看全部”直接跳转到 `view=inspection`。

## 8. 顶部数量与上下文

页面只展示两个核心数量：

- 我负责的房源数量。
- 待我勘察的房源数量。

在“我的房源”中，二级视图标签可显示为：

```text
全部 28 | 待我勘察 6
```

数量通过现有分页房源接口的 `total` 获取。可以使用轻量查询分别获取负责房源总数和待勘察总数，不增加独立统计接口。

第一版不展示“缺照片 X 套、缺视频 X 套、资料过期 X 套”等汇总数字，避免引入重叠口径和额外聚合契约。

## 9. 待勘察列表

待勘察视图继续复用现有房源表格、房源范围导航、搜索、房态筛选、分页、列设置和实体预览能力。

### 9.1 关键列

待勘察视图必须清楚展示：

- 房源识别信息：小区、楼栋、房号及当前已有的辅助信息。
- 房态。
- 待勘察原因。
- 资料更新时间，即 `House.updated_at`。
- 操作。

“我的房源”范围已经表达负责人是当前员工，因此不重复增加“负责人：我”列。

### 9.2 原因展示

原因使用可读标签并允许同时展示多个：

- 缺少照片。
- 缺少视频。
- 超过 `{inspection_max_age_days}` 天未更新。

缺媒体属于需要关注状态，使用警示语义；资料超过周期属于已逾期状态，使用错误语义。状态不能只依赖颜色，必须保留完整文字。

### 9.3 原因筛选

待勘察视图提供“勘察原因”筛选：

- 全部原因。
- 缺少照片。
- 缺少视频。
- 资料过期。

筛选通过扩展现有房源列表查询参数实现，不增加新接口。第一版不在筛选项旁展示原因数量。一个房源可以同时命中多个原因，因此切换原因时结果数量不要求相加等于待勘察总数。

查询参数固定为：

```text
inspection_reason=missing_images
inspection_reason=missing_videos
inspection_reason=expired
```

## 10. 行操作与资料更新闭环

行操作根据当前原因给出明确动作：

- 缺少照片或缺少视频：主要操作为“补充资料”。
- 仅资料过期：主要操作为“更新资料”。
- 同时存在缺媒体和资料过期：主要操作仍为“补充资料”，并保留“查看详情”。

操作直接进入现有房源编辑或媒体维护能力，不创建勘察表单。

### 10.1 缺媒体

员工补充照片或视频并保存后：

- 刷新该房源数据。
- 重新计算待勘察原因。
- 如果仍有其他原因，房源继续留在待勘察视图并只展示剩余原因。
- 如果所有原因均已消失，房源自动从当前列表移除。

### 10.2 资料过期但信息未变化

员工现场或通过其他方式核对资料后，可能确认房源信息仍然准确而无需修改字段。编辑界面需要提供“确认资料仍有效”操作：

- 复用现有房源更新接口。
- `HousePatchIn` 增加非模型、只写动作参数 `confirm_current: bool = False`。
- 前端向现有 `PATCH /houses/{house_id}/` 提交 `{ "confirm_current": true }`。
- 后端消费并移除该动作参数后调用 `house.save()`，只刷新自动维护的 `House.updated_at`，不得尝试把 `confirm_current` 写入模型字段。
- 不创建勘察完成记录、历史表或奖励记录。
- 成功后刷新房源列表和工作台待勘察查询。

普通房源字段编辑同样会刷新 `House.updated_at`，不需要额外确认。

## 11. 空、加载、错误与权限状态

### 11.1 空状态

- “我的房源 / 全部”为空：显示“当前没有分配给你的负责房源”。
- “我的房源 / 待我勘察”为空：显示“当前负责房源均无需勘察”。
- 待勘察空状态提供“查看我的全部房源”。
- 搜索或筛选导致无结果时，显示“未找到符合条件的房源”并提供清除筛选。

### 11.2 加载与错误

- 表格使用现有加载状态。
- 顶部数量加载时显示稳定占位，不闪现错误的 0。
- 主列表失败时保留现有错误处理和重试能力。
- 数量轻量查询失败不能阻塞主列表；对应数量显示为不可用状态。

### 11.3 权限

- 所有查询继续受当前组织隔离和房源查看权限约束。
- “我的房源”只返回当前账号根据职责规则命中的房源。
- 未承担任何职责的员工看到明确空状态，不回退为全部房源。
- 工作台组件与房源列表使用相同权限和职责过滤语义。

## 12. 个人工作台组件

在“我的工作台”增加独立的“待勘察房源”组件，不把内容继续挤入现有“待办概览”。

组件内容：

- 待勘察总数。
- 前 5 套待勘察房源。
- 每套房源的房号、楼栋或小区识别信息。
- 当前待勘察原因。
- “查看全部”入口。

交互：

- 点击房源进入对应房源详情或资料维护位置。
- “查看全部”跳转到 `/rental/properties/list?view=inspection`。
- 无数据时显示“当前负责房源均无需勘察”。
- 组件支持工作台现有的显示、隐藏和布局偏好能力。

数据：

```text
responsibility=mine
inspection_due=true
page=1
page_size=5
```

使用分页响应的 `total` 展示总数，使用 `items` 展示前 5 套房源，不增加工作台专用后端接口。

## 13. 前后端边界

### 13.1 后端

后端继续负责：

- 当前组织隔离。
- 当前员工负责房源过滤。
- 待勘察条件计算。
- 租户过期周期读取。
- 勘察原因计算。
- 勘察原因筛选。
- “确认资料仍有效”时刷新 `House.updated_at`。

现有列表接口参数映射固定为：

```text
view=mine       -> responsibility=mine
view=inspection -> responsibility=mine + inspection_due=true
```

`view` 仅是前端 URL 状态，不作为新的后端查询参数。

不新增勘察模型、工作台统计接口或新的业务应用。

### 13.2 前端

前端负责：

- `view` 与双层 Tab 的映射。
- URL、筛选、分页和选择状态同步。
- 顶部两个数量的轻量查询。
- 原因标签和原因筛选。
- 根据原因提供对应操作。
- 保存后失效房源列表及工作台相关查询。
- 工作台组件的加载、错误、空状态和跳转。

前端不得使用当前页数据自行推导组织范围内的勘察总数或原因总数。

## 14. 验收标准

- 房源列表可在“全部房源”和“我的房源”之间切换。
- “我的房源”只展示当前员工负责的房源。
- “我的房源”内可切换“全部”和“待我勘察”。
- `view=mine` 和 `view=inspection` 可刷新、可复制并正确恢复视图。
- 原有 `view=inspection` 链接继续有效。
- 待勘察视图显示完整原因和房源更新时间。
- 原因筛选由后端对完整结果集执行，而不是只过滤当前页。
- 缺少媒体的房源可直接进入资料补充流程。
- 资料未变化时可确认仍有效并刷新房源更新时间。
- 原因消失后房源自动退出待勘察视图。
- 个人工作台展示待勘察总数和前 5 套房源，并可进入完整列表。
- 无负责房源、无需勘察、筛选无结果、加载失败和数量查询失败均有明确状态。

## 15. 验证范围

后端验证：

- 负责房源过滤。
- 缺照片、缺视频、资料过期及多原因组合。
- 组织级过期天数设置。
- 勘察原因筛选。
- 确认资料仍有效后 `updated_at` 刷新。
- 组织隔离和未分配员工空结果。

前端验证：

- 双层 Tab 与 URL 映射。
- 切换范围后分页、选择状态和筛选处理。
- 数量加载、失败与展示。
- 原因标签、原因筛选和行操作。
- 工作台组件的列表、空状态、错误重试和跳转。
- 房源更新后相关查询失效并自动移出待勘察列表。

静态和构建验证：

- TypeScript 检查。
- Biome / ESLint 检查。
- Django system check。
- 迁移检查；本设计原则上不新增模型迁移。
