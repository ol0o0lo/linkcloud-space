# 公开房源跨城市地区选择设计

## 背景

首页导航栏目前固定展示“全城”，但没有选择交互。公开房源数据已经在 `Estate` 上保存省、市、区县，公开房源列表接口也接受 `province`、`city`、`district` 参数；现有筛选项接口只分别返回三个扁平字符串数组，无法表达城市与行政区的从属关系，也没有跨页面共享的地区状态。

本次设计补齐“全国、城市全城、城市行政区”三级找房范围，并让首页瀑布流、找房列表和地图找房使用同一选择结果。

## 目标

- 支持用户在已开通城市之间切换，并进一步选择城市内行政区。
- 点击首页导航栏地区后在当前页面完成选择，不跳转新页面。
- 选择后直接刷新首页当前瀑布流。
- 首页、找房列表和地图找房共享同一地区范围。
- 地区选择在本机持久化，重新打开应用后恢复。
- 同名行政区必须由省、市共同限定，不能跨城市混入房源。
- 只向用户展示当前存在有效公开房源的城市和行政区。

## 非目标

- 首版不建设完整的全国行政区主数据表。
- 首版不展示尚无公开房源的待开通城市。
- 首版不提供街道、商圈级行政区选择。
- 首版不将地区偏好同步到用户账号或服务端。
- 首版不在应用首次打开时自动申请定位权限。

## 方案选择

采用独立的公开房源地区接口，从当前有效公开房源实时聚合省、市、区县层级。

不直接复用现有筛选项接口的扁平数组，因为它无法判断行政区属于哪个城市，同名行政区存在串数据风险。暂不新增行政区模型，因为当前只需要展示实际有房源的地区，维护完整全国行政区目录会增加数据同步和运营成本。

## 地区范围模型

前端统一使用以下结构表示当前地区：

```ts
interface PublicHouseRegionSelection {
  province: string
  city: string
  district: string
}
```

字段为空的含义如下：

- 三个字段均为空：全国。
- 省、市有值，区县为空：所选城市全城。
- 省、市、区县均有值：所选行政区。

不允许只保存区县或只有省份没有城市的前端状态。地区匹配暂时继续使用后端现有字符串字段，但所有查询必须成组携带省、市、区县，不能仅凭区县筛选。

## 后端设计

### 地区聚合接口

新增公开接口：

```http
GET /api/public/houses/regions/
```

响应示例：

```json
{
  "items": [
    {
      "province": "广东省",
      "house_count": 168,
      "cities": [
        {
          "city": "深圳市",
          "house_count": 128,
          "districts": [
            { "district": "南山区", "house_count": 42 },
            { "district": "福田区", "house_count": 36 }
          ]
        }
      ]
    }
  ]
}
```

聚合数据只来源于 `get_public_houses_queryset()`，因此天然排除未上架房源和无效组织。查询还需要排除空白值以及历史占位值“默认”，并对首尾空白进行统一清理。

省份、城市、行政区按照稳定中文顺序返回；每一级返回对应公开房源数量。结果缓存 5 分钟，避免首页频繁执行分组聚合。首版允许缓存自然过期，不额外增加复杂的信号失效链路。

### 房源列表

公开房源列表已支持 `province`、`city`、`district`，保持现有接口不变。前端调用规则调整为：

- 全国：三个参数均不发送。
- 城市全城：发送 `province` 和 `city`。
- 行政区：同时发送 `province`、`city`、`district`。

后端暂时兼容旧客户端仅传 `district` 的行为，新客户端不再这样调用，避免破坏现有版本。

### 地图找房

公开地图接口补充可选参数 `province` 和 `city`，并与现有 `district` 一起传入 `apply_public_house_filters()`。地图聚合、地图列表和首页列表必须使用相同地区范围。

### 地区数据质量

公开房源发布前应确认所属小区的省、市、区县均为有效非占位值。已有“默认”或空地区数据不出现在地区接口中，但仍可在全国范围内被查询，避免直接改变历史房源可见性。

首版不引入行政区编码迁移。后续如果需要展示无房城市、运营开城或对接多个地图供应商，再增加基于行政区编码的地区主数据模型。

## 前端设计

### 共享状态

新增公开找房地区 Store，负责：

- 保存当前 `province`、`city`、`district`。
- 使用项目现有版本化存储方式进行本地持久化。
- 加载地区接口并校验缓存选择是否仍然有效。
- 城市变化时自动清空旧行政区。
- 暴露列表、地图和首页统一使用的请求参数。
- 暴露适合导航栏展示的短文案。

恢复顺序：

1. 恢复本地最后一次选择。
2. 使用地区接口验证选择仍存在。
3. 选择已失效时回退到全国，并以轻提示说明当前地区暂无公开房源。
4. 没有历史选择时默认全国，不自动申请定位。

### 首页导航栏

导航栏左侧地区文案规则：

- 全国范围显示“全国”。
- 城市全城显示去掉行政后缀的城市短名，例如“深圳”。
- 选择行政区后显示去掉行政后缀的区县短名，例如“南山”。

点击地区后打开高位底部弹层，不离开首页。搜索框仍然进入找房列表，但找房列表读取同一地区 Store。

### 地区选择弹层

弹层标题为“选择地区”，使用高尺寸底部弹层，包含：

1. “全国”入口。
2. 用户主动触发的“定位当前城市”入口。
3. 已开通城市列表，展示城市名称和公开房源数量。
4. 选择城市后展示“全城”和该城市行政区列表。
5. 当前选择使用品牌色和勾选标记突出。

选择“全国”、城市“全城”或具体行政区后立即关闭弹层，重置首页分页并刷新当前瀑布流，不增加额外确认按钮。

首版城市数量预计较少，使用列表即可；当已开通城市超过 15 个时再增加城市搜索和字母索引，不提前建设复杂交互。

### 页面联动

- 首页：地区变化后刷新推荐瀑布流，保留当前“猜你喜欢、最新、低价”等推荐模式。
- 找房列表：读取共享地区并展示当前地区筛选；用户在找房页修改行政区时同步更新 Store。
- 地图找房：初始请求携带共享地区，地图视野移动不会清除地区选择。
- 搜索：从首页进入找房列表时不依赖 URL query 传递地区，避免 Tab 页面参数丢失。

### 附近模式

地区范围和当前位置附近查询是两种互斥的找房范围：

- 选择“附近”后进入附近模式，请求使用当前位置和半径，不叠加城市或行政区参数。
- 附近模式不删除已持久化的地区选择，退出附近模式后可以恢复原地区。
- 用户重新选择地区时立即退出附近模式。
- 界面处于附近模式时，地区位置显示“附近”，避免仍显示其他城市造成误解。

## 定位当前城市

定位必须由用户在地区弹层中主动触发。前端获取 GCJ-02 坐标后，调用后端逆地理编码接口；后端复用现有高德 Web Service Key，返回省、市、区县。

逆地理编码结果只在该城市存在公开房源时才能直接选中：

- 城市已开通：选择该城市全城，并允许继续选择行政区。
- 城市未开通：保持原选择，提示“当前城市暂未开通公开房源”。
- 定位或高德服务失败：保持原选择，提供重试，不影响手动切换城市。

逆地理编码不是首版地区选择上线的阻塞项，可以在手动跨城市切换完成后作为第二阶段接入。

## 错误与空状态

- 地区列表加载失败：弹层展示重试操作，首页继续使用当前或全国范围。
- 城市没有可用行政区：仍允许选择该城市全城。
- 地区切换后的房源为空：保留选择并展示正常房源空状态，不自动回退全国。
- 缓存选择已失效：仅在地区目录校验失败时回退全国。
- 请求竞态：快速切换地区时只接收最后一次分页刷新结果，复用现有分页任务抢占机制。

## 测试范围

### 后端

- 地区接口只聚合有效公开房源。
- 空值和“默认”地区不进入地区目录。
- 省、市、区县层级和房源计数正确。
- 两个城市存在同名行政区时不会合并。
- 列表和地图同时使用省、市、区县过滤。
- 地区接口缓存返回稳定结果。

### 前端

- 地区状态序列化、恢复和失效回退正确。
- 切换城市会清空旧行政区。
- 全国、城市全城、行政区请求参数正确。
- 首页切换地区后原地刷新瀑布流。
- 首页、找房列表和地图读取同一地区。
- 附近模式不叠加地区参数，重新选择地区后退出附近模式。
- 地区接口失败、定位失败和无房城市提示正确。

## 验收标准

- 用户可以从首页导航栏选择全国、任一有房城市及其行政区。
- 选择过程不跳转页面，完成后首页瀑布流立即刷新。
- 重新打开应用后仍保持最后一次有效地区选择。
- 首页、找房列表和地图展示的地区范围一致。
- 同名行政区不会跨城市返回房源。
- 附近模式与地区模式的界面文案和查询结果不存在冲突。
- 地区接口异常不会阻塞用户继续浏览全国公开房源。

## 实施阶段

1. 后端地区聚合接口、列表与地图筛选测试。
2. 前端地区 Store、持久化和请求参数适配。
3. 首页地区选择弹层与瀑布流刷新。
4. 找房列表、地图找房统一接入。
5. 用户主动定位与逆地理编码增强。
