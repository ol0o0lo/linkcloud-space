# 管理端交互闭环优化设计

## 背景与目标

本次优化面向尚未上线的 `frontend_admin` 活跃业务页面，目标是让运营列表具备可靠的服务端筛选和可恢复状态，让分页、筛选和详情能够通过 URL 保留，让高风险操作具备确认、防重复提交和明确结果反馈，并统一业务状态与键盘可访问性。

已经被组织工作区替代、且只由路由重定向保留兼容入口的旧成员、邀请、团队和旧空间概览页面不再修复。对应页面源码和测试将从项目中移出，但旧 URL 重定向继续保留，避免已有链接失效。

## 方案选择

采用端到端增量方案：扩展现有 Django Ninja 列表接口的查询参数，前端继续使用现有 React、Ant Design、ProTable 和 React Query 模式，不引入新的列表框架。

不采用纯前端筛选，因为纯前端只能筛选当前页，无法保证数据准确性；不进行全局列表框架重构，因为当前目标可以通过现有页面模式闭环，额外抽象会扩大回归范围。

## 一、未使用页面退役

退役以下无直接引用、且路由已重定向到 `/space/organization` 的页面及测试：

- `frontend_admin/src/pages/space/invites/`
- `frontend_admin/src/pages/space/members/`
- `frontend_admin/src/pages/space/teams/`
- `frontend_admin/src/pages/space/overview/`

仓库规则禁止物理删除，因此文件移动到用户本地可恢复的废纸篓目录，不进入项目构建和测试范围。`config/routes.ts` 中 `/space/members`、`/space/invitations`、`/space/teams` 等重定向继续保留；`SPACE_PATHS` 常量也保留，用于兼容外部链接和安全跳转。

## 二、后端查询能力

在不改变现有分页响应结构的前提下扩展查询参数：

### 平台订阅

- 订单：`keyword`、`organization_id`、`status`、`refund_status`、`created_from`、`created_to`。
- 开票申请：`keyword`、`organization_id`、`status`、`created_from`、`created_to`。
- `keyword` 匹配订单号、组织名称和组织 slug；开票申请额外匹配发票抬头和发票号码。

### 邀请奖励

- 邀请记录：`keyword`、`status`、`created_from`、`created_to`。
- `keyword` 匹配邀请人和受邀人的用户名、姓名与邮箱。

### 钱包

- 钱包账户：`keyword`、`created_from`、`created_to`。
- 提现申请：`keyword`、`status`、`created_from`、`created_to`。
- `keyword` 匹配用户 ID、用户名、姓名和邮箱。

日期筛选采用包含起点、排除终点的时间范围，前端选择日期时将结束日期转换为次日零点，避免漏掉结束日当天数据。

## 三、运营列表交互

订阅与订单、邀请奖励、钱包账户和提现管理增加紧凑筛选栏。筛选条件和页码写入 URL；修改筛选时回到第一页；无效 URL 参数回退到默认值。

订阅页面包含两个独立表格，分别使用 `order_*` 和 `invoice_*` 参数，避免两个表格互相改写分页和筛选。

每个列表区分：

- 首次加载；
- 空数据；
- 筛选无结果；
- 请求失败，并提供明确的重试按钮；
- 后台刷新，不清空当前数据。

重要操作成功后显示简短反馈，包括退款登记、开票处理、奖励规则保存、奖励审核、调账、提现审核和打款操作。

## 四、团队协作与订单状态

### 团队任务

URL 保存当前视图、两类列表各自页码、筛选条件和当前详情 ID。页面内打开详情时写入 URL，关闭详情时移除对应参数。

“接受任务”在请求期间显示行级 loading 并禁用重复点击；其他互斥状态操作同步禁用。

### 团队公告

URL 保存页码、状态、关键词和详情 ID。列表失败时显示错误说明与重试按钮，不再显示正常空状态。

### 套餐订单

URL 保存订单页码。加载失败时显示独立错误提示和重试按钮，而不是只把错误文案放入空状态。

## 五、危险操作和表单保护

邀请奖励“通过”和“驳回”先显示确认：说明审核对象和结果，其中通过会触发奖励发放。请求期间锁定当前行操作。

新建任务和新建公告在表单已填写且未提交时，关闭、按 Esc 或点击遮罩均提示是否放弃；请求提交期间继续禁止关闭。

## 六、可访问性与状态统一

安全设置中的密码、手机和 MFA 操作从无 `href` 的点击链接改为 `Button type="link"`，确保键盘可聚焦与触发。

状态展示优先复用 `AppStatusTag`：

- 现有 `invoice-request` 和 `wallet.withdrawal` 直接接入。
- 新增 `subscription.order`、`subscription.payment`、`subscription.refund`、`referral.record` 状态定义及对应图标定义。
- 状态必须同时包含文字、图标和语义色，不再由页面手写颜色。

## 七、数据流与错误处理

后端查询参数由生成的 OpenAPI 客户端承接，不手改生成文件。接口变更后运行项目现有 OpenAPI 生成命令。

URL 解析和写入使用小型纯函数，保留页面无关的其他查询参数和 hash。页面内部状态以 URL 初始化，交互时同步更新 URL；租户边界变化时清理不再有效的详情和页码。

请求失败保留现有筛选和输入；提交失败不关闭表单。全局请求错误提示继续保留，页面级错误负责解释当前区域为何不可用以及如何重试。

## 八、测试与验收

后端为每组新增查询参数补 API 测试，覆盖关键词、状态和日期边界。

前端按 TDD 补充以下测试：

- URL 初始化、更新和无效参数回退；
- 筛选请求参数和分页互不干扰；
- 失败态与空态区分及重试；
- 行级防重复提交与确认；
- 未保存表单关闭确认；
- 安全设置按钮语义；
- `AppStatusTag` 状态映射。

最终运行相关后端 pytest、相关前端 Vitest、TypeScript、改动文件 Biome 和 Ant Design 检查。全仓库既有检查问题单独报告，不混淆为本次改动失败。
