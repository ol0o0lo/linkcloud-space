# 房东邀请绑定与公开店铺设计

日期：2026-08-25
状态：待用户审阅

## 1. 背景

中介租户会先在系统内建立房东联系人并采集其房源。房东后续注册为普通平台用户，通过中介主动发出的临时邀请建立账号绑定。一个平台用户可以分别接受多个中介租户的邀请，并在房东视角中切换查看各租户交给自己管理的房源。

房东店铺不是独立经营实体，也不是中介代运营的店铺配置。它是基于“当前租户中的房东联系人及其公开房源”实时组成的公开页面。房东可以分享该页面或单套房源自行拓客；本期不接入咨询、线索分配或跨中介房源同步。

## 2. 目标

- 允许中介员工向当前租户中的房东联系人发出临时邀请。
- 只有邀请目标手机号与当前用户已验证手机号一致时才允许绑定。
- 继续使用现有 `Contact.user` 表示当前有效绑定，不新增绑定关系表。
- 一个房东联系人最多绑定一个普通平台用户；一个用户可以绑定多个租户中的房东联系人。
- 允许同一用户同时拥有员工身份和房东身份，两个视角及权限相互独立。
- 房东可以在已绑定的中介租户之间切换，并只读查看当前关系下的全部房源和租约。
- 为每个已绑定的租户级房东联系人提供独立的虚拟公开店铺及分享入口。
- 公开店铺自动展示当前联系人名下符合现有公开发布规则的招租中房源。

## 3. 非目标

- 不新增 `LandlordBinding`、`LandlordInvitation` 或 `LandlordStore` 数据库表。
- 不允许无邀请的手机号自动认领，也不跨租户扫描并自动绑定同手机号联系人。
- 不支持房东或中介解除绑定、换绑或误绑申诉流程。
- 不支持房东修改、删除、上下架房源或修改房态。
- 不支持房东编辑店铺名称、简介、头像、封面等装修资料。
- 不支持跨中介汇总店铺、跨中介同步房源资料或向第三方平台分发。
- 不实现租客咨询、聊天、线索、转交中介或客户隐私数据。
- 不实现店铺浏览、分享、咨询或成交分析。

## 4. 核心领域边界

### 4.1 平台用户

房东账号继续使用现有普通 `User`，不创建专门的房东账号模型。用户只要拥有至少一个符合条件的 `Contact.user` 绑定，就具备房东视角。

同一用户可以同时是某些组织的 `OrganizationMember`，并绑定一个或多个组织中的房东联系人。员工身份不授予房东权限，房东身份也不授予员工权限。

### 4.2 房东联系人

`Contact` 仍是租户内部房东档案及房源归属主体：

- `organization` 确定数据所属租户。
- `roles` 必须包含 `landlord`。
- `user` 为空表示未绑定；有值表示当前绑定的全局用户。
- `is_active` 决定联系人是否可以继续作为有效房东关系使用。

一个用户可以出现在不同租户的多个联系人上。一个联系人通过外键只能指向一个用户。

### 4.3 房东店铺

房东店铺是虚拟查询结果，不保存独立店铺记录。其组成规则为：

```text
店铺身份 = Contact.user 对应的 User
租户范围 = Contact.organization
房源范围 = House.landlord == Contact
公开房源 = 房源满足现有公开发布查询规则
```

每个租户级联系人拥有独立分享入口。同一用户在中介 A 和中介 B 的联系人不会合并为跨租户店铺。

## 5. 持久化与临时状态

### 5.1 数据库

继续以 `Contact.user` 作为绑定的唯一事实来源。不给联系人写接口暴露 `user_id`，只能由接受邀请服务写入。

为 `Contact` 增加可空、不可枚举且全局唯一的 UUID 公开分享标识 `public_key`：

- 默认可以为空。
- 首次成功接受邀请时生成。
- 用于公开店铺和店铺内单套房源分享。
- 联系人未绑定、已停用、失去房东角色或绑定用户失效时，即使 key 存在也不得公开解析。

已有 `Contact.user` 绑定的房东联系人通过数据迁移补齐 `public_key`，避免上线后只有新绑定房东可以分享。

本期不提供解绑，因此不设计 key 轮换和历史链接失效操作。

### 5.2 Redis 邀请

邀请仅是临时授权凭证，保存在 Redis，不写数据库。建议使用两个键：

```text
landlord-invite:token:{token}   -> 邀请载荷，TTL 7 天
landlord-invite:contact:{id}    -> 当前有效 token，TTL 7 天
```

邀请载荷至少包含：

- `contact_id`
- `organization_id`
- `inviter_user_id`
- 创建邀请时标准化后的手机号快照
- 创建时间

token 使用安全随机值且不可枚举。同一个联系人同时只保留一个有效 token。重新发送邀请时生成新 token，并通过 Redis 原子操作使旧 token 立即失效。

Redis 数据丢失只会使未接受邀请失效，不影响已经写入数据库的绑定关系。中介重新发送邀请即可恢复。

## 6. 邀请流程

### 6.1 创建或重新发送邀请

中介员工在联系人详情发起邀请。后端校验：

- 当前用户具有当前租户的联系人管理权限。
- 联系人属于当前租户。
- 联系人已启用。
- 联系人角色包含 `landlord`。
- 联系人手机号可以标准化为有效手机号。
- `Contact.user` 为空。

校验通过后生成新 token，以标准化手机号作为邀请手机号快照写入 Redis，并通过现有短信后端发送链接。重新发送会使此前 token 失效。

联系人列表中的“邀请待接受”状态是 Redis 临时状态，不是数据库状态；“已绑定”只由 `Contact.user` 判断。

### 6.2 查看邀请

公开邀请查询通过 token 返回最少展示信息：

- 中介组织名称。
- 房东联系人名称。
- 掩码后的受邀手机号。
- 邀请是否仍然有效。

接口不得返回完整手机号、联系人备注、内部房源或邀请人敏感信息。

### 6.3 接受邀请

用户必须先登录并完成手机号验证。接受服务执行以下校验：

```text
Redis token 存在且未过期
token 仍是该 contact_id 的当前有效 token
Contact 仍属于载荷中的 organization_id
Contact 已启用且仍包含 landlord 角色
Contact.user 为空
User.phone_verified == True
标准化 User 手机号 == 标准化 Contact 手机号 == 邀请手机号快照
```

任何手机号不一致都直接拒绝，不提供人工审批、员工代认领或管理员绕过入口。

写入时开启数据库事务并通过 `select_for_update()` 锁定联系人。校验通过后：

1. 写入 `Contact.user = request.user`。
2. 如果 `public_key` 为空则生成公开分享标识。
3. 数据库事务提交成功后尽力删除 Redis token 及联系人索引键；清理失败不回滚已经建立的绑定，剩余 token 由 TTL 自动清理。
4. 返回已绑定关系摘要，供房东端进入对应租户视角。

并发接受同一个邀请时，只有第一个事务可以写入。后续请求在拿到锁后发现联系人已绑定当前用户时按幂等成功处理；如果已绑定其他用户则返回冲突错误，绝不覆盖已有用户。

### 6.4 停止旧的自动认领

现有手机号绑定流程会在当前组织中自动查找同手机号联系人并写入 `Contact.user`。本设计启用后必须停止该行为。手机号验证只证明用户拥有手机号，不能替代中介主动邀请。

## 7. 房东视角与租户切换

### 7.1 独立于员工组织上下文

现有 `X-Org-Slug` 和 `request.org` 只接受 `OrganizationMember`，继续用于员工端。房东不因为接受邀请成为组织成员，也不复用员工组织切换状态。

房东关系列表直接查询：

```text
Contact.user == request.user
Contact.is_active == True
Contact.roles 包含 landlord
```

建议提供：

```text
GET /api/house/landlord/relationships/
```

每项返回：

- `contact_id`
- `organization_id`
- 组织名称和 slug
- 房东联系人名称
- 全部房源数量
- 当前公开房源数量

### 7.2 切换状态

房东切换的实际参数是 `contact_id`，不是员工端组织上下文。前端将选择保存为独立的 `selected_landlord_contact_id`，不得覆盖 `selectedOrgSlug`。

所有房东私有接口使用显式联系人路径：

```text
GET /api/house/landlord/contacts/{contact_id}/houses/
GET /api/house/landlord/contacts/{contact_id}/leases/
```

后端每次请求都验证：

```text
contact.user_id == request.user.id
contact.is_active == True
contact.roles 包含 landlord
```

不属于当前用户的 `contact_id` 统一返回 404，避免泄露其他租户和房东关系是否存在。

现有依赖 `request.org` 的 `/my-houses/`、`/my-leases/` 不再作为普通房东端的主要接口；可暂时保留兼容，但新房东端只调用显式联系人接口。

## 8. 房东私有数据范围

房东私有房源列表返回当前联系人名下的全部房源，包括：

- 空置
- 招租中
- 已租
- 装修中
- 已停用

租约列表仅返回当前联系人名下房源对应的租约。所有数据都由 `house.landlord_id == contact_id` 和联系人归属校验限定。

本期只提供只读接口。房东不能通过房东端修改房源字段、房态、媒体、公开描述、租约或合同，也不能删除房源。

## 9. 公开店铺与分享

### 9.1 整店公开页面

建议公开地址：

```text
/h5/landlord/{public_key}
```

公开 API 根据 `public_key` 查询联系人，并校验：

- 联系人已启用。
- 联系人角色包含 `landlord`。
- 联系人已绑定用户。
- 绑定用户账号有效。
- 绑定用户仍有已验证手机号。

公开身份信息实时读取绑定用户的全局资料：

- 姓名。
- 头像。
- 当前已验证手机号。

姓名使用用户全局展示名；未设置展示名时回退到用户名。手机号只在当前号码仍处于已验证状态时公开。

店铺没有独立名称、简介、封面或装修字段。组织只用于限定数据来源，不作为咨询接收方，也不公开中介员工联系方式。

### 9.2 房源公开规则

店铺房源不保存中间关系，也不提供单独展示开关。查询条件为：

```text
House.landlord == 当前 Contact
并且 House 位于现有全局公开房源查询集
```

因此房源只有在状态为招租中且满足现有公开发布规则时才展示。房态或资料变化会实时影响店铺，不需要额外同步。

店铺没有公开房源时仍返回有效页面，展示“暂无在租房源”。

### 9.3 单套分享

单套分享使用店铺上下文：

```text
/h5/landlord/{public_key}/houses/{house_id}
```

公开接口必须同时验证房源属于该联系人并位于现有公开查询集。不能仅凭合法 `house_id` 绕过店铺范围。

## 10. 身份变化规则

### 10.1 用户换号

手机号一致只用于首次接受邀请。绑定成功后，用户修改全局手机号不会解除已有绑定。公开店铺联系电话实时使用用户当前已验证手机号。

### 10.2 员工与房东双重身份

同一用户可以在同一组织或不同组织中同时拥有员工与房东身份：

- 员工端继续使用组织成员关系、`X-Org-Slug` 和现有 RBAC。
- 房东端使用 `Contact.user` 和显式 `contact_id`。
- 两个前端选择状态分别保存。
- 任一身份不得继承另一身份的接口权限。

### 10.3 联系人状态变化

联系人被停用或移除房东角色后：

- 不再出现在房东关系切换列表中。
- 房东私有接口返回 404。
- 公开店铺和单套分享返回 404。
- `Contact.user` 暂不自动清空，以免在没有解绑流程的情况下产生隐式关系变更。

恢复启用并重新添加房东角色后，原绑定继续生效。

## 11. API 轮廓

### 11.1 中介端

```text
POST /api/house/contacts/{contact_id}/landlord-invite/
```

创建或重新发送临时邀请。已绑定联系人返回 409。

联系人输出增加派生状态：

- `landlord_binding_status`: `unbound | invited | bound`
- `landlord_invite_expires_at`: 仅待接受时返回

### 11.2 邀请端

```text
GET  /api/house/landlord-invites/{token}/
POST /api/house/landlord-invites/{token}/accept/
```

邀请查询允许未登录访问最少展示信息；接受必须登录且手机号已验证。

### 11.3 房东私有端

```text
GET /api/house/landlord/relationships/
GET /api/house/landlord/contacts/{contact_id}/houses/
GET /api/house/landlord/contacts/{contact_id}/leases/
```

分页接口继续遵循项目约定，使用 `page`、`page_size` 和 `{ items, total, page, page_size }`。

### 11.4 公开端

```text
GET /api/house/public/landlords/{public_key}/
GET /api/house/public/landlords/{public_key}/houses/{house_id}/
```

公开接口不接受租户 slug 或联系人 ID，避免暴露可枚举内部标识。

## 12. 前端信息架构

### 12.1 中介管理端

联系人列表和详情显示房东绑定状态：

- 未绑定：显示“邀请房东”。
- 邀请待接受：显示过期时间和“重新发送”。
- 已绑定：显示“已绑定”，不提供邀请或解绑操作。

本期不提供邀请历史、撤销、解绑或换绑界面。

### 12.2 房东端

房东中心包含：

- 已绑定中介列表及当前选择。
- 当前联系人名下的只读房源列表。
- 当前联系人名下的只读租约列表。
- 公开店铺预览。
- 整店分享和单套公开房源分享。

房东选择以 `contact_id` 保存，不能复用员工端组织选择状态。

### 12.3 公开 H5

公开页面展示：

- 房东姓名、头像、当前已验证手机号。
- 符合公开规则的房源列表。
- 单套房源详情与分享能力。
- 无公开房源时的明确空状态。

本期不展示咨询按钮、聊天入口、中介员工联系方式或线索提交表单。

## 13. 错误处理

- Redis 不可用：创建、查看或接受邀请返回可重试的服务不可用错误，不写入绑定。
- token 不存在或 TTL 已到期：统一提示“邀请无效或已过期”，因为纯 Redis 临时邀请在键消失后不保留历史状态。
- 重新发送后的旧 token：返回邀请已失效。
- 用户未登录：要求登录后继续接受。
- 用户手机号未验证：引导完成手机号验证。
- 用户、联系人和邀请快照手机号任一不一致：返回 403，不提供绕过入口。
- 联系人已绑定：返回 409，禁止覆盖。
- 联系人停用或失去房东角色：邀请失效。
- 非本人 `contact_id`：房东私有接口返回 404。
- 无效或不可公开的 `public_key`：公开接口返回 404。
- 店铺中的房源不属于联系人或不再公开：单套公开接口返回 404。

## 14. 测试与验收

### 14.1 邀请

- 创建邀请写入双 Redis key，并设置 7 天 TTL。
- 重新发送生成新 token，旧 token 立即失效。
- 已绑定、停用、非房东角色或无有效手机号的联系人不能邀请。
- 邀请公开查询只返回最少且脱敏的信息。
- Redis 丢失或不可用不会影响已建立绑定。

### 14.2 接受与安全

- 用户必须登录且手机号已验证。
- 国内号码和 `+86` 格式经标准化后可以正确匹配。
- 手机号不一致、邀请无效或过期、旧 token、联系人停用均拒绝。
- 两个请求并发接受时只有一个实际执行绑定写入，当前用户的后续重试按幂等成功处理。
- 已绑定联系人不能被其他用户覆盖。
- 数据库已成功绑定但 Redis 清理失败时，当前用户重试接受仍得到幂等成功。
- 手机号绑定或登录本身不会自动认领任何联系人。

### 14.3 多租户与身份隔离

- 一个用户可以分别接受多个租户的邀请。
- 房东关系列表只返回当前用户有效的房东联系人。
- 切换 `contact_id` 后房源和租约严格按联系人隔离。
- 访问他人的 `contact_id` 返回 404。
- 同一用户兼具员工和房东身份时，员工组织上下文与房东联系人选择互不覆盖。
- 房东身份不能调用员工管理接口，员工身份也不能绕过房东联系人校验。

### 14.4 私有与公开房源

- 房东私有列表包含其名下全部房态的房源。
- 房东端没有修改或删除房源的写入口。
- 公开店铺仅展示联系人名下且符合现有公开规则的房源。
- 已租、停用或资料不满足公开规则的房源不会展示。
- 空店铺正常展示“暂无在租房源”。
- 单套分享不能访问其他联系人或不可公开的房源。

### 14.5 用户资料变化

- 用户更换并验证新手机号后绑定继续有效。
- 公开店铺联系电话更新为用户当前已验证手机号。
- 联系人停用或移除房东角色后，私有与公开入口都失效；恢复后原绑定继续有效。

## 15. 实施边界

本设计的第一期只交付：

1. Redis 临时邀请。
2. 接受邀请并写入 `Contact.user`。
3. 关闭现有无邀请自动认领。
4. 房东关系列表和显式 `contact_id` 切换。
5. 房东房源、租约只读查询。
6. 基于 `Contact.public_key` 的虚拟公开店铺和单套分享。
7. 中介端邀请状态与房东端基础入口。
