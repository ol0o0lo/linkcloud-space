# 角色管理工作台设计

日期：2026-08-24
状态：已被 `2026-08-24-role-management-scope-workbench-design.md` 取代

> 本文保留为方案演进记录。后续设计、计划和实施均以新的“角色作用范围工作台”设计文档为准。

## 1. 背景

现有权限管理将空间角色、空间授权、团队角色、团队授权拆成多个菜单和页面。组织架构重构后，员工及团队的角色分配已经具备明确的业务上下文，继续保留独立授权页面会造成入口重复，也会混淆“定义角色”和“给成员授权”两类任务。

本次设计面向租户管理员，将角色定义集中到一个工作台，将人员授权保留在组织架构中。

## 2. 目标

- 左侧菜单仅保留一个“角色管理”入口。
- 在同一页面管理空间角色和各团队的角色定义。
- 让管理员可以连续切换团队，不需要反复返回组织架构。
- 保留角色使用情况的审计能力，但不在角色管理中直接修改成员授权。
- 从组织架构进入时保留团队上下文。
- 明确加载、空、错误、只读、无权限和窄屏状态。

## 3. 非目标

- 不修改后端角色、权限点和授权关系的数据模型。
- 不新增空间授权或团队授权管理页面。
- 不在角色管理页面直接给成员分配或移除角色。
- 不重新增加组织根节点或改变组织架构的数据层级。
- 不兼容旧的权限管理四菜单信息架构；项目内部入口统一迁移到新的角色管理页面。

## 4. 核心原则

角色管理是规则中心，负责回答“这个角色能做什么”。

组织架构是执行中心，负责回答“谁拥有这个角色”。

两者通过上下文链接衔接，不在同一个界面重复提供授权编辑能力。

## 5. 信息架构

### 5.1 主导航

“空间管理”下保留：

- 组织架构
- 角色管理
- 套餐与用量
- 业务设置
- 消息触达

移除“权限管理”分组及以下菜单入口：

- 空间角色
- 空间授权
- 团队角色
- 团队授权

### 5.2 角色管理页面

页面标题为“角色管理”，说明文字为“定义空间与团队角色，成员授权在组织架构中完成。”

页面包含两个顶部 Tab：

- 空间角色
- 团队角色

“空间角色”用于管理作用于当前租户全局范围的角色。“团队角色”用于管理某个具体团队内部的角色。

## 6. 页面布局

### 6.1 空间角色

空间角色使用单栏表格，不显示团队导航。表格上方显示当前空间角色标题和“新建角色”按钮。

表格列：

- 角色
- 类型
- 权限
- 已授权
- 操作

### 6.2 团队角色

桌面端采用左右工作台布局：

- 左侧：团队列表。
- 右侧：当前团队的角色表格。

团队列表包含：

- 团队搜索。
- 当前账号有角色查看权限的团队。
- 每个团队的角色数量。
- 当前选中状态。

右侧包含：

- 当前团队名称。
- 角色作用范围说明。
- “新建角色”按钮。
- 与空间角色一致的角色表格。

管理员切换团队时只替换右侧内容，页面整体结构和 Tab 保持稳定。

## 7. 角色操作

### 7.1 新建和编辑

新建、编辑角色继续使用 Modal，字段保持现有功能：

- 角色名称。
- 权限点多选。

空间角色和团队角色复用同一套表单组件，但调用各自现有接口。

### 7.2 系统角色

系统角色只读：

- 不显示编辑操作。
- 不显示删除操作。
- 保留权限数量和已授权人数。

### 7.3 自定义角色

自定义角色允许有管理权限的管理员编辑和删除。删除前保留二次确认；已有授权引用时不得删除，并显示后端返回的明确错误。

## 8. 已授权成员 Drawer

“已授权”列显示使用当前角色的成员数量。数量大于零时可以点击，打开只读 Drawer。

Drawer 内容：

- 角色名称和作用范围。
- 已授权成员列表。
- 团队角色同时显示当前团队信息。
- 空状态“暂无授权成员”。
- 主操作“前往组织架构调整”。

Drawer 不提供直接分配、移除或批量修改功能。

点击“前往组织架构调整”进入组织架构：

- 空间角色进入组织架构的成员管理上下文。
- 团队角色进入对应团队上下文。

## 9. 组织架构衔接

组织架构继续承担授权操作：

- 选中员工后，在“权限管理”Tab 分配或移除空间角色、团队角色。
- 选中团队后，可以查看团队成员及其角色使用情况。
- 团队上下文提供“管理角色定义”快捷入口。
- 左侧组织架构底部保留“角色管理”快捷入口。

从具体团队点击“管理角色定义”时，打开角色管理页面的团队角色 Tab，并自动选中当前团队。

## 10. 路由与状态

唯一规范页面路由为：

```text
/space/access
```

查询参数：

```text
?tab=space
?tab=team&team=<团队ID>
```

规则：

- 缺少 `tab` 时默认打开空间角色；如果当前账号不能查看空间角色但能查看团队角色，则默认打开团队角色。
- `tab=team` 时优先使用合法且有权限的 `team` 参数。
- 没有 `team` 参数时选择团队列表中的第一个可见团队。
- 通过链接进入无权限团队时显示无权限状态，不自动切换到其他团队。
- Tab 和团队选择写入 URL，刷新、复制链接和浏览器前进后退均能恢复状态。

## 11. 权限规则

页面首先加载一次组织架构导航能力数据，并复用以下能力：

- `role_view`：查看空间角色。
- `role_manage`：新建、编辑、删除空间角色。
- `team_role_view_ids`：允许查看角色的团队 ID。
- `team_role_manage_ids`：允许管理角色的团队 ID。

展示规则：

- 两类角色都无查看权限：显示整页“无权访问角色管理”。
- 没有空间角色查看权限：空间角色 Tab 显示无权限状态。
- 团队列表只显示当前账号有角色查看权限的团队。
- 只能查看不能管理时保留表格和已授权 Drawer，隐藏新建、编辑和删除操作，并显示简短只读提示。
- 通过链接进入无权限团队时明确显示无权限，不泄露团队角色数据。

## 12. 数据流与缓存

- 页面级只加载一次角色管理导航能力。
- 空间角色 Tab 激活后加载空间角色和空间授权关系。
- 团队角色 Tab 激活后加载可见团队列表。
- 选中团队后加载该团队的角色和团队授权关系。
- 角色和授权查询键继续包含空间 slug；团队查询键额外包含团队 ID。
- 切换团队时保留 React Query 缓存，返回已访问团队时直接展示缓存数据并在后台按现有策略刷新。
- 新建、编辑或删除后只失效对应空间或团队的角色、授权查询，不清空其他团队缓存。

## 13. 页面状态

### 13.1 加载

- 首次进入时，角色工作区只显示一组统一骨架屏。
- 团队切换时保留左侧团队列表，仅右侧角色区域进入加载状态。
- 避免团队列表、角色表格和权限状态分别闪烁。

### 13.2 错误

- 导航能力加载失败：整页错误提示和“重新加载”。
- 团队列表加载失败：左侧区域错误提示和重试。
- 角色或授权数据加载失败：右侧区域错误提示和重试，不影响团队列表切换。
- 新建、编辑和删除失败：保留 Modal 或当前页面状态，并展示真实请求错误。

### 13.3 空状态

- 没有团队：提示前往组织架构新建团队。
- 当前团队没有自定义角色：仍展示系统角色；有管理权限时保留“新建角色”。
- 角色无人使用：Drawer 显示“暂无授权成员”。

## 14. 响应式

桌面端保留左侧团队列表和右侧角色表格。

窄屏下：

- 团队列表收敛为角色表格上方的团队选择器。
- 角色表格允许横向滚动，角色名称和操作列保持可用。
- 已授权成员 Drawer 使用接近全屏宽度。
- Tab、选择器和主操作保持固定阅读顺序，不把新建操作藏入多级菜单。

## 15. 组件边界

建议拆分为以下职责清晰的组件：

- `RoleManagementPage`：页面容器、URL 状态、Tab 和全局权限状态。
- `OrganizationRolesPanel`：空间角色查询、表格和角色操作。
- `TeamRolesPanel`：团队选择、团队角色查询、表格和角色操作。
- `TeamRoleNavigator`：团队搜索、数量、选中状态和窄屏选择器。
- `RoleTable`：空间与团队共用的角色表格。
- `RoleEditorModal`：共用角色表单和保存状态。
- `RoleUsageDrawer`：只读授权成员列表和组织架构跳转。

页面组件不直接实现成员授权写操作。

## 16. 测试与验收

至少覆盖：

- 左侧菜单只显示一个“角色管理”入口。
- 默认空间角色 Tab。
- Tab 与 URL 参数双向同步。
- 团队列表只显示有查看权限的团队。
- 团队切换更新 URL 和右侧数据。
- 从组织架构携带团队 ID 进入时恢复团队上下文。
- 空间角色和团队角色的新建、编辑、删除调用正确接口并失效正确查询。
- 系统角色没有编辑、删除操作。
- 只读权限隐藏写操作但保留表格和 Drawer。
- 无权限团队深链接显示无权限且不加载角色数据。
- 已授权人数打开正确的成员 Drawer。
- Drawer 跳转到正确的组织架构上下文。
- 加载、错误、无团队、无人授权等状态。
- 窄屏团队选择器和角色表格基本可用。

## 17. 已确认决策

- 采用独立角色管理工作台，不完全嵌入组织架构。
- 角色管理页面同时管理空间角色和团队角色。
- 团队角色使用左侧团队列表，而不是单一顶部下拉框。
- 已授权人数打开只读 Drawer。
- 成员授权继续在组织架构中完成。
- UI 使用“空间角色”，不使用技术性更强的“租户角色”。
