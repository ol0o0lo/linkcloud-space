# 小程序租客、房东与中介业务闭环设计

## 1. 文档定位

本文定义 `frontend_miniprogram/` 在微信小程序与 H5 中补齐租客、房东和中介三种业务视角的产品范围、交互边界、工程结构、接口契约和验收方式。

目标是让同一用户在移动端按已有关系进入租客、房东或组织工作空间，并完成与 `frontend_admin/` 非超级管理员能力基本一致的业务结果。移动端不复制桌面端的菜单、表格和抽屉布局，但必须复用同一套后端数据、权限、状态和校验。

本文建立在以下现有成果之上：

- 当前未提交的小程序工程底座重构；
- `docs/superpowers/specs/2026-09-06-miniprogram-foundation-redesign-design.md`；
- `docs/miniprogram-context-api-contract.md`；
- `docs/miniprogram-capability-matrix.md`；
- 管理端当前路由、页面行为、OpenAPI 客户端和后端接口。

如旧文档与本文冲突，以本文为准。本文特别覆盖以下旧规划：

- 不新增“找房单 / 找房需求”领域和接口；
- 不新增租客确认租约、提出异议、确认版本等状态；
- 不新增房东审批、改价、上下架或租约编辑能力；
- 租赁流程、状态转换和权限继续采用管理端与现有接口的默认行为。

## 2. 已确认目标

### 2.1 产品范围

- 一个应用承载游客、租客、房东和中介视角；
- 微信小程序与 H5 同时支持；
- 三个登录后视角全部推进，不把本次范围缩减为单一租客闭环；
- 中介视角覆盖完整组织工作台，并按现有 RBAC 动态展示能力；
- 排除超级管理员及平台级运营后台；
- 当租客个人访问能力缺少安全接口时，允许补充最小后端接口；
- 不为移动端新增另一套业务状态、校验和权限事实。

### 2.2 登录策略

- 游客可以免登录浏览公开房源、公开房东店铺和公开配房分享；
- 收藏、预约、个人消息和本人租约等个人动作按需登录；
- 微信小程序优先使用微信登录自动建立或恢复平台账号；
- H5 提供手机号验证码和邮箱密码登录；
- 需要建立租客业务关系的动作要求用户先完成手机号验证；
- 登录前保存目标页面和一次性动作，登录后最多恢复执行一次。

### 2.3 对齐原则

“对齐管理端”指以下结果一致：

1. 同一用户、组织和权限看到相同业务数据范围；
2. 同一动作使用相同后端接口或同一领域服务；
3. 状态枚举、状态转换、字段校验和错误结果一致；
4. 小程序修改后，管理端刷新即可看到相同结果，反之亦然；
5. 移动端可以重组导航和页面交互，但不能改变业务语义。

## 3. 模式、上下文与权限

### 3.1 应用模式

| 模式 | 进入条件 | 请求作用域 | 数据范围 |
| --- | --- | --- | --- |
| 游客 | 无有效登录会话 | `public` | 全平台公开房源、公开房东店铺、公开配房分享 |
| 租客 | 已登录 | `personal` | 收藏、本人预约、本人带看进度、本人租约、个人消息与账号能力 |
| 房东 | 已登录且拥有有效房东联系人关系 | `landlord` | 当前房东关系下的房源、租约、公开店铺和关系消息 |
| 中介 | 已登录且为有效组织成员 | `organization` | 当前组织内、当前 RBAC 权限允许的经营与管理数据 |

同一平台账号可以同时拥有多个房东关系和多个组织成员关系。默认登录后进入租客模式；用户主动选择房东关系或组织工作空间。保存的上次选择必须在每次启动时重新校验，关系失效时回退租客模式。

### 3.2 请求不变量

- 公开请求可以携带会话 Token，但禁止携带 `X-Org-Slug`；
- 租客个人请求必须登录，禁止携带 `X-Org-Slug`；
- 房东请求由后端根据当前用户与房东联系人关系推导组织，禁止携带组织头；
- 中介请求必须携带当前 `X-Org-Slug`，并由后端继续执行组织成员与 RBAC 校验；
- 公开房源和公开店铺深链临时使用游客或租客视角，不覆盖用户保存的房东关系或组织工作空间。

## 4. 移动端信息架构

微信构建清单保持五个稳定 Tab 槽位，切换业务模式后更新标题、图标和页面内容。

| 槽位 | 租客模式 | 房东模式 | 中介模式 |
| --- | --- | --- | --- |
| 1 | 首页 | 概览 | 工作台 |
| 2 | 找房 | 房源 | 业务 |
| 3 | 我的找房 | 租约 | 待办 |
| 4 | 消息 | 消息 | 消息 |
| 5 | 我的 | 我的 | 我的 |

游客只开放首页、找房和我的。登录后开放当前模式对应的完整五 Tab。

### 4.1 租客入口

- 首页：公开房源推荐、最近浏览或个人业务摘要、快捷找房；
- 找房：公开房源搜索、筛选、列表、详情、收藏、分享和公开配房分享；
- 我的找房：收藏、预约、取消预约、带看进度和本人租约；
- 消息：本人业务通知和通知偏好；
- 我的：个人资料、实名、账号安全、钱包、推广记录和身份切换。

不在没有后端事实来源时新增公开找房地图、找房需求单或租客租约确认入口。

### 4.2 房东入口

- 概览：当前合作关系、房源数量、租约摘要和公开店铺信息；
- 房源：当前关系下名下房源、状态筛选、详情与分享；
- 租约：当前关系下租约列表与详情；
- 消息：与当前房东关系相关的本人通知；
- 我的：公开店铺、房东关系切换、个人资料、安全与其他身份切换。

房东能力与当前 Web 房东中心一致，默认只读。邀请认领沿用现有邀请查询和接受流程。

### 4.3 中介入口

- 工作台：个人与组织经营摘要、风险、快捷动作和待处理入口；
- 业务：房产资产、地图、房表同步、客户、带看、租约、登记签约、收益分配和经营分析；
- 待办：本人任务、团队任务、公告和处理状态；
- 消息：组织、团队和本人业务通知；
- 我的：组织、成员、团队、角色与绑定、房源职责、组织/团队设置、订阅、通知分发、个人资料与身份切换。

模块入口由 `/api/access/navigation/` 返回的能力裁剪。无权模块不展示；直接访问时进入统一无权限恢复页。

## 5. 业务流程

### 5.1 租客预约

1. 租客从公开房源详情发起预约；
2. 未登录时保存房源、目标路由和预约动作，完成登录后恢复；
3. 未验证手机号时先完成手机号验证；
4. 后端根据房源确定所属组织，租客不能选择组织、团队或负责人；
5. 后端在房源所属组织内绑定或创建租客联系人；
6. 创建现有 `ViewingRecord`，初始状态固定为 `scheduled`；
7. 中介端通过现有带看列表、工作台入口和通知看到新预约。

预约不自动创建新的业务状态或另一套预约表。若现有团队任务模型没有稳定的业务关联，本次不强行创建重复任务记录。

### 5.2 联系人绑定

个人预约和本人租约读取使用以下规则：

- 只使用当前用户已验证手机号；
- 在房源所属组织内查找相同标准化手机号的有效联系人；
- 联系人已绑定当前用户时直接复用，并确保具有租客角色；
- 联系人未绑定用户时绑定当前用户，并确保具有租客角色；
- 不存在联系人时创建组织内租客联系人并绑定当前用户；
- 同一手机号已绑定其他平台用户、存在多条冲突记录或联系人已停用时，不自动合并，返回明确冲突；
- 冲突信息不得暴露其他用户身份，组织员工继续使用现有联系人管理能力处理。

### 5.3 带看处理

中介端使用现有组织带看接口和默认状态：

```text
scheduled -> viewed | canceled | no_show | converted
```

租客只能查看本人关联带看进度；取消动作通过专用个人命令将本人仍处于 `scheduled` 的记录转为 `canceled`。租客不能修改房源、负责人、实际带看时间、成交状态和内部备注。

### 5.4 登记签约

中介继续采用管理端现有流程：

1. 将带看记录更新为 `converted`；
2. 缺少租客主体时先补齐现有组织联系人；
3. 从成交带看或房源入口使用现有登记签约能力；
4. 复用 `deal-signing`、`leases` 和 `allocation` 领域服务；
5. 租约继续使用 `pending`、`active`、`expired`、`terminated`；
6. 房源、收益分配、经营分析和后续任务继续使用现有后端行为。

租客和房东只读取本人关系允许的租约投影和通知，不增加确认、异议、审批或编辑命令。

## 6. 能力范围

### 6.1 租客能力

- 公开房源列表、筛选和详情；
- 公开房东店铺及公开房源；
- 公开配房分享及分享内房源；
- 收藏、取消收藏和失效收藏状态；
- 提交预约、取消本人待进行预约；
- 查看本人预约、带看结果和本人租约；
- 消息、通知偏好、个人资料、实名与账号安全；
- 当前管理端已有且适合个人用户的钱包与推广记录能力。

### 6.2 房东能力

- 房东邀请查询与接受；
- 有效房东关系列表和关系切换；
- 当前关系下房源列表、详情和公开分享；
- 当前关系下租约列表和详情；
- 公开房东店铺查看与分享；
- 关系相关通知；
- 共用个人资料、实名和账号安全能力。

### 6.3 中介能力

除超级管理员路由外，对齐管理端当前可用的组织能力：

- 工作台、任务、任务分配、公告；
- 房源、小区、楼栋、地图、待定位楼栋、房表同步、发布规则；
- 联系人、房东邀请、员工房源职责；
- 带看、成交转换、租约、登记签约；
- 收益分配申请、审核、应计流水和汇总；
- 经营分析；
- 组织成员、邀请、团队、组织/团队角色与绑定；
- 组织设置、团队设置；
- 组织订阅、订单、发票资料和支付；
- 通知、通知偏好和有权限的通知分发；
- 个人资料、实名、账号安全、钱包与推广记录。

### 6.4 明确排除

- `/super-admin` 下的平台用户管理；
- 平台级实名审核；
- 平台钱包账户、提现审核和人工调账；
- 平台订阅订单、发票请求和退款后台；
- 平台推广配置与记录审核；
- 系统运维工具；
- 电子合同和具有法律效力的电子签署；
- 没有管理端或现有接口依据的租客、房东新业务流程。

## 7. 工程结构

### 7.1 复用现有底座

继续复用当前未提交重构形成的目录和职责：

```text
src/app        应用 Provider、启动边界和 bootstrap
src/core       配置、错误、生命周期和日志
src/platform   H5 / 微信平台适配
src/infra      认证、请求、持久化、上传和分析基础设施
src/domain     无 Vue、Pinia、uni-app 依赖的纯规则
src/modules    模块、路由、Tab 和分包注册
src/shared     公共组件、组合函数、主题和工具
src/features   业务视图与业务服务
src/store      runtime、session、workspace
```

本次在该底座上增量实现业务，不恢复旧 alova、旧 token/user Store、模板 API 或直接页面请求。

### 7.2 分包

| 分包 | 职责 |
| --- | --- |
| `pages-housing` | 公开房源详情、公开配房分享、公开主体深页 |
| `pages-personal-rental` | 租客预约、带看进度和本人租约 |
| `pages-landlord` | 房东邀请、关系、房源、租约和公开店铺 |
| `pages-org-rental` | 房产、客户、带看、租约、签约、收益和分析 |
| `pages-org-work` | 工作台、任务、待办和公告 |
| `pages-org-admin` | 成员、团队、角色、绑定、职责、设置、订阅和通知分发 |

模块首次具备真实页面和服务时才从 `planned` 切换为 `active`。不创建生产可见的空白页面或“敬请期待”模块。

### 7.3 唯一调用链

```text
页面路由入口
  -> feature view / composable
  -> feature service
  -> services/manual adapter
  -> services/openapi 生成客户端
  -> Django API / domain service
```

约束：

- 页面和 feature 不直接导入 `services/openapi/**`；
- 页面和 feature 不直接调用 `uni.request`、`uni.uploadFile`、`uni.login` 或支付 API；
- 生成客户端不保存当前模式或工作空间状态；
- 请求作用域由 manual adapter 或 feature service 明确指定；
- OpenAPI 生成文件只通过代码生成更新，不手改。

## 8. 最小后端补充

后端新增个人租赁 Router，默认采用 `/api/house/tenant/` 前缀，继续归属 `apps.house` 领域。接口只暴露当前管理模型的个人安全投影：

```text
GET  /api/house/tenant/viewing-records/
POST /api/house/tenant/viewing-records/
GET  /api/house/tenant/viewing-records/{id}/
POST /api/house/tenant/viewing-records/{id}/cancel/
GET  /api/house/tenant/leases/
GET  /api/house/tenant/leases/{id}/
```

约束：

- 所有列表使用 `page`、`page_size` 和项目标准分页结构；
- 列表可以跨组织聚合当前用户本人记录，并返回必要的组织展示摘要；
- 创建预约只接受公开房源 ID、预约时间和租客可填写的公开备注；
- 后端忽略或拒绝组织、联系人、负责人和状态等客户端越权字段；
- 取消只允许当前用户本人仍处于 `scheduled` 的记录；
- 租约接口只读，只返回 `tenant.user == request.user` 的记录；
- 房东关系接口继续使用现有 `/api/house/landlord/relationships/` 和 `/contacts/{id}/...`；
- 中介接口继续使用现有组织 API，不增加移动端专用副本。

实现个人接口后重新生成管理端和小程序 OpenAPI 客户端；所有手写适配器放在各自的 `services/manual`。

## 9. 移动端交互规则

### 9.1 列表

- 使用搜索、状态快捷筛选和确认式筛选面板；
- 支持下拉刷新与触底分页；
- 修改筛选后从第一页重新加载；
- 新请求返回前保留当前列表；
- 旧请求晚到时不得覆盖新查询；
- 空结果提供清除筛选或主业务动作。

### 9.2 详情

- 顶部展示状态、关键摘要和当前可执行主动作；
- 关联房源、联系人、带看、租约、收益申请使用明确深链；
- 长信息按业务分组，不照搬桌面表格；
- 租客和房东详情隐藏组织内部字段和无权操作。

### 9.3 表单与操作

- 简单动作使用 Popup、ActionSheet 或确认 Dialog；
- 复杂创建和编辑使用整页表单或分步流程；
- 字段、枚举、必填和服务端校验与管理端相同；
- 服务端字段错误回填到对应表单项；
- 提交期间禁用重复提交；
- 成功后刷新受影响的列表、详情、工作台摘要和通知数；
- 危险操作必须二次确认，但不增加管理端不存在的审批流程。

具体组件实现优先使用 Wot UI v2 的现有组件、hooks、ConfigProvider 和主题变量。

## 10. 错误与恢复

| 场景 | 行为 |
| --- | --- |
| `401/410` | 保存当前路由和可恢复动作，重新登录后恢复；失效会话才清理 Token |
| `403` | 展示当前身份/组织无权访问，提供返回、切换组织和回租客模式 |
| `404` | 显示内容不存在，返回对应列表或公开找房 |
| `409` | 展示关系、状态或联系人冲突，不做自动合并或覆盖 |
| `422` | 展示后端业务消息并回填字段错误 |
| 网络/超时 | 保留已加载数据和筛选，允许重试，不自动退出登录 |
| 模式关系失效 | 回退租客模式并刷新 Tab，不继续停留在失效页面 |

请求客户端不直接显示 Toast 或导航；页面/feature 根据稳定 `AppError` 决定反馈方式。

## 11. 实施批次

所有批次均属于本次目标，批次只决定依赖顺序和验收边界。

### 批次 1：底座收口

- 完成当前小程序工程底座重构；
- 固化 runtime、session、workspace、模块注册、路由和请求边界；
- 完成登录、手机号验证、身份切换、公共状态页和 Wot UI 根级能力；
- 保证现有公开找房、收藏和配房分享不回退。

### 批次 2：租客闭环

- 增加个人预约与租约只读接口；
- 完成联系人安全绑定；
- 实现预约、取消、带看进度和本人租约；
- 补齐相关通知与登录后动作恢复。

### 批次 3：房东中心

- 完成邀请认领、关系切换、名下房源、租约、公开店铺、分享和消息；
- 与管理端房东中心逐项对照。

### 12.3 真实流程

## 13. 完成标准

本需求完成需要同时满足：

- 租客、房东、中介三个模式均有真实业务入口，不存在生产可见空模块；
- 管理端非超级管理员能力在能力矩阵中有明确移动端对应或明确不适用原因；
- 移动端不引入独立租赁状态机；
- 中介写操作继续受现有组织成员校验与适用的 RBAC 控制；
- 租客和房东个人数据严格按本人关系隔离；
- H5 与微信小程序生产构建通过；
- 三角色关键链路完成真实验证并记录未覆盖的真机项；
- 不覆盖或丢失当前工作区已有未提交改动；
- 未经明确要求不执行 Git 暂存、提交、分支或推送。
