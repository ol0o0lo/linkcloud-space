# `startup` 分支说明

## 目标

本仓库同时承担两个角色：

- `main` 分支用于当前项目的持续开发与交付
- `startup` 分支用于作为新项目的纯净启动模板

`startup` 的核心目标不是保存“当前项目的另一个版本”，而是保存“未来新项目可以直接复用的基础能力”。

## 分支职责

### `main`

`main` 负责承载当前项目的真实业务演进，可以包含：

- 当前项目专属业务模型、接口与页面
- 当前项目品牌、文案、Logo、导航结构
- 当前项目环境配置、部署约束与第三方集成
- 只服务当前客户或当前场景的功能

### `startup`

`startup` 只保留可复用、可迁移、适合作为新项目起点的内容，例如：

- Django / Vue / Docker / Just / 测试基建
- 认证、用户、组织、团队、多租户脚手架
- 通知系统、对象存储、任务队列等通用基础能力
- 通用布局、基础页面壳子、权限骨架
- 新项目普遍会用到的开发规范和工程配置

## 严格边界

以下内容原则上**不要进入** `startup`：

- 当前项目专属业务流程
- 当前项目数据库历史包袱与仅本项目需要的迁移设计
- 当前项目品牌素材、运营文案、页面文案
- 客户特有集成、外部系统对接、临时兼容逻辑
- 带有真实环境信息的配置与脚本

如果某项改动不确定是否通用，默认先留在 `main`，不要急着回灌到 `startup`。

## 推荐工作方式

### 当前项目开发

当前项目的日常开发以 `main` 为主。凡是明显只属于当前项目的需求，直接在 `main` 体系内推进，不需要同步到 `startup`。

### 通用能力沉淀

当 `main` 中出现被确认可复用的能力时，再选择性同步到 `startup`。这类改动通常包括：

- 通用模型抽象优化
- 基础设施升级
- 认证、权限、组织能力增强
- 测试基建和开发体验改进

### 回灌原则

不建议定期把 `main` 整体合并回 `startup`。  
推荐做法是：只把已经确认“对未来项目也有价值”的提交，按提交粒度挑选到 `startup`。

建议遵循以下规则：

- 优先保持提交粒度清晰，一个提交只做一件事
- 通用能力与业务定制尽量拆分到不同提交
- 同步到 `startup` 前先复核是否引入了项目专属内容

## 新项目启动方式

当需要新建项目时，推荐两种做法：

### 方式一：从 `startup` 拉新分支

适合还在同一仓库内快速孵化新方向时使用。

基本流程：

1. 基于 `startup` 创建新分支
2. 替换项目名称、域名、品牌文案与导航
3. 清理不需要的示例页面或演示能力
4. 开始新项目业务开发

### 方式二：从 `startup` 派生新仓库

适合新项目已经确定要独立维护时使用。

基本流程：

1. 从 `startup` 导出代码作为新仓库初始内容
2. 重置仓库名称、远程地址、CI/CD 配置
3. 按新项目需要保留或删除模块
4. 以新仓库自己的 `main` 继续开发

长期来看，如果模板演进越来越频繁，建议最终拆分出独立模板仓库。

## 分支维护建议

- `main` 永远优先服务当前项目
- `startup` 永远优先保持纯净、通用、可启动
- 不追求两个分支完全同步
- 宁可少同步，也不要把业务污染带进模板

## 建议的判断标准

准备把某个改动同步到 `startup` 之前，可以先问三个问题：

1. 如果明天启动一个全新项目，这个改动还会需要吗？
2. 去掉当前项目名称、客户背景和业务上下文后，这个改动还能成立吗？
3. 这个改动会不会让新项目一开始就背上不必要的业务包袱？

只要其中有一个答案偏负面，就先不要进 `startup`。

## 当前约定

- `main`：当前项目主开发分支
- `startup`：纯净项目启动模板分支

后续如果模板能力不断增长，可以再把 `startup` 升级为独立模板仓库；在此之前，先按本文档约束执行。
