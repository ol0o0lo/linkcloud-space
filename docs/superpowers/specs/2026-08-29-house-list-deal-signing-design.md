# 房源列表成交签约抽屉设计

日期：2026-08-29
状态：已实施

本文是房源列表成交签约功能的当前设计依据，替代本文件早先的“跳转租约页面并打开抽屉”交互。成交签约改为在房源列表原地完成，并保留专用后台事务接口。

## 1. 目标

在管理端房源列表的“更多操作”中提供“成交签约”，让用户不离开列表即可完成历史成交补录或现场签约登记。

一次成功提交必须原子完成：

1. 关联已有租客或创建新租客。
2. 创建状态为“生效中”的租约。
3. 将房态更新为“已租”。
4. 创建收益归属申请并进入现有审核流程。

用户应始终明确知道本次操作会让租约立即生效并改变房态，但界面不使用夸张警告或额外确认步骤阻碍正常录入。

## 2. 设计结论

- 使用响应式宽抽屉，不使用居中弹窗，也不跳转租约页面。
- 电脑端采用双栏工作台：左侧核对房源和结果，右侧完成录入。
- 平板端将左侧摘要收为表单顶部的房源卡片，维持字段和按钮的触控尺寸。
- 默认直接填写租客姓名和手机号，也可切换为选择已有租客。
- 姓名和手机号同时一致才自动关联为同一租客。
- 同手机号、不同姓名允许保存为不同租客。
- 合同和备注为选填，默认折叠，可以成交后补充。
- 提交按钮直接使用“确认成交并生效”，不再增加二次确认弹窗。

## 3. 范围与非目标

### 3.1 本次范围

- 优化房源列表成交签约抽屉的视觉层级和响应式布局。
- 将租客填写、自动关联和已有租客选择整合进主流程。
- 调整联系人唯一性规则，使其与“姓名 + 手机号”身份判断一致。
- 保留租期、租金、押金、付款日、收益归属、合同和备注能力。
- 保留成交签约专用事务语义和现有收益审核语义。

### 3.2 非目标

- 不让普通租约保存或任意租约状态修改自动改变房态。
- 不改造普通“新建租约”和“编辑租约”流程。
- 不新增账单、收付款、工资发放或结算能力。
- 不自动创建带看记录。
- 不要求成交时必须上传合同。
- 不在抽屉中再弹出“新建租客”弹窗。

## 4. 入口与容器

房源列表行级“更多操作”保留“成交签约”入口。点击后直接打开可复用的 `DealSigningDrawer`，传入当前房源，不修改路由，不丢失列表筛选、分页和滚动位置。

### 4.1 电脑端

- 抽屉目标宽度为 880–960px，最终使用项目现有宽度常量或响应式计算，不写死超出视口的宽度。
- 左栏约占 31%–34%，只展示房源名称、楼栋房号、户型、报价、当前房态和成交后的状态结果。
- 右栏承载全部可编辑字段。
- 底部操作栏固定可见，左侧放轻量结果说明，右侧放取消与主按钮。

### 4.2 平板端

- 不强行压缩双栏。
- 房源摘要移动到表单顶部，变成一张紧凑卡片。
- 表单保持单列或两列自适应；触控控件不因视口缩小而降低可用尺寸。
- 底部按钮仍固定可见。

### 4.3 窄屏兜底

虽然管理端主要面向电脑和平板，窄屏下仍应切换为单列表单和纵向底部按钮，避免内容溢出。

## 5. 组件边界

### 5.1 `DealSigningDrawer`

负责：

- 抽屉开关、离开保护和提交状态。
- 加载并展示房源上下文。
- 组合租客、租赁条件、收益归属、合同与备注区域。
- 调用成交签约接口。
- 成功后关闭抽屉并刷新房源、租约和收益相关缓存。

组件通过 `house` 或 `houseId` 接收目标房源，通过 `onSuccess` 通知调用方，不耦合具体列表实现，因此可以在房源详情或其他入口复用。

### 5.2 租客录入组件

从抽屉中拆出职责单一的租客字段组件，提供两种模式：

1. `identity`：填写姓名和手机号。
2. `existing`：按姓名或手机号搜索并选择已有租客。

组件只输出明确的租客输入，不负责创建租约：

```text
{ mode: "identity", name, phone }
或
{ mode: "existing", tenant_id }
```

自动匹配结果只用字段下方一行浅色辅助文字表达，例如“将关联已有租客”，不展示大面积成功卡片，不弹窗，不抢占表单注意力。

### 5.3 复用现有组件

- 收益归属继续复用 `EarningAttributionFields`。
- 合同文件继续复用 `MediaRefsUpload`。
- 房源、状态和图标继续使用项目统一的预览、状态和图标组件。
- 样式优先使用 Ant Design、Tailwind 布局和 `antd-style` 主题 token，不建立独立视觉体系。

## 6. 租客身份与唯一性

### 6.1 匹配规则

后台是最终权威。用户提交姓名和手机号时，服务端先执行最小规范化：

- 姓名执行 `strip()` 去除首尾空白，保留内部空格、大小写和原始文字。
- 手机号执行 `strip()` 去除首尾空白并保留原始展示格式，不进行可能改变既有联系人显示和邀请逻辑的全局格式迁移。

只有当前组织内规范化后的姓名和手机号均一致，才视为同一联系人并自动关联。

### 6.2 新建规则

- 没有精确匹配项时，在成交事务内创建联系人并添加租客角色。
- 同手机号但姓名不同，不自动关联，允许创建为两个联系人。
- 联系人的数据库唯一性由“组织 + 姓名 + 手机号”共同约束，替代当前“组织 + 手机号”约束。
- 通过 `tenant_id` 主动选择已有租客时，继续校验联系人属于当前组织、处于启用状态且具备租客角色。
- 通过姓名和手机号精确匹配到已停用联系人时不静默启用；提交返回明确但克制的字段错误，引导先启用联系人或选择其他租客。
- 精确匹配到启用联系人但缺少租客角色时，在成交事务中补充租客角色后复用该联系人，避免重复联系人。

### 6.3 并发规则

前端的即时匹配只用于反馈，不作为提交依据。服务端必须在事务中重新匹配，并依赖数据库唯一约束处理并发创建：

- 两个请求同时提交同一姓名和手机号时，创建方捕获唯一约束竞争并重新查询精确匹配联系人，最终只保留一个联系人，两个请求都复用该联系人；后续房源或租约校验仍按各自业务结果返回。
- 不允许因为联系人竞争而留下租约、房态或收益申请的部分修改。

## 7. 表单交互

### 7.1 租客资料

- 默认选中“填写资料”。
- 姓名和手机号均填写完整后，可以执行低频、防抖的精确匹配查询。
- 精确命中时仅显示“将关联已有租客”。
- 未命中时不要求额外确认，提交时创建新租客。
- 用户可以随时切换“选择已有”，通过姓名或手机号搜索。
- 切换模式时清除另一模式不会提交的值，避免同时携带 `tenant_id` 与身份字段。

### 7.2 租期与金额

- 起租日期默认当天，允许修改。
- 租期提供“半年”“1 年”“2 年”“自定义”快捷项。
- 使用快捷租期时自动计算到期日；到期日仍允许切换为自定义值。
- 月租默认带入房源报价，允许修改。
- 押金提供“无押金”“押一月”“自定义”；“押一月”随当前月租计算，用户仍可覆盖。
- 每月付款日默认取起租日的日号，并限制在 1–31。
- 接口继续提交明确的起止日期和金额，不把“半年”“押一月”等界面快捷值保存为新的领域字段。

### 7.3 收益归属

- 保留现有必填规则和权限能力判断。
- 归属团队和参与员工压缩为紧凑区域，但不得隐藏审核语义。
- 成交成功只表示收益申请已提交，不能表达为员工收益已经生效。

### 7.4 合同与备注

- 默认折叠，标题明确标注“选填，可成交后补充”。
- 展开后保留合同上传和内部备注。
- 没有合同文件时允许提交。
- 合同上传失败只影响文件字段，不清空其他表单内容。

## 8. 后台输入契约

成交签约接口继续使用专用端点，不复用普通租约创建端点。租客输入改为二选一结构：

```text
lease:
  house_id
  tenant_id              # 选择已有租客时提供
  tenant_identity:       # 直接填写时提供
    name
    phone
  start_date
  end_date
  monthly_rent
  deposit
  payment_day
  contract_files
  notes
team_id
beneficiary_user_ids
```

约束：

- `tenant_id` 与 `tenant_identity` 必须且只能提供一个。
- 客户端不能传入租约状态或目标房态。
- 普通租约接口仍使用现有 `tenant_id` 契约，不受此次调整影响。
- 接口不自动填写 `sign_at`；历史成交的真实签约时间不能由服务器当前时间代替。后续如需采集，应增加明确字段。

## 9. 原子事务与数据流

```text
房源列表“更多操作”
  → 打开 DealSigningDrawer
  → 填写或选择租客
  → 填写租期、金额、收益归属，可选合同
  → POST 成交签约专用接口
      → 锁定并校验房源
      → 解析 tenant_id 或匹配/创建 tenant_identity
      → 创建 ACTIVE 租约
      → 将房态更新为 RENTED
      → 创建收益归属申请与关联记录
  → 全部成功后提交事务
  → 关闭抽屉并刷新房源、租约、收益缓存
```

联系人解析、租约创建、房态更新、收益申请和业务关联必须在同一数据库事务内。任一步失败时全部回滚。

该联动只属于成交签约用例：不新增 `post_save` 信号，不在 `Lease.save()` 中修改房态，不改变普通租约保存和状态流转语义。

## 10. 状态与异常

- 已停用房源不能成交签约；前端禁用入口，后台仍独立校验。
- 已存在生效中租约时拒绝重复成交签约。
- 房源未登记房东时沿用现有校验并拒绝提交。
- 房源已经是“已租”但不存在生效中租约时，允许补录成交签约，房态保持“已租”。
- 服务端字段校验错误显示在对应字段附近。
- 房源并发变更、已有生效租约或事务性错误显示在抽屉顶部，不清空表单。
- 提交期间禁用重复提交和关闭行为。
- 用户关闭有修改的表单时，保留现有放弃填写确认；正常提交不增加二次确认。

## 11. 成功反馈

成功后使用一次明确的轻量消息：

> 成交签约完成，租约已生效，房态已更新为已租；收益等待审核。

随后关闭抽屉并刷新：

- 房源列表与房源详情缓存。
- 租约列表与租约详情缓存。
- 收益归属申请相关缓存。
- 当前打开入口依赖的房源统计缓存。

## 12. 数据迁移

- 将联系人唯一约束从 `(organization, phone)` 改为 `(organization, name, phone)`。
- 本次迁移只替换数据库唯一约束，不改写现有联系人姓名或手机号。
- 联系人列表、创建、更新、邀请和用户绑定逻辑需要验证是否仍错误依赖“组织内手机号全局唯一”。
- 前端生成的 OpenAPI 客户端不手改；后端 schema 更新后按项目命令重新生成，再由手写适配层承接成交签约调用。

## 13. 测试范围

### 13.1 后端

- 姓名和手机号精确一致时关联已有租客，不创建重复联系人。
- 无精确匹配时创建新租客并完成成交。
- 同手机号、不同姓名可以创建为不同租客。
- 同姓名、不同手机号可以创建为不同租客。
- 已有联系人缺少租客角色时补充角色并复用。
- 已停用联系人不能被静默复用。
- `tenant_id` 和 `tenant_identity` 的二选一校验。
- 并发创建相同租客时不产生重复联系人或部分业务数据。
- 成交成功后租约为生效中、房态为已租、收益申请为待审核。
- 房态更新或收益申请失败时，联系人、租约和房态全部回滚。
- 普通租约创建仍保持原语义，不联动房态。
- 联系人创建、更新、邀请和用户绑定相关回归测试。

### 13.2 前端

- 房源列表入口原地打开抽屉，不发生路由跳转。
- 电脑端双栏、平板端顶部摘要和窄屏单列布局。
- 两种租客模式互斥输出正确请求体。
- 精确匹配只显示低干扰辅助文字。
- 租期快捷项正确计算到期日。
- 月租默认值和押金快捷项正确联动。
- 合同折叠且不上传文件也可提交。
- 提交中避免重复请求，失败后保留表单。
- 成功后显示准确消息并刷新所需缓存。

## 14. 验收标准

- 用户能从房源列表在一个抽屉中完成成交签约，不跳转页面，不打开第二层租客弹窗。
- 电脑和平板均能清晰核对房源并完成表单。
- 姓名和手机号均一致时自动关联已有租客；同手机号不同姓名可以独立保存。
- 成交提交不会被不必要的提示或二次确认打断。
- 成功响应前，联系人、租约、房态和收益申请不存在部分写入。
- 成功后界面立即显示房态为已租，并能在租约列表看到生效租约。
- 普通租约流程的状态和房态语义保持不变。
