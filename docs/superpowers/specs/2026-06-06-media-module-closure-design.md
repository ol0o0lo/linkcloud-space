# Media 模块闭环设计

## 背景

当前 `apps/media` 已具备这些基础能力：

1. 直传凭证接口：`GET /api/media/oss-token/`
2. 直传登记接口：`POST /api/media/confirm/`
3. 服务端上传接口：`POST /api/media/upload/`
4. 统一媒体记录模型：`MediaFile`
5. 基于 `media_id` 列表的顺序回显能力：`get_media_list_info()`
6. 基于引用收集器的延迟清理任务：`cleanup_unreferenced_media()`

本设计不再把 `media` 视为某个具体业务的上传附件实现，而是将其定义为：**供其他业务模块复用的通用媒体存储平台**。

业务侧通过 `JSON list[int]` 保存 `media_id` 列表，`media` 模块负责上传、登记、查询回显、引用治理和延迟回收。

---

## 已确认的设计决策

### 1. 同一个媒体可被多个业务复用

同一个 `MediaFile` 允许被多个模型、多个记录同时引用。

这意味着：

- 媒体本体只描述文件本身
- 引用关系由业务数据决定
- 不能把“排序”“归属某一记录”等语义放在 `MediaFile` 本体上

### 2. 删除引用不等于立即删除媒体

当业务模型把某个 `media_id` 从自己的 `JSON list[id]` 中移除时，只表示**解除该业务引用**。

平台不立即物理删除文件，也不立即删除 `MediaFile` 记录；真正删除交给延迟清理任务处理。

### 3. 权限由业务模块负责

`media` 模块不负责“当前请求是否有权查看或使用某个 `media_id`”的业务权限判断。

平台只负责：

- 媒体是否存在
- 是否能按 `list[id]` 返回完整信息
- 是否已被任何业务引用

具体“谁能用、谁能看、谁能改”由调用该能力的业务模块自行校验。

### 4. 顺序以业务 `media_ids` 列表顺序为准

媒体顺序属于业务引用关系，不属于媒体本体。

因此：

- 业务保存 `[5, 9, 3]`
- 平台回显时必须返回 `[5, 9, 3]` 对应的完整信息
- 不需要在 `MediaFile` 上维护全局 `order`

### 5. `confirm` 链路保持轻校验

`POST /api/media/confirm/` 继续采用轻量登记模式：前端传入 `oss_path`、`original_filename`、`resource_type`、`file_size` 后，后端直接登记 `MediaFile`。

本轮闭环不要求对对象存储中的文件存在性做额外确认，也不要求把“申请 token 的路径”和“确认登记的路径”做强绑定校验。

---

## 闭环目标

按本次范围，`media` 模块要达到的闭环标准是：

1. **上传闭环**：业务能获得可保存的 `media_id`
2. **查询闭环**：业务能把 `JSON list[id]` 还原为有序完整信息
3. **引用闭环**：平台能知道哪些 `media_id` 仍被业务引用
4. **回收闭环**：未被引用的媒体在保留期后能自动清理
5. **协议闭环**：新业务接入时遵守统一协议，而不是各写一套

---

## 当前能力判断

### 已闭环部分

当前实现已基本闭环的能力有：

- 上传凭证申请
- 直传完成后的媒体登记
- 服务端文件上传并登记
- `media_id` 到媒体完整信息的顺序回显
- 基于引用收集器的延迟清理框架

这说明 `media` 已经具备“可被接入”的基础能力，不是从零开始。

### 未闭环部分

当前尚未闭环的关键点有：

1. **引用治理尚未真正接通**
   - `MEDIA_REFERENCE_PROVIDERS` 仍为空
   - 清理任务缺少真实业务引用数据源
   - 如果没有业务 provider 接入，就无法安全判断某个媒体是否已无引用

2. **全局 `order` 语义与可复用模型冲突**
   - 既然同一媒体可被多个业务复用，顺序应由业务自己的 `media_ids` 列表表达
   - `MediaFile.order` 属于错误抽象，应从平台主语义中移除

3. **统一协议仍未成文**
   - 目前已有 `get_media_list_info()` 这类函数
   - 但还没有形成明确的接入协议，约束业务如何存、如何校验、如何回显、如何接入清理系统

4. **服务端上传接口还不够通用**
   - 当前 `upload_and_register()` 固定将文件上传到 `user` 作用域目录
   - 如果业务需要上传组织级共享媒体，平台能力还不完整

---

## 目标方案（方案 B）

本轮采用“中平台”方案：

- `media` 负责统一媒体记录、查询回显、引用收集协议、延迟清理协议
- 业务侧统一用 `JSON list[int]` 保存媒体引用
- 权限仍由业务模块负责
- 不引入独立引用表，不引入重型关联系统

这个方案能保证平台边界清晰，也能避免过度设计。

---

## 平台协议

### 1. 业务字段协议

凡是接入 `media` 平台的业务模型，统一使用 `JSON list[int]` 保存媒体引用。

协议要求：

- 字段值是整数 ID 列表
- 列表顺序就是前端展示顺序
- 不允许重复 ID
- 空列表表示无媒体
- 删除某个 ID 只表示解除该业务引用

本轮不强制字段名必须统一为 `media_ids`，但推荐优先使用 `media_ids`。若业务使用其他字段名，也必须遵守同一语义。

### 2. 查询回显协议

平台必须提供统一服务，将 `list[id]` 解析为完整媒体信息列表。

行为要求：

- 返回顺序与传入 `list[id]` 一致
- 如果列表为空，返回空列表
- 如果包含重复 ID，抛出校验错误
- 如果包含不存在的 ID，抛出校验错误
- 不做业务权限过滤

返回结构统一为媒体信息对象列表，至少包含：

- `id`
- `resource_type`
- `original_filename`
- `original.url`
- `thumbnail`
- `file_size`
- `created_at`

### 3. 引用收集协议

凡是业务模型保存了媒体 ID 列表，都必须提供一个引用收集器函数，并注册到 `MEDIA_REFERENCE_PROVIDERS`。

收集器职责：

- 扫描本业务模型内所有仍有效的媒体引用
- 返回当前仍被引用的 `media_id` 集合或可迭代对象
- 不返回空值或非法值

平台职责：

- 汇总所有 provider 的返回结果
- 计算仍被业务引用的媒体全集
- 只清理不在该全集中的旧媒体

### 4. 延迟清理协议

延迟清理继续保留当前策略：

- 仅清理超过保留窗口的媒体
- 仅清理未被任何 provider 报告为“仍被引用”的媒体
- 清理时同时删除物理文件和 `MediaFile` 记录

这与“业务解除引用后不立即删除”的约束保持一致。

## 数据模型调整

### 保留字段

`MediaFile` 保留以下平台必要字段：

- `uploader`
- `resource_type`
- `original_filename`
- `file`
- `file_size`
- `created_at`
- `updated_at`

### 移除字段

`MediaFile.order` 不再属于平台模型。

原因：

- 它描述的是某一次引用中的顺序，而不是媒体本体属性
- 在同一媒体被多个业务复用时，全局 `order` 无法表达真实顺序
- 列表顺序已经由业务的 `JSON list[id]` 表达，无需冗余存储

---

## 服务层设计

### 1. 保留现有上传登记能力

以下服务继续保留：

- `get_oss_token()`
- `register_media_file()`
- `upload_and_register()`

### 2. 强化 `list[id]` 解析能力

`get_media_list_info()` 保留为平台标准能力，作为业务回显入口。

职责：

- 接收 `list[int]`
- 执行重复校验
- 执行存在性校验
- 按输入顺序返回完整信息

业务模块不应在各自 app 中重复实现同类逻辑。

### 3. 服务端上传能力泛化

`upload_and_register()` 需要从“固定上传到 user 目录”扩展为“支持按作用域生成路径”。

最低要求：

- 支持 `user` 作用域
- 支持 `org` 作用域

是否暴露为公共 API 参数，取决于具体业务是否需要；但服务层本身应支持该能力，避免平台基础设施卡住业务。

---

## `resource_type` 策略

本轮不重做 `resource_type` 体系。

设计决策如下：

- 继续保留枚举型 `resource_type`
- 允许后续随业务扩展新增枚举值
- `resource_type` 的主要用途是业务分类和前端展示语义提示
- 不把 `resource_type` 设计成权限边界或引用边界

这意味着当前的 `avatar`、`org_logo` 虽然偏业务用途，但不会阻碍平台先闭环。

---

## 错误处理

平台层约定：

- 重复 `media_id`：返回校验错误
- 不存在的 `media_id`：返回校验错误
- 非法 `resource_type`：API 层返回 `422`
- 非法扩展名：API 层返回对应错误

不纳入本轮的平台错误处理：

- 当前请求是否有权限访问某个媒体
- 某个媒体是否允许被某个具体业务场景绑定

这些仍由业务模块决定。

---

## 测试要求

本轮闭环至少需要覆盖这些测试：

1. `list[id]` 顺序回显测试
   - 保证返回顺序与输入顺序一致

2. `list[id]` 重复校验测试
   - 重复 ID 必须失败

3. `list[id]` 缺失校验测试
   - 不存在 ID 必须失败

4. 引用 provider 接入测试
   - provider 返回的引用能被清理任务识别

5. 清理任务测试
   - 已引用媒体不删
   - 未引用且过期媒体可删

6. 服务端上传作用域测试
   - `upload_and_register()` 能覆盖 `user/org` 两种路径生成

---

## 接入要求

任何新业务要使用 `media` 平台，必须满足以下要求：

1. 用 `JSON list[int]` 保存媒体 ID
2. 按列表顺序展示，不额外依赖平台全局排序字段
3. 调用平台统一的媒体回显服务
4. 注册自己的媒体引用 provider
5. 自己负责权限和业务规则校验

只有满足以上要求，`media` 才能真正作为“平台能力”而不是“某几个接口”。

---

## 最小实施清单

为了让 `media` 达到本次定义的闭环，最小实施范围是：

1. 移除 `MediaFile.order` 及相关排序服务语义
2. 保留并固化 `get_media_list_info()` 作为统一回显能力
3. 形成并落地 `JSON list[id]` 的平台协议
4. 接入真实业务的 `MEDIA_REFERENCE_PROVIDERS`
5. 将 `upload_and_register()` 扩展为支持多作用域路径生成

完成以上 5 项后，`media` 就能作为一个对其他模块可复用、具备引用治理和延迟回收能力的基础平台。

---

## 非目标

本轮明确不做：

- 统一引用表或中间关系表
- 平台层权限系统
- `confirm` 接口的对象存储强校验
- 回收站机制
- 针对所有业务场景的一次性抽象建模

这些内容要么超出本轮闭环所需，要么会引入过度设计。
