# 房源租赁地址与默认定位设计

## 背景与目标

小区（`Estate`）和楼栋（`Building`）模型已具备 `address`、`lat`、`lng` 字段，但管理端仅允许手工填写地址，也未将坐标暴露为可维护的选址交互。本次改动让地址必须通过高德地图选择，并为每个租户维护一个可复用的默认定位。

目标：

- 在租户设置中维护默认地址和经纬度。
- 新建小区、独立楼栋时预填该默认定位。
- 用一个可复用的高德选址组件同步标准地址和坐标。
- 关联小区的楼栋继承小区位置，避免维护两份相互矛盾的位置。

不在本次范围内：团队级默认定位、为现有历史数据自动补地理编码、服务端代理高德 Web 服务 API。

## 方案选择

采用浏览器端高德 JS API 的可复用地址选择组件。项目已经通过 `useAmap` 从 app context 安全加载高德 JS API key 和安全密钥；组件在此基础上加载地点搜索与地理编码能力。选择搜索结果或点击地图后，组件输出 `{ address, lat, lng }`。

未采用后端代理高德服务：它可隐藏浏览器 key，但会额外引入服务端密钥、配额、限流和错误处理，而现有项目已经为浏览器地图交互准备了 JS API。未采用保存后异步地理编码：该方式无法让用户在保存前确认位置，也不符合地址应由选择产生的要求。

## 数据与接口

默认定位以通用设置项 `property_rental.default_location` 保存：

```json
{
  "address": "广东省深圳市南山区科技园路 1 号",
  "lat": 22.540123,
  "lng": 113.934567
}
```

设置项注册在既有 `DefaultSetting` / `OrganizationSetting` 机制中，分类为“房源租赁设置”，并声明专用 UI 类型，供租户设置页渲染地址选择器。未配置时，设置值为 `null`，新建表单不预填位置。

`EstateIn`、`EstatePatchIn`、`BuildingIn`、`BuildingPatchIn`、输出 schema 都应支持坐标字段。后端接受既有历史记录的空坐标，但创建或更新时若提供坐标，必须同时提供 `lat` 和 `lng`，并校验纬度在 -90 至 90、经度在 -180 至 180。地址仍可为空以兼容既有记录；管理端的新建和编辑流程通过选址组件写入地址，因而不提供手工地址输入。

## 管理端交互

新增可复用 `LocationPicker`：

1. 输入关键词后调用高德地点搜索，展示候选地址。
2. 选择候选项或点击地图后，更新地图标记、完整地址、纬度和经度。
3. 可清除已选位置；清除后地址和坐标一并清空。
4. 高德 key 缺失或 SDK 加载失败时明确展示不可用状态，且不允许用手工文本绕过地址选择。

租户“空间设置”的“房源租赁设置”中新增“默认定位”字段。选择并保存后，值写入现有组织设置接口。

小区新建抽屉加载完成后读取默认定位并预填 `LocationPicker`；编辑时显示小区自身已保存的位置。小区保存时同步 `address`、`lat`、`lng`。

独立楼栋（未关联小区）遵循相同逻辑。关联小区的楼栋不显示可编辑的地址选择器，而显示所属小区地址和坐标的只读说明；创建/更新时不写入独立定位。楼栋使用位置时由所属小区位置作为有效位置；旧数据中的楼栋级坐标保留，不做迁移或删除。

## 默认值与有效位置规则

- 小区新建：租户默认定位 -> 用户重新选择（可清空）。
- 独立楼栋新建：租户默认定位 -> 用户重新选择（可清空，但仍受既有“独立楼栋必须有地址”约束）。
- 关联小区楼栋：仅继承小区位置，不预填或编辑楼栋独立位置。
- 编辑：始终展示资源自身保存的位置；不因后来调整租户默认定位而覆盖已有数据。

## 错误处理与测试

- 后端单测覆盖：定位设置默认值/租户覆盖、坐标成对与范围校验、小区与独立楼栋的坐标 API 往返。
- 前端单测覆盖：设置页按专用 UI 类型渲染选址控件；新建小区/独立楼栋预填默认定位；关联小区楼栋显示继承说明。
- 组件单测覆盖：候选地址选择与清除会同步地址和坐标；SDK 加载异常展示错误状态。
- 高德查询失败时保留当前已选位置并显示可恢复错误提示；保存失败沿用页面既有错误提示和重试行为。

## 自查

- 设置范围明确为租户级，未引入没有当前上下文的团队级默认值。
- 地址、纬度、经度的来源、覆盖时机与清空行为一致。
- 关联小区楼栋的继承规则不会覆盖历史楼栋坐标，也不会要求数据迁移。
- 改动限于房源租赁、通用设置和管理端高德地图能力。
