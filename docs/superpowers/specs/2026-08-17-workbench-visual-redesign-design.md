# 工作台视觉重设计

## 背景与范围

`/rental/workbench/overview` 已具备可配置的组件注册表、三列栅格、拖拽排序、组件显隐与宽度配置。本次只重塑工作台内容区的视觉语言和信息层级，不改变既有数据请求、业务操作、布局配置结构或路由。

范围包括：

- 工作台页头、视角切换器和“自定义工作台”入口。
- “我的工作台”的五个已注册组件。
- “空间工作台”的五个已注册组件。
- 组件公共框架的加载、错误、空状态。
- 桌面端编辑工具栏、可拖拽组件边界、组件管理抽屉。
- 工作台内容区的平板与移动端响应式外观。

左侧导航、全局顶部栏、页面路由、多语言文件、`package.json`、生成 API 客户端和业务数据契约不在本次范围内。

## 已确认视觉方向

采用“冷静指挥台”的平衡版：用深蓝控制条、蓝色主操作态、细边框和低饱和状态色建立秩序；通过少量可识别的组件细节避免所有内容沦为相同白卡片。

视觉规则：

- 页面背景为冷灰浅色画布，组件使用白色或极浅色平面；不使用厚重卡片阴影。
- 深蓝 `#182338` 仅用于工作台页头和高优先级控制区；主操作蓝约为 `#4F7CFF`，青绿色只作为在线/完成辅助色。
- 红、琥珀、绿、紫分别表达阻断、临期、可执行、待确认/待签约等状态，不能仅用颜色传达含义，必须保留图标或文字标签。
- 所有数字使用等宽数字外观；指标采用细色带或小型状态图标，不能堆叠无意义图表。
- 组件统一使用 14–16px 圆角、1px 细边框和左上角短角标；交互悬停只提升边框与轻微阴影。
- 视觉装饰限制为页头的低对比椭圆线、状态色带、组件编号和公告折角；不使用背景点阵、密集网格、微型趋势柱或多层发光。

## 页面结构

### 共享页头

保留当前组织名称、日期、数据刷新状态、工作台视角切换和自定义入口的业务逻辑。

- 将页面信息组织为一条深蓝“指挥栏”：上方为小型英文/状态眉标，中间为当前工作台的中文摘要，下方显示组织、日期与数据更新时间。
- “我的工作台 / 空间工作台”继续使用现有 `Segmented` 控件，改造成暗色栏中的紧凑双选项；选中态为蓝底白字，未选中态为低对比文字。
- 自定义入口使用与切换器同高的方形图标按钮，保留现有权限与禁用逻辑。
- 手机端页头改为纵向布局：标题信息在上，切换器和自定义入口在下，两个切换项等宽。

### 我的工作台

默认组件顺序和宽度能力保持已有注册表定义不变。

| 组件 | 视觉结构 | 保留的业务能力 |
| --- | --- | --- |
| 待办概览 | 一体化四段状态轨道；每段有顶部状态色带、名称、数量和状态图标 | 跳转到逾期、今日到期、待接受与公告待确认筛选页 |
| 优先处理 | 带截止时间色条的任务队列；标题、标签、操作按钮分列 | 接受、完成、查看任务及现有排序规则 |
| 任务进展 | 单个环形完成率配合三个简短统计值 | 当前任务统计与进度计算 |
| 公告摘要 | 琥珀色左边条与右上折角的便笺式内容区 | 公告详情、全部公告和确认动作 |
| 快捷操作 | 两列或单列的紧凑入口块，深蓝/主蓝图标方块 | 已有快捷链接与权限控制 |

空公告使用现有空状态语义，但图标容器改为浅色圆角方块；错误与加载态沿用公共组件框架。

### 空间工作台

默认组件顺序和宽度能力保持已有注册表定义不变。

| 组件 | 视觉结构 | 保留的业务能力 |
| --- | --- | --- |
| 经营总览 | 五段经营指标甲板：在管房源、阻断发布、可发布、待补租客、待签约 | 当前汇总数据与自动刷新 |
| 发布工作区 | 有筛选分段控件的操作队列；左侧状态条区分阻断与可发布记录 | 补资料、检查后发布、发布与现有链接 |
| 关键风险 | 两个或多个纵向警报块，突出数量、原因和进入处理页的箭头 | 从现有空间数据派生风险，不新增请求 |
| 成交转签 | 四阶段横向流程轨道，底部保留当前最紧急的一条待办 | 待补租客、待签约跳转和现有处理入口 |
| 空间快捷操作 | 三列紧凑动作矩阵，分别进入房源、带看和租约 | 已有快捷链接与权限控制 |

发布工作区在较窄组件宽度下切换为紧凑列表：保留状态条、房源名、原因/说明和主要操作，隐藏非关键辅助信息。

## 公共组件框架与状态

`WorkbenchWidgetFrame` 继续承担标题、附标题、额外操作、加载、错误和空状态的结构责任；视觉层只通过新增可选的变体/类名表达组件类型，不能将业务条件判断迁入公共框架。

- 标题区统一显示小型编号方块、标题和右侧元信息/操作；编号由 widget 或注册表传入，不能依赖渲染顺序推导。
- 加载状态使用与目标组件宽高相近的骨架屏，保留 1px 边框和左上角标，避免布局跳动。
- 错误状态保留“组件数据加载失败”和“重新加载”操作，采用非阻塞的浅红提示面，不能使其他组件不可用。
- 空状态使用当前图标、标题与说明；仅替换容器和间距，不改变文字与跳转语义。

## 编辑态与组件管理

不改变 `WorkbenchLayout`、`SortableWorkbenchWidget`、`WorkbenchEditToolbar` 和 `WorkbenchCustomizeDrawer` 的职责及数据流。

- 编辑工具栏改为深蓝指挥条，明确显示“正在自定义 [视角]”、未保存状态、恢复默认、取消和保存布局。
- 可编辑组件保留虚线边框，但改为主蓝细虚线和左上角标；仅编辑状态显示宽度 `Segmented` 与拖动手柄。
- 当前拖动或焦点组件使用蓝色实边框及柔和外扩光圈；其他组件保持低对比虚线，不能同时高亮多个组件。
- 宽度 `Segmented` 继续只显示注册表允许的“窄 / 中 / 宽”选项；不得改变宽度值 `1 | 2 | 3` 的存储方式。
- 组件管理抽屉保留无蒙层、380px 宽度、显隐开关和桌面宽度控制。抽屉项增加组件编号方块、当前可见数量提示和更明确的禁用样式；仍至少保留一个组件。
- 编辑态提示语明确：排序在工作台内拖动，显隐与宽度在组件管理中调整；不得添加新的保存入口。

## 响应式规则

沿用现有栅格断点和配置规则：桌面三列、平板两列、移动端单列；不改变用户保存的宽度、顺序与显隐数据。

- 1199px 以下：两列栅格，宽度 2、3 均跨两列；指标甲板可按内容换行。
- 767px 以下：所有 widget 单列；我的待办概览为两列状态块；空间经营指标在两列或单列之间根据容器宽度折叠；发布队列隐藏辅助列。
- 移动端不渲染拖拽传感器、拖动手柄或宽度控件，保留现有“只调整显隐”的抽屉逻辑。
- 移动端仍由同一个“自定义工作台”入口打开 `Drawer`，但抽屉从底部弹出，只显示组件显隐开关和可见数量；不新增第二套管理入口，也不显示宽度或排序控件。
- 触控目标最小 40px；文本、状态标签和主要操作不应因窄屏截断到不可理解。

## 实施边界

主要修改集中在 `frontend_admin/src/pages/team-operations/workbench/`：

- `styles.ts`：建立工作台专属的页面、公共框架、widget、编辑态和响应式样式。
- `index.tsx`：调整页头的结构类名和必要的语义图标包装；不修改视角、权限、日期或数据状态逻辑。
- `WorkbenchWidgetFrame.tsx`：允许传入有限的外观变体/编号数据，保持加载、错误和正常渲染分支。
- `widgets/mine/*`、`widgets/space/*`：仅调整组件内部层级与样式类名；复用现有数据、路由、回调和可访问性标签。
- `WorkbenchEditToolbar.tsx`、`SortableWorkbenchWidget.tsx`、`WorkbenchCustomizeDrawer.tsx`：增加设计所需的语义包装和样式类名，不改变布局草稿、Dnd-Kit、抽屉开关或保存行为。

不修改 `layout/`、`data/`、`registry.tsx`、手写服务、生成服务、多语言、全局主题或后端代码，除非实现过程中现有组件无法提供必要的展示元数据。出现该情况时，应优先在 widget 局部定义展示常量，不能改动存储协议。

## 可访问性与交互

- 保留所有现有按钮、链接、分段控件、开关、拖动手柄的可访问名称。
- 新增的纯装饰图标、角标和色带必须带 `aria-hidden="true"`；业务状态必须保留可读文本。
- 焦点态使用主蓝 2px 轮廓，且与悬停态区分；不能只通过阴影表达焦点。
- 状态色与文本对比度满足现有 Ant Design 主题要求；红/绿状态配合图标或标签。
- 动效限于边框、背景和阴影的短过渡；遵循 `prefers-reduced-motion` 时不执行明显位移动画。

## 验证方案

- 为修改了条件渲染或组件结构的 widget 更新/补充 Vitest 测试，覆盖标题、关键数字、主要操作与空/错状态。
- 保留并运行现有工作台布局、编辑工具栏、组件管理抽屉和视角切换测试。
- 使用 1440px、1024px、768px、390px 视口检查：页头换行、三/二/一列栅格、指标折叠、主要操作和编辑控件可达性。
- 在浏览器中验证“我的工作台”和“空间工作台”均能展示真实数据、刷新状态、筛选跳转、任务操作、房源发布入口、编辑保存和取消。
- 运行管理端范围 TypeScript/Biome 检查；不修改 `package.json`、`package-lock.json` 或多语言文件。

## 风险与回退

- 最大风险是单个 widget 的内部信息密度与其可选宽度不匹配。通过 widget 自己的响应式分支处理，不能强制全局卡片统一高度。
- 公共框架的变体如果过多会重新形成“万能组件”。仅接受边框/标题区等外观变体，业务布局仍留在各 widget 内。
- 所有调整均为前端视觉层，布局配置协议、请求参数、接口和数据缓存不变；必要时可通过还原样式层回退，不涉及数据迁移。
