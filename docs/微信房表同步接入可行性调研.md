# 微信房表同步接入可行性调研与设计

调研日期：2026-10-27。依据为本次直接读取的微信官方文档和当前项目代码。尚未登录真实服务号后台，未进行微信真机收发或实际导入验证；本文是调研和设计，功能尚未实现。

## 已确认范围

- 使用者为普通微信的房东或中介，房表以文字消息为主。
- 首期只接入服务号，通过收到的消息触发房表同步，并在原会话回复结果。
- 服务号身份绑定一次，后续复用该身份；一次消息可以包含同一组织内有权限的多栋房表，不逐栋重新绑定。
- 消息导入流程保持通用，预留其他渠道的接入位置；首期只实现服务号 Adapter。
- 房表解析、预览与执行复用现有 `apps/house/house_sync/`。

## 可行性结论

| 入口 | 获取收到的消息 | 返回结果 | 本次结论 |
| --- | --- | --- | --- |
| 服务号 | 支持，微信向服务器推送文字正文和发送人 OpenID | 支持被动回复；具备权限后可异步发送客服消息 | 首期选定方案 |
| 微信客服 | 支持，收到事件后调用 `sync_msg` 拉取正文 | 支持客服消息，受会话状态和额度约束 | 可作为后续渠道 |
| 企微员工与外部客户普通单聊 | 有条件支持会话内容存档，涉及开通、告知及客户同意 | 本次未证实通用的员工身份自动回复接口 | 不据此承诺完整闭环 |
| 企微自建应用会话 | 支持企业成员向应用发消息的回调 | 支持应用消息及被动回复 | 适合企业内部使用 |

服务号依据：[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html)、[发送客服消息](https://developers.weixin.qq.com/doc/service/api/customer/message/api_sendcustommessage)。微信客服依据：[接收消息和事件](https://developer.work.weixin.qq.com/document/path/94670)、[发送消息](https://developer.work.weixin.qq.com/document/path/94677)。企微应用依据：[接收应用消息](https://developer.work.weixin.qq.com/document/path/90239)、[发送应用消息](https://developer.work.weixin.qq.com/document/path/90236)。

企微普通外部单聊不能与“微信客服”混用接口。会话内容存档要求配置员工范围、可信 IP 和加密公钥，外部联系人需要同意；消息通知后还需按 `seq` 拉取并解密。服务商接入另有数据与智能专区限制，不能直接承诺将员工聊天原文拉到链云后台。它适合作为后续独立可行性评估，不影响首期服务号方案。

依据：[存档使用前帮助](https://developer.work.weixin.qq.com/document/path/91361)、[获取会话内容](https://developer.work.weixin.qq.com/document/path/91774)、[会话通知](https://developer.work.weixin.qq.com/document/path/95039)、[服务商接口限制通知](https://open.work.weixin.qq.com/wwopen/common/readDocument/55098)、[数据与智能专区概述](https://developer.work.weixin.qq.com/document/path/99941)。

## 服务号已核实的能力和限制

### 消息接收

配置消息推送 URL、Token、EncodingAESKey 后，普通用户发送的文字会以 XML POST 到服务器。主要字段为 `FromUserName`（本服务号下的发送者 OpenID）、`Content`、`MsgId`、`CreateTime`。平台身份使用 `(channel, AppID, OpenID)`，不直接等同于小程序 OpenID 或链云用户 ID。

回调只提供实际提交人的身份，文字结构没有原转发作者身份字段。不能根据房表署名或正文中的手机号认定提交人的权限。

依据：[消息推送配置](https://developers.weixin.qq.com/doc/service/guide/dev/push/)、[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html)。

### 可靠接收与结果回复

- 微信等待回调响应的时限为 5 秒，未得到响应会重试，总共重试三次。接入层应先持久化并排重，再快速响应，后台任务负责耗时同步。
- 被动回复是本次回调直接返回 XML；异步处理可以快速返回 `success`，之后调用 `POST /cgi-bin/message/custom/send` 回复结果。
- 最新客服发送接口要求公众号、服务号为企业主体已认证账号；还需核对实际账号的接口权限。
- 用户发送消息后，客服回复额度为 5 条、有效期 48 小时。关注、扫码和特定菜单触发的是 3 条、1 分钟，不能把这些动作当作 48 小时回复许可。
- 接入时核对现有自动回复和菜单配置；官方消息推送指南提示开发者接管会影响原后台功能。

依据：[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html)、[被动回复](https://developers.weixin.qq.com/doc/service/guide/product/message/Passive_user_reply_message.html)、[发送客服消息](https://developers.weixin.qq.com/doc/service/api/customer/message/api_sendcustommessage)、[消息推送配置](https://developers.weixin.qq.com/doc/service/guide/dev/push/)。

### 历史与转发体验

官方存在 `POST /customservice/msgrecord/getmsglist` 获取客服聊天记录，查询区间最多 24 小时、单次最多 10000 条。这里的 24 小时是查询区间，不是历史保留期限。它属于客服记录；是否完整覆盖本业务消息尚未实测，首期可靠接收依赖实时回调和本地任务记录。

普通消息文档列出的类型包含文字、图片、语音、视频、位置和链接，没有列出通用文件或合并聊天记录。首期仅处理普通 `text` 文字。

官方服务端文档未保证服务号能直接出现在微信“转发”选择器中。这一点必须分别在 iOS、Android 验证；直接打开服务号会话并发送文字是另一种交互，不应混称为已验证的一键转发。

依据：[获取客服聊天记录](https://developers.weixin.qq.com/doc/service/api/customer/message/api_getmsglist)、[接收普通消息](https://developers.weixin.qq.com/doc/service/guide/product/message/Receiving_standard_messages.html)。

## 通用消息导入设计

### 模块和 Interface

建议新增 `apps/message_imports/` 作为通用 Module。渠道变化发生在 Adapter，房表规则继续由 `house_sync` 维护。

```text
服务号回调 → 服务号 Adapter ─┐
                           ├→ 标准消息 → 通用导入任务 → 房表预览/执行
后续渠道   → 对应 Adapter ─┘                              │
                                      渠道 Adapter ← 结果回执
```

通用入口接收标准消息，不接收微信 XML 或请求对象。公开 Interface 保持小范围：接受消息创建任务、查询任务结果、通过原渠道发送回执。渠道 Adapter 负责验签解密、消息归一化，以及将通用回执转换成渠道支持的发送请求。

服务号回调直接携带正文；微信客服先通知再拉取正文。两种模式都在得到标准消息后进入同一个导入入口，通用 Module 不假定每个 HTTP 回调都对应一条房表。

标准消息的必要信息：

| 字段 | 含义 |
| --- | --- |
| `channel` | 首期为 `wechat_official_account` |
| `channel_account_id` | 接收消息的服务号 AppID，区别于组织 ID |
| `message_id` | 渠道消息 ID，以字符串保存 |
| `external_sender_id` | 渠道发送者 ID；服务号为 OpenID |
| `message_type`、`text` | 首期仅文字，保留正文换行 |
| `sent_at`、`received_at` | 消息发送和本地接收时间 |
| `reply_context` | 原会话回复上下文，由对应 Adapter 解释 |

首期提供服务号 Adapter 和房表处理函数。后续新增渠道主要增加 Adapter、身份关联和渠道配置；房表处理函数不读取 `FromUserName`、`OpenKfId` 等原始字段。

### 身份和导入授权

身份绑定与业务授权分别处理。服务号身份能匹配已有关联账号时复用；尚未关联时，通过已登录链云账号的一次性绑定凭证建立关联，不按昵称或正文中的联系方式自动认人。绑定针对服务号中的用户身份，只需完成一次，不绑定到某一栋楼；之后同步其他已授权楼栋时直接复用。楼栋授权变化不要求重新认证身份。

导入绑定记录当前渠道身份、链云用户、目标组织、允许同步的楼栋或房源范围，以及是否允许自动执行完整房表。同一人有多个组织时，必须能明确当前任务的目标；组织和楼栋不从房表正文中任意指定。

房东可复用 `Contact.user` 和现有房东房源关系，不因绑定消息入口自动获得组织管理权限。任务创建时确定组织和资源范围，执行或确认时再次校验授权仍有效。

### 任务与幂等

建议以 `MessageImportTask` 保存标准消息、授权范围、处理状态、预览摘要、`plan_hash`、实际结果和回执状态。通过数据库唯一约束 `(channel, channel_account_id, message_id)` 排重。

同一消息的回调重试不能重复导入；同一任务的重试或重复确认也不能重复执行写入。任务执行时需要锁定任务并结合现有同步事务处理。相同文字在其他时间主动重发是新消息，不按内容永久去重。

任务持久化后，通过事务提交后的任务派发和已有 Celery 处理；未成功派发的待处理任务需要可恢复。同步结果与回执发送状态分开保存，回复失败只补发回执，不重新执行导入。

回执由 Adapter 检查渠道窗口和处理错误，通用业务不假定可以无限主动发消息。超出回复窗口时，结果仍可在链云任务详情中查看。

### 房表同步策略

当前规划器会将楼栋中未出现在房表里的有效房源改为已租。因此自动同步必须建立在“提交的是授权范围内的完整待租清单”之上。

现有解析器已经支持同一段文字中的多栋房表：每栋以地址开头，后跟房间清单，楼栋之间以空行分隔。服务号入口保留该能力，以同一组织内的一栋或多栋房表作为一个导入任务，逐栋匹配和校验，统一执行，再通过一条回执返回总计及各栋摘要。未出现在本次房表中的其他楼栋不参与同步。

- 绑定明确、具有所有目标楼栋的整栋同步授权、每栋房表完整、各栋唯一匹配且解析通过时，可以生成计划后自动执行。
- 一批多栋房表沿用现有整批校验和事务规则：存在未解决错误时不执行整批，执行中失败时回滚本批写入。
- 楼栋歧义、新楼栋、无法确认完整性或异常房态变化时，进入待确认，回传核对链接。
- 只有部分房源权限时，不能把现有整栋计划直接执行；所有计划变更都必须经过资源范围校验，越权时阻断。
- 多条分段消息不能逐条执行全量同步，需要明确收齐后统一生成计划。
- 确认操作绑定具体任务和 `plan_hash`；计划过期时重新预览。现有扫码登录事件继续按原流程分发。

这些策略是待实现设计；当前同步入口尚未提供外部消息提交人的完整授权校验。
