# Uhome 整团队自助迁移设计

日期：2026-10-25。状态：方案已确认，实施与验证记录见对应实施计划。

## 1. 已确认的目标和范围

旧系统由 `/Users/lan/Project/django/Uhome` 后端和 `/Users/lan/Project/uni-app/Uhome-frontend-insider` 前端组成；新系统为当前 `linkcloud-space`。

迁移主体是团队负责人：在旧系统导出本团队全部业务数据，随后在新系统选择自己管理的组织上传文件，完成校验、数据导入和后台媒体迁移。

第一版一次交付完整可用的流程：旧版导出、新版预检和导入、历史档案查询、媒体后台迁移、进度、异常报告、失败重试和中断恢复。内部按依赖顺序开发，验收覆盖完整流程。

已确认的媒体方案：

- 导出包只包含结构化业务数据和媒体 URL 清单，不下载、打包图片或视频实体。
- 新系统服务器后台读取旧资源并迁入新存储，用户不承担媒体文件的下载和再次上传。
- 迁移期间可回退展示旧 URL；成功后使用新媒体引用。
- 业务数据和媒体迁移分别展示状态，不能把“业务数据已导入”显示为“全部迁移完成”。

迁移包含团队业务资料和相关历史数据。密码、登录凭据、微信身份凭据、系统密钥、全站运行数据不属于迁移内容。首期提供文件迁移，不承担两套系统持续双向同步。

## 3. 用户流程和权限

### 3.1 旧版导出

入口：管理员 → 数据迁移。

页面提供当前团队信息、业务数量概览、生成全量迁移包、任务进度、下载、异常明细和历史任务。负责人不需要逐类勾选数据。

流程：

1. 根据服务端确认的当前团队展示概览及归属异常。
2. 第一个短请求保存任务并提交数据库，立即返回任务编号。
3. 第二个生成请求同步固定业务快照，生成数据文件、媒体 URL 清单、校验值和报告。
4. 显示来源团队、快照时间、各类数量和完整性结果，提供下载。
5. 离开页面或生成请求超时后，可以返回查询已保存记录。连接断开不直接判定任务失败；执行进程被终止时不会自动继续，长时间无进度的记录提示中断并允许重试。

导出权限限当前团队有效且已准入的 `boss/admin` 员工。每次创建、查看、重试、签发下载入口都重新检查 token、员工是否停用、`Staff2Team.accept`、关系删除标记和团队一致性；不能仅相信请求头或历史任务创建者身份。

下载文件通过鉴权接口或短时下载凭证提供，不放在公开可枚举地址。电脑下载入口使用一次性兑换的短时凭证，不携带账号 token；凭证失效可回到已登录页面重新申请。任务历史保留审计信息，文件是否仍可下载单独展示。

### 3.2 新版导入

入口：组织管理 → 数据迁移 → 从旧版 Uhome 导入。管理端与小程序/H5 端均提供入口和任务查询；大文件提供电脑操作路径。

第一版限目标组织所有者操作。上传文件不能自动创建账号、授予权限或切换到包内声明的组织。

流程：选择目标组织 → 上传 → 后台预检 → 补全和冲突处理 → 确认导入 → 查看业务、媒体两组进度 → 查看报告。

上传页推荐使用空组织，也支持已有组织。目标组织名称在上传、确认、任务详情中持续显示。一次任务只能写入一个明确的目标组织。

预检不写入正式业务数据，展示来源、版本、快照时间，以及预计新增、复用、归档、重复、冲突、错误数量。业务阻断项处理完毕后才能确认执行；对现有组织的匹配结果重新核对版本，避免使用过期预览写入。

### 3.3 结果和历史查询

任务页按数据类型展示记录数和异常，支持定位到旧记录标识、处理结果和新版记录。媒体列表展示资源、关联对象、迁移状态、尝试次数、失败原因及重试入口。

“历史档案”支持分类、时间、经办人、旧单号、关联房源、审核和删除状态筛选，并提供列表、详情和关联跳转。财务类历史档案沿用组织内财务权限；非财务成员不能因可查看房源而读取旧薪资、佣金或审核信息。

## 4. 数据范围和归属规则

### 4.1 数据清单

| 数据集 | 旧版来源 | 归属条件 | 新版去向 |
| --- | --- | --- | --- |
| 团队资料 | `Team` | 当前团队 | 组织资料的确认映射及来源档案 |
| 业务设置 | `Settings`、`SettingTeam` | 当前团队，按明确的业务字段清单导出 | 兼容设置经确认应用，其余业务值进入档案 |
| 员工、相关身份资料 | `Staff`、`Staff2Team`、必要的 `User` 字段 | 当前或历史团队关系；业务关联的历史身份仅取必要字段 | 历史员工档案、成员映射 |
| 房东 | `Landlord` | 当前团队 | `Contact`，角色为房东 |
| 楼栋 | `Building` | 当前团队 | `Building` |
| 房源 | `House`、`House2Team` | 当前团队关联 | `House` 及来源记录 |
| 员工房东分配 | `Staff2Landlord` | 本团队房东和本团队员工范围 | 已映射成员的 `PropertyResponsibility`；未映射关系保留待绑定 |
| 业绩账单 | `Bill`、`Bill2Team` | 当前团队关联 | 历史账单档案 |
| 加扣薪资 | `Salary` | 有唯一、可验证的本团队归属 | 历史薪资档案 |
| 勘察及旧媒体 | `HouseSurvey` | 本团队房源；外部员工仅保留必要历史身份 | 历史勘察档案及关联媒体 |
| 房源统计 | `HouseStats` | 本团队房源 | 独立标识为旧版累计统计的档案 |
| 入职申请 | `AuthApply` | 当前团队 | 历史入职申请档案，不触发重新审批或入职 |

显式读取含软删除记录的数据集合，再执行团队范围筛选，不能依赖旧版默认过滤删除记录的 manager。已删除记录保留原标记并进入历史档案，不自动恢复为活跃房源、联系人或员工关系。

全站事件统计、POI 缓存、平台权限目录、账号认证数据、个人收藏等不作为团队业务资产导出。团队相关身份资料只包含业务所需的旧标识、姓名和必要联系方式，不导出全局用户表。

### 4.2 跨团队及不明确归属

- 房源和账单按当前团队关联筛选，不递归带出关联对象的其他团队数据，也不向导出包写入其他团队成员清单。
- 楼栋、房东外键指向其他团队时，不展开外部对象明细；保留本团队原始业务记录及关联异常，在预检中要求映射到目标组织自有对象。
- 薪资优先使用可唯一对应的账单及 `Bill2Team` 证明归属。不能仅凭员工当前在哪个团队，就推定其全部历史薪资属于该团队。
- 无法证明归属的敏感数据不进入包；导出结果展示异常数量和原因，不展示跨团队明细。由有相应权限的平台人员补正来源归属后重新导出。
- 存在未解决的归属异常时，任务不能标记为“本团队全部数据完整导出”。报告必须体现异常，切换验收前解决。

### 4.3 员工和账号

员工资料先保留为历史身份。负责人可以在预检或导入后映射到目标组织现有的有效成员；同名不自动绑定，手机号只作为匹配提示。

未加入组织的员工通过现有邀请流程加入后再绑定。旧角色、微信标识、密码不转换为新版登录能力或权限。完成成员映射后可以恢复本团队有效的房东分配关系，不重复创建已有分配。

## 5. 迁移包协议 v1

### 5.1 文件结构

```text
uhome-migration-<team>-<export-id>.zip
├── manifest.json
├── data/
│   ├── team.jsonl
│   ├── settings.jsonl
│   ├── identities.jsonl
│   ├── staff.jsonl
│   ├── staff_team_relations.jsonl
│   ├── landlords.jsonl
│   ├── buildings.jsonl
│   ├── houses.jsonl
│   ├── house_team_relations.jsonl
│   ├── staff_landlord_relations.jsonl
│   ├── bills.jsonl
│   ├── bill_team_relations.jsonl
│   ├── salaries.jsonl
│   ├── surveys.jsonl
│   ├── house_stats.jsonl
│   └── auth_applications.jsonl
├── media.jsonl
└── export-report.json
```

不包含 `assets/` 或任何媒体实体。数据集为空时仍保留空文件和零条数量，区分“没有数据”与“导出遗漏”。

### 5.2 清单和记录

`manifest.json` 至少包括：

- `format: uhome-team-migration`、`schema_version: 1`。
- 稳定的 `source_instance_id`、`source_team_id`、团队显示名和唯一 `export_id`。实例标识跨导出任务保持一致。
- `snapshot_at`、`generated_at`、`source_timezone`。
- 每个数据文件的路径、记录数、字节数和 SHA-256。
- 媒体引用数量、去重资源数量、导出完整性和异常数量。

SHA-256 用于检查文件完整性，不证明来源真实性，也不作为授权依据。

每条业务记录包含 `entity_type`、`source_id`、业务字段、来源时间、删除标记和关联旧标识。`source_id` 使用旧表主键字符串；房源 `houseId`、员工 `staff_uid` 等另行保留，避免把缺少唯一约束的业务字段作为唯一身份。

金额用十进制字符串交换；保留旧值和转换结果。旧浮点金额只按实际存储值转出，不声称恢复已经丢失的小数精度。时间使用带时区的 ISO 8601，保留原始业务时间；新版实际导入时间单独记录。

采用显式业务字段清单，不使用数据库整库备份或 Django 全字段 dump。设置中的密钥、通知凭据和认证字段在导出前剔除；导出报告记录字段类别及数量，不记录秘密值。

### 5.3 媒体清单

每条媒体引用包含：来源实体及旧标识、字段路径、顺序、媒体类型、原始 URL、可取得的对象标识、已知文件信息。视频及其封面分别登记，并保留对应关系；勘察旧图、组织标志和员工历史业务图片同样登记。

稳定 URL 直接保存。带过期签名的 URL 同时保存可取得的对象标识和过期信息；后台通过平台配置的旧存储只读访问能力获取资源，访问密钥不进入包。签名链接失效且没有读取能力时，记录为明确的资源失败，支持修正来源后重试或补传。

导出只解析并归集已有引用，不逐个发送网络请求检查资源。实际可访问性、类型和大小由新版媒体任务确认。

### 5.4 文件接收

仅接受协议允许的文件路径和数据集，检查版本、校验值、计数、重复身份、悬空关联和资源引用。按配置限制压缩包、展开总量和单条记录大小，拒绝路径穿越、符号链接及异常压缩包。

初始接收上限设为压缩后 100 MiB、展开总量 1 GiB，作为可调整的运行配置。超限明确报错，不截断数据；上线前用真实团队样本验证并调整容量。媒体不占用这些数据包容量。

## 6. 新旧字段映射与冲突

| 旧字段或差异 | v1 处理规则 |
| --- | --- |
| 旧团队 → 新组织 | 用户明确选择已拥有的目标组织；组织名称、联系方式和标志逐项确认，不自动覆盖已有组织资料或套餐 |
| 楼栋地区、地址 | 优先使用本团队 `Building`，房源早期内嵌值作为可见的回退候选，矛盾时提示确认 |
| 楼栋名称 | 预检要求确认；地址可作为建议值，不隐式冒充已有楼栋名称 |
| 楼栋总楼层 | 可展示房源 `floor.totalFloor` 的一致值作为建议；有缺失或矛盾时要求确认，不把最高房源楼层当真实总楼层 |
| 房东字段 | 本团队 `landlordNew` 优先；仅有旧 `landlord/phone` 时生成待确认候选；无有效联系方式时补全或取消房东关联并保留原始档案 |
| `houseNum` | 映射房号；为空或同楼栋重复时预检处理，不静默生成新房号 |
| `houseType.rooms/halls/toilets` | 映射卧室、客厅、卫生间数量；保持原始数值，前端继续使用“单间”共享展示规则 |
| `floor.atFloor`、`area`、`rent` | 映射楼层、面积、挂牌租金；非法值显式提示 |
| `useWay` | 按明确枚举映射出租分类；无法识别时保留原值并提示确认 |
| `payMethod`、`dueTime`、置顶等旧字段 | 原始内容完整保留在来源档案或房源扩展数据；不能将旧付款周期、到期日期直接拼成完整租约 |
| `isRented` | `true` 映射已出租；`false` 的候选状态为招租中；缺失或不明确为暂不出租。预检确认应用状态，已删除房源仅归档 |
| 经纬度 | 标明 GCJ-02 等来源坐标系，调用现有坐标工具转 WGS84；保留原值。默认占位坐标和未知来源需要确认，不能当作真实定位 |
| 图片、视频 | 保留 URL、顺序和类型，进入后台迁移；超出房源 9 图、3 视频限制的内容进入关联历史附件，并提供查看入口 |
| 旧账单、薪资 | 原单号、经办人、金额、审核状态、时间及删除状态进入历史档案，不编造租客和租期 |
| 旧累计统计 | 单独标识来源和快照时间，不合并进新版实时事件，避免重复累计 |

完整原始业务记录保存在受权限保护的来源档案，正式业务字段仅写入经过转换和校验的内容。公开房源接口不返回完整原始记录、员工薪资或其他内部档案。新版业务对象的实际创建、更新时间不伪装为旧系统时间；旧时间在档案和详情中可查。

匹配顺序为：已有来源映射 → 目标组织内精确业务键候选 → 人工确认。联系人依据组织、姓名、标准化联系方式提供候选；楼栋依据组织及结构、地址；房源依据目标楼栋和房号。地址相似、姓名相同均不能直接合并。

已有对象可由负责人确认复用。重复来源且内容相同的记录跳过；同一来源内容变化、或目标已修改的记录展示字段差异，可选择保留现状、确认更新允许字段、重新映射。更新不覆盖未授权字段、不改变租约和财务结果。决定及其依据版本进入预检结果，执行时再次校验。

## 7. 模块、持久化和后台执行

### 7.1 模块边界

旧后端新增独立 `DataMigration` 模块，负责归属、显式序列化、快照、打包、任务和下载；复用现有鉴权及存储能力。旧前端新增管理员迁移页面，沿用现有 uni-app、请求和权限展示方式。

新版新增 `apps/data_migration`，包含包解析、预检、Uhome 字段转换、记录导入、历史查询、资源迁移及任务 API；复用现有 Celery、组织权限、媒体登记和坐标工具。第一版只实现已确定的 Uhome 协议，不建设通用插件或任意模型导入引擎。

### 7.2 核心记录

| 记录 | 用途 |
| --- | --- |
| 旧版导出任务 | 团队、操作者、快照、状态、数量、心跳、文件、异常报告 |
| `MigrationBatch` | 目标组织、来源实例和团队、导出标识、文件校验、预检决定、业务及媒体状态、操作者 |
| `MigrationRecord` | 来源身份、原始业务记录、内容校验、来源时间、导入结果、目标映射、错误；历史档案复用此记录，增加分类查询所需字段和索引 |
| `MigrationObjectMapping` | 跨批次的稳定来源身份到目标对象映射、最近确认的来源内容校验和目标版本 |
| `MigrationAsset` | 组织内资源身份、原 URL/对象标识、资源类型、目标媒体、状态、尝试次数、心跳及错误 |
| `MigrationAssetBinding` | 来源记录、目标对象、字段、顺序、有效标记和回填版本，将资源本体与业务排列关系分开 |

来源身份采用 `(目标组织, 来源实例, 来源团队, 数据类型, 来源主键)`。`MigrationObjectMapping` 对该组合设置唯一约束，后续导出沿用；`MigrationRecord` 对批次及来源身份设置唯一约束，每个批次保留独立来源快照与处理结果，不用新快照覆盖旧审计记录。

批次内每条来源记录唯一；确认和记录处理均幂等。目标指针只允许固定模型及当前组织范围，不能由包内模型名称触发任意写入。

### 7.3 旧版任务执行

旧版采用“先保存记录，再用独立 HTTP 请求同步生成”的方式，不要求常驻 worker，也不创建后台线程或子进程。前端先显示已提交的记录，再发起生成请求；已有记录重复触发时依靠指定任务认领和租约避免重复打包。管理命令保留为可选维护工具，不是正常导出的部署前置条件。

生成请求显式脱离 `ATOMIC_REQUESTS`，先完成指定任务认领的提交，再固定一致性读快照并流式输出 JSONL。所有关联和最终计数来自同一快照；读取快照完成后结束读事务，再生成 ZIP。独立进度连接不参与请求级事务，确保进度能被其他请求查询。

同步生成仍占用一个 Web 处理进程，不能保证在代理断开连接或 Web 进程硬超时后继续完成。前端遇到超时会查询状态，成功则恢复下载入口，仍在执行则继续查询。查询本身不执行导出；等待开始或执行中记录超过 5 分钟无有效进度时，撤销旧租约并提示重试，避免永久停留在生成中。未成功发布的半成品不能下载，旧进程不能覆盖重试结果。

### 7.4 新版任务执行

预检、业务导入和媒体迁移使用现有 Celery。任务入队在数据库提交后进行；定期恢复器重新投递未入队或租约超时的任务，处理发布失败和 worker 重启。

业务记录按依赖顺序、小事务处理，写入结果和来源映射与业务对象同事务提交。组织内迁移写入串行协调，依靠唯一约束和行锁处理重复确认及并发任务；网络下载不持有数据库长事务。

历史账单、薪资、申请、勘察按档案写入，不调用成交、收益分配、钱包入账、工资发放或外部通知流程。

## 8. 媒体迁移和过渡展示

### 8.1 资源读取和写入

媒体去重范围限定目标组织、来源资源身份和资源用途。相同 URL 或对象标识、相同用途的引用复用任务及结果，不进行跨组织去重。不同用途沿用现有 `resource_type` 校验，不用同一个错误用途的记录强行复用。

媒体任务只允许访问配置的旧 OSS/CDN 来源。解析地址及 HTTP 重定向均校验来源和网络目标，不能通过导入 URL 读取任意内网服务；限制超时、读取体积和响应类型。对象标识只能通过受控配置的旧存储访问能力解析。日志不输出带签名的完整 URL 或读取凭据。

服务器流式读取并写入新存储，不把整段视频加载进内存。复用现有文件类型、大小和图片校验；不支持的文件明确记录失败及处理入口，不默默丢弃。

新文件写到目标组织目录，登记适当的 `MediaFile`，图片复用现有缩略图任务。仅用于历史档案且没有现有用途的合法业务附件增加明确的历史附件用途，不修改现有房源媒体约束。

每次任务最多自动重试 3 次，采用退避。404、权限、签名过期、类型不支持、超限等保留可读错误；负责人可以更新合法来源或补传文件，再单独重试。旧资源确实缺失时记录为缺失，不能标记迁移成功。

### 8.2 回退展示与编辑

正式 `images/videos/logo` 字段继续只保存有效的新版媒体引用。通过只读的迁移媒体附加信息返回未完成引用及其位置，由共享展示逻辑合并展示，不把任意 URL 或伪造 `media_id` 写进 `MediaRefsField`。

迁移媒体附加信息遵守对应对象及字段的读取权限；公开房源只能取得原本允许公开的房源媒体，不能夹带员工二维码、历史薪资附件等内部资源。两端上线前核对旧资源展示域名及签名 URL 的刷新方式。

| 资源情况 | 展示及处理 |
| --- | --- |
| 迁移成功 | 使用新版资源及可用缩略图 |
| 排队、迁移中 | 回退旧 URL；没有可用 URL 时展示迁移中占位 |
| 迁移失败、旧 URL 仍可用 | 继续展示旧资源，任务页保留失败原因 |
| 旧资源失效 | 展示缺失状态，支持修正来源或补传 |
| 超出正式展示数量 | 在关联历史附件中查看，不挤掉用户现有媒体 |

编辑提交不把只读迁移信息作为正式媒体引用。用户可以移除待迁移引用；正常编辑若改变了媒体字段，必须更新引用有效性和字段版本。后台回填加锁并检查版本，仅更新仍有效的迁移引用，按原顺序合并。

若用户修改与回填冲突，已复制文件保留在关联迁移附件中，显示“待确认关联”，支持负责人选择附加，不覆盖当前字段，也不把已移除的图片重新插回。封面随有效顺序恢复。

### 8.3 媒体引用生命周期

`MigrationAsset` 和历史附件仍持有的目标媒体接入 `MEDIA_REFERENCE_PROVIDERS`，避免“已复制、未回填”或“仅历史档案引用”的文件被现有孤儿清理机制判为未引用。

源文件迁移成功后，实际展示和编辑使用新版存储，来源 URL 只用于审计。全部媒体完成或明确核对缺失项后，迁移任务才具备切断旧资源依赖的验收条件。

## 9. 状态、恢复和核对

业务状态：`uploaded → validating → awaiting_confirmation → importing → completed`。预检业务错误进入 `blocked`；执行失败进入 `partial_failed/failed`，修正后从未完成记录继续。

媒体状态：`pending/processing/succeeded/failed/missing`。尚未产生媒体任务时不展示虚假百分比；资源总数明确后展示成功、处理中、失败、缺失及总数。

任务页总体结果区分：待确认、数据导入中、数据已导入/媒体迁移中、需要处理异常、全部完成。历史归档属于设计内的正常结果；未处理记录、媒体失败、缺失及待确认关联不能显示为全部完成。

每类业务记录满足：

`包内记录数 = 新增 + 已确认更新 + 已确认复用 + 相同来源跳过 + 历史归档 + 未完成/失败`

上述结果按来源记录互斥计数；原始档案的留存不额外增加“历史归档”结果，只有以档案为最终去向的记录计入该项。关系记录、资源引用数和去重资源数分别统计，不能混用。

档案金额按原账单类型、审核和删除状态分别核对。旧版存在浮点表示差异时展示原值及规范化结果，不通过模糊汇总宣称金额一致。

重复上传同一包返回或复用已有批次，保留已有进度；新导出包通过来源身份识别已有对象，变化记录重新预检。恢复任务不重新覆盖已经处理且后来被用户修改的数据。

报告可在页面查看并下载。日志和报告保留批次、旧标识、目标标识、状态和错误；敏感内容按查询权限展示，技术日志不记录整包业务原文。

## 10. 接口和页面边界

旧版接口沿用既有 `/api/`、token、`Request-Team` 和响应封装，归入 `/api/data-migration/`：概览、创建记录、任务列表、详情、同步生成、重试和下载凭证兑换。`POST exports` 仅提交记录，`POST exports/<id>` 的 `action=generate` 在请求内生成，`action=retry` 重置失败记录后由前端重新触发生成。下载服务不复用公开房源文件地址。

新版 Ninja API 归入 `/api/data-migration/`：创建上传批次、预检、保存补全及映射、确认导入、任务详情和列表、记录结果、资源列表及重试、来源修正或补传关联、历史档案查询和报告下载。来源修正操作只能处理当前组织的合法资源，补传沿用现有媒体上传能力。

所有列表使用 `page/page_size` 和 `{items, total, page, page_size}`，依照项目 paginator 声明。确认请求包含预检版本，业务状态和媒体状态独立返回。

前端分为旧版导出页、新版导入向导、迁移任务详情、历史档案列表及详情。管理端与小程序/H5 共用协议和后端状态；图片、封面及视频回退展示使用各端共享适配方法，避免各页面自行猜测迁移状态。

对接新版 API 时生成客户端，不手工修改 `services/openapi`。实施管理端、小程序页面分别遵守对应目录说明和组件 API 查询要求；不顺带修改多语言、依赖清单或其他业务模块。

## 11. 实施顺序与第一版验收

### 11.1 同一版本的实施顺序

1. 固定协议 v1、显式导出字段清单和字段转换，准备脱敏团队样本；为归属不明数据提供可定位报告。
2. 完成旧版任务、快照导出、下载及管理员页面。
3. 完成新版批次、预检、字段补全、成员和实体映射、正式业务导入及来源幂等。
4. 完成历史档案、记录查询、报告、两端任务进度及恢复机制。
5. 完成媒体后台迁移、过渡展示、引用回填、历史附件、补传和独立重试。
6. 使用同一团队验证完整流程，修复数据和兼容问题后作为第一版一起交付。

### 11.2 必须验证的场景

- 负责人可以完成从旧版导出到新版使用的全过程，无需开发人员直接操作数据库导入。
- 导出只包含当前团队数据；篡改团队、任务、批次或资源标识不能越权；离职或失去负责人权限后不能继续下载。
- 含软删除、历史员工、跨团队异常、旧内嵌字段和空数据集的样本有明确处理结果。
- 楼栋、联系人、房源、分配和历史记录的数量及关联可核对；历史金额和审核状态保持可解释。
- 缺楼栋字段、重复房号、重复联系人、现有组织匹配和过期预检均有可操作的处理流程。
- 同一包重复上传、重复确认、同一来源的新包导入不会重复创建或无确认覆盖数据。
- 旧版导出连接或 Web 进程中断后记录仍可查询并可重试；新版 Celery worker 和任务发布中断后可以恢复，重试不重复写入已成功记录。
- 媒体 URL 字符串、旧视频对象和封面、重复 URL、超数量、404、超时、签名失效、非法来源、大视频等均有明确结果。
- 图片先回退旧 URL，迁移后保持顺序和封面；用户期间增删或修改图片，后台不覆盖或复活旧引用。
- 历史附件和待关联媒体仍被正确引用，现有清理机制不会误判其无主。
- 导入历史账单不产生新租约、收益分配、钱包流水、工资发放或外部业务通知。
- 管理端及小程序/H5 能完成入口操作、进度查看、异常定位和重试；大文件电脑路径单独验证。
- 使用脱敏真实团队样本核对数据并评估容量，不能以 mock 页面或静态检查代替正式流程验收。

验证优先覆盖归属、金额、幂等、恢复、媒体回填和端到端业务链路，不为简单展示堆积重复单测。后端测试按项目要求在容器内执行；视觉证据放入 `.codex/audits/uhome-team-migration/`，不写入项目根目录。

### 11.3 正式切换

先试迁移并核对样本及字段映射；正式切换时团队短暂停止旧版录入，生成最终快照并重新预检变化记录。完成业务核对后启用新版业务操作；旧存储维持可读直到后台媒体迁移和缺失项核对完成。

第一版完成的依据是上述验收结果。本文档确定设计和交付范围；具体实施、测试及部署边界记录在 `docs/superpowers/plans/2026-10-25-uhome-team-data-migration.md`，不能把脱敏样本或本地检查解释为生产数据、真实 OSS 网络或微信真机验收。
