# 功能总览

本文档从“当前仓库已经具备什么能力”的角度整理功能边界，帮助新同学快速判断哪些能力已经现成可用，哪些能力应该在现有模块上继续扩展。

## 1. 系统入口

当前项目包含两个前端入口、一个临时根路径页面和一套统一后端：

- 根路径 `/`：Django 临时跳转页，后续替换为正式官网地址
- 后台 `/dashboard/`：Ant Design Pro 管理后台前端，用于运营、审核和管理功能
- H5 `/h5/`：由小程序工程产出的 H5 版本
- API `/api/`：统一的 django-ninja API
- 认证接口 `/_allauth/`：django-allauth headless 浏览器端与 app 端认证入口

## 2. 认证与账号体系

对应模块：`apps/accounts`、`apps/base`

### 已有能力

- 邮箱/密码登录
- 注册与邮箱验证
- 密码重置
- 手机号验证码流程
- 微信小程序手机号绑定
- GitHub 登录
- 微信开放平台登录
- 微信小程序 token 登录
- MFA：TOTP、恢复码、WebAuthn passkeys
- 用户头像上传与裁剪
- 超级管理员 impersonate / hijack

### API 与鉴权特点

- 统一使用 allauth headless 流程，浏览器端返回 JSON 而不是模板页
- `/api/` 同时支持 Django Session、JWT Bearer、`X-Session-Token`
- `/api/app-context/` 返回当前用户、当前租户和前端初始化所需上下文
- `/api/csrf/` 用于独立前端获取 CSRF token
- `/api/auth/provider-login/` 提供 GitHub/微信等第三方登录跳转入口

### 后台账号管理

已提供用户生命周期接口，支持：

- 用户列表、搜索、创建、更新
- 启用/禁用账号
- 管理员直接设置密码
- 重置用户 MFA
- 解绑手机号
- 解绑微信账号

## 3. 实名认证

对应模块：`apps/accounts`

### 已有能力

- 用户端查看实名状态
- 用户端提交实名认证
- 驳回或撤销后的重新提交
- 实名认证时间线日志
- 后台查看实名记录详情
- 后台人工复核、通过、驳回、撤销

### 当前设计特点

- `User` 上保留实名摘要字段，便于列表和上下文快速读取
- `RealNameVerification` 保存每次实名申请记录
- `RealNameVerificationLog` 保存状态流转日志
- 完整姓名与证件号采用加密存储，同时保留脱敏值和 hash 辅助字段
- 当前默认实现是“模拟自动校验 + 人工兜底”的服务层，为后续接入真实实名厂商预留了接口位置

## 4. 多租户组织体系

对应模块：`apps/organizations`

### 已有能力

- 创建组织
- 切换当前组织
- 设置主组织
- 退出当前组织上下文
- 更新组织资料
- 组织归档/恢复
- 转移 owner
- 查看组织成员/团队用量

### 成员与邀请

- 组织成员列表与搜索
- 添加成员、修改 owner 状态、移除成员
- 创建邀请、查看邀请、重发邀请、取消邀请
- 公开邀请页查询邀请详情
- 登录后接受/拒绝邀请

### 会话中的组织上下文

- `OrganizationMiddleware` 负责在请求中注入当前组织上下文
- 会话中会缓存精简租户信息，减少每次请求的数据库负担
- 登录、hijack 开始/结束时会自动切换到主组织

## 5. 团队与 RBAC 权限

对应模块：`apps/teams`、`apps/access`

### 团队能力

- 团队列表、搜索、详情
- 创建团队并设置初始成员
- 更新团队名称和成员
- 删除团队

### 权限能力

- 权限点清单查询
- 组织级角色列表
- 团队级角色列表
- 自定义角色创建、修改、停用
- 组织级角色绑定与移除
- 团队级角色绑定与移除

### 使用边界

- 权限系统已经覆盖“谁能看、谁能改、谁能管理角色”的基础闭环
- 业务模块新增权限时，可以沿用现有角色/权限/绑定模型扩展，不需要再单独发明一套授权系统

## 6. 通知系统

对应模块：`apps/notifications`

### 已有能力

- 站内通知列表
- 未读数量统计
- 单条已读/未读切换
- 批量已读、批量未读、批量删除
- 通知详情查询
- 通知偏好设置
- 测试通知发送入口

### 当前特点

- 同时支持站内和邮件两个通道
- 偏好按通知类别维护
- 目标模型清理和保留期清理由配置驱动
- 可通过 `notify()` 在业务代码中直接产出通知

## 7. 设置系统

对应模块：`apps/settings`

### 已有能力

- 用户级设置的读取、更新、删除
- 组织级设置的读取、更新、删除覆盖值
- 团队级设置的读取、更新、删除覆盖值

### 设计意图

- 默认值在系统层统一定义
- 用户、组织、团队可以覆盖同一类设置键
- 适合承接通知偏好以外的展示、行为、业务阈值类配置

## 8. 媒体与文件上传

对应模块：`apps/media`、`docs/media-platform.md`

### 已有能力

- 获取 OSS/STS 临时上传凭证
- 前端直传完成后确认登记媒体文件
- 服务端接收文件后上传并登记，支持 `user/org` 两种作用域
- 统一媒体文件记录模型
- `validate_media_ids()` 用于业务保存前做重复/存在性校验
- `get_media_list_info()` 按业务传入的 `media_ids` 顺序回显完整媒体信息
- Provider 驱动的“业务引用扫描 + 垃圾清理”约定

### 当前接入模型

- 业务侧通常使用 `media_ids` 保存引用关系
- 顺序以业务保存的 `media_ids` 列表顺序为准，不依赖媒体表中的全局排序字段
- 媒体平台只负责文件记录与存储，不自动理解业务权限
- 媒体是否可清理，由 `MEDIA_REFERENCE_PROVIDERS` 报告的引用结果决定
- 在尚未接入任何真实业务 provider 之前，媒体清理任务会安全 `no-op`，避免误删历史文件

## 9. 前端与页面层现状

### 站点根路径 `/`

- 当前由 Django 直接返回临时跳转页
- 后续会替换为正式官网地址
- 不再保留旧 `frontend/` 主站 SPA 作为当前入口

### `frontend_admin/` 管理后台

- 作为官方 Ant Design Pro 独立子工程存在
- 已用于承接后台管理与审核类功能
- 当前第一阶段仅完成后台壳子替换，真实鉴权与业务页面迁移会在后续阶段接入

### `frontend_miniprogram/` 小程序端

- 作为独立子工程存在
- 承接微信小程序及其 H5 版本能力
- 当前仓库同样保留了上游模板 README，项目落地能力应以当前接口与业务实现为准

## 10. 开发与运维基础设施

### 开发侧

- Docker Compose：`db`、`redis`、`web`、`worker`，`docs` 作为可选 profile
- Just 命令统一封装常用开发操作
- uv / epicenv 管理 Python 依赖与环境变量生成

### 质量保障

- Ruff、Ty、ESLint、djLint
- pytest + pytest-django
- Playwright e2e
- model-bakery 测试数据生成

### 部署侧

- gunicorn 生产运行
- WhiteNoise 提供静态资源服务
- 支持 S3/MinIO 兼容媒体存储
- Celery + Redis 处理异步任务和定时任务

## 11. 哪些能力适合继续复用

以下能力已经适合作为后续业务开发的“公共基础设施”：

- 认证与多端登录
- 组织、团队、多租户上下文
- RBAC 权限模型
- 通知与通知偏好
- 媒体上传与文件记录
- 用户/组织/团队设置
- 实名认证状态流与后台审核闭环

如果新增业务域，优先考虑基于这些既有模块扩展，而不是平行再造一套能力。
