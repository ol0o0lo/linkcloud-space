# 楼栋可选绑定小区与关联资源删除保护设计

## 背景

当前房源空间结构为 `Organization -> Estate -> Building -> House`。`Building.estate` 是必填外键，房源组织归属和部分权限查询通过 `House -> Building -> Estate -> Organization` 推导。这种设计无法准确表达独立公寓、城中村单栋、园区外单体楼等没有小区档案的真实场景。

本次调整允许楼栋不绑定小区，同时保持房源必须绑定楼栋。小区从权限归属链中的必经节点调整为楼栋的可选归类；楼栋自身的 `organization` 成为稳定的租户边界。

## 目标

- 楼栋可选择绑定小区，也可作为独立楼栋存在。
- 房源继续强制绑定楼栋，带看、租约、房东查询等业务流程保持不变。
- 独立楼栋与绑定小区的楼栋拥有相同的数据可见性和操作能力。
- 小区地址表示项目整体地址，楼栋地址表示具体楼栋地址，两者独立保留。
- 删除小区或楼栋前检查关联资源；存在关联资源时禁止删除，并允许前端快速跳转查看。
- 删除接口在并发情况下重新检查关联资源，并返回可供前端直接展示的最新资源摘要。

## 非目标

- 不允许房源脱离楼栋独立存在。
- 不引入统一的通用空间节点模型。
- 不改变默认项目和默认楼栋的组织初始化逻辑。
- 不提供级联删除或强制删除。
- 不在本期实现地图地址解析、行政区自动补全或坐标去重。
- 不重构与本次空间归属无关的房源租赁业务。

## 方案选择

### 方案一：继续强制绑定小区并使用默认小区

改动最小，但依赖占位数据，不能真实表达独立楼栋，未采用。

### 方案二：楼栋可选绑定小区，独立楼栋使用名称和地址区分

小区作为可选归类，楼栋直接归属组织。该方案能够覆盖真实业务场景，并保留现有房源、带看和租约结构，改造范围可控，采用此方案。

### 方案三：引入统一空间节点模型

将小区、园区和楼栋抽象为可嵌套节点，扩展性较强，但需要重构现有模型、接口和前端信息架构，超出当前需求，未采用。

## 领域模型

```text
Organization
├── Estate
│   ├── address：小区或项目整体地址
│   └── Building
│       ├── address：具体楼栋地址
│       └── House
└── Building（estate = NULL）
    ├── address：独立楼栋地址
    └── House
```

### Building

- `organization` 保持必填，作为楼栋及其房源的租户边界。
- `estate` 调整为可空外键，仍使用 `on_delete=PROTECT`。
- `address` 始终保留。独立楼栋创建、解绑小区时要求地址非空。
- 绑定小区时，必须保证小区和楼栋属于同一组织。
- 楼栋绑定小区、迁移到其他小区或解除小区归属时，其下房源整体跟随楼栋，无需逐条更新房源。

### House

- `building` 继续保持必填。
- `organization` 属性改为通过 `building.organization` 获取。
- 房号唯一性继续保持为 `building + room_number`。
- 带看记录、租约和房东关系继续关联房源，不改变现有领域关系。

## 地址与唯一性

### 绑定小区的楼栋

同一小区内楼栋名称唯一：

```text
estate + name
```

### 独立楼栋

同一组织内，独立楼栋按名称和地址组合唯一：

```text
organization + name + address
```

不同地址允许出现同名独立楼栋。独立楼栋地址必须填写，避免空地址使唯一规则退化或产生无法区分的楼栋。

名称和地址保存前执行基础规范化，并将规范化结果直接写回 `name` 和 `address` 字段，使数据库条件唯一约束与业务校验使用相同的持久化值：

- 去除首尾空白。
- 将连续空白合并为单个空格。
- 不在本期执行地图标准地址转换或复杂语义归一化。

若绑定、解绑或修改名称和地址后触发唯一冲突，接口返回字段级业务错误，不向客户端暴露数据库异常。已绑定楼栋地址为空时，解除小区绑定必须失败并提示先补充楼栋地址。

## 组织隔离与查询调整

所有房源业务统一通过楼栋判断组织归属：

```python
house.building.organization
```

现有依赖小区的组织过滤链需要调整：

```text
building__estate__organization       -> building__organization
house__building__estate__organization -> house__building__organization
```

调整范围覆盖：

- 房源列表、详情、创建和更新权限校验。
- 房东名下房源和租约查询。
- 带看记录查询与一致性校验。
- 租约查询与一致性校验。
- Django admin 的组织筛选。

小区搜索和筛选仍可通过 `estate` 关系完成，但不得再作为租户边界。独立楼栋必须正常出现在楼栋、房源、房东、带看和租约等查询中。

## API 契约

### 楼栋输入输出

楼栋创建、更新和输出中的小区字段调整为可空：

```text
estate_id: int | null
estate: EstateSummary | null
```

PATCH 更新语义：

- 未传 `estate_id`：保持当前归属不变。
- 传具体 ID：绑定或迁移到指定小区。
- 传 `null`：解除小区归属。

创建独立楼栋或解除小区归属时，楼栋地址必须非空。绑定具体小区时必须校验其属于当前组织。

### 显示标签

统一使用可空小区兼容的显示规则：

```text
绑定小区：星河湾 / 1栋 / 101
独立楼栋：1栋 · 科技路10号 / 101
```

楼栋选择器至少展示楼栋名称和地址，避免不同地址下的同名独立楼栋难以区分。

## 关联资源检查接口

新增两个删除检查接口：

```http
GET /api/house/estates/{estate_id}/delete-check/
GET /api/house/buildings/{building_id}/delete-check/
```

小区检查关联楼栋，楼栋检查关联房源。统一响应示例：

```json
{
  "can_delete": false,
  "resources": [
    {
      "type": "building",
      "label": "关联楼栋",
      "count": 3,
      "items": [
        { "id": 11, "label": "1栋 · 科技路10号" },
        { "id": 12, "label": "2栋 · 科技路10号" }
      ],
      "truncated": true,
      "target": {
        "path": "/property-rental/estates",
        "query": {
          "view": "buildings",
          "estate_id": 10
        }
      }
    }
  ]
}
```

`items` 仅返回前 5 条资源预览；`count` 返回完整数量；资源超过预览上限时 `truncated=true`。完整资源通过 `target` 指定的页面和筛选参数查看。

楼栋检查使用相同结构，资源类型为 `house`，跳转目标为房源列表并携带 `building_id`。

## 删除接口与并发处理

新增删除接口：

```http
DELETE /api/house/estates/{estate_id}/
DELETE /api/house/buildings/{building_id}/
```

删除规则：

- 小区没有关联楼栋时才能删除。
- 楼栋没有关联房源时才能删除。
- 不提供级联删除和强制删除。
- 数据库外键继续使用 `PROTECT`，作为业务检查之外的最后保护。

资源检查仅服务于前端体验，DELETE 是最终裁决。删除接口在事务内重新检查关联资源，处理“检查通过后其他用户新增关联资源”的竞态。

存在关联资源时返回 `409 Conflict`，并携带最新资源信息：

```json
{
  "code": 409,
  "error": "RESOURCE_IN_USE",
  "message": "当前小区已关联楼栋，不能删除。",
  "data": {
    "can_delete": false,
    "resources": []
  },
  "timestamp": 0,
  "traceId": ""
}
```

其中 `data.resources` 与删除检查接口采用相同结构；`timestamp` 使用实际响应时间。目标对象已经被其他用户删除时返回 `404`。

## 管理端交互

### 楼栋表单

- 所属小区改为可清空选择。
- 选择小区时展示小区整体地址，楼栋地址字段仍独立填写。
- 未选择小区时，将楼栋地址标记为必填。
- 从小区详情进入新建楼栋时，默认带入当前小区。
- 从房源建档中快速新建楼栋时，允许直接创建独立楼栋。
- 所有楼栋继续使用同一个楼栋列表，不增加“小区楼栋/非小区楼栋”分类、筛选或专用 URL 参数。
- 楼栋列表按现有搜索和小区条件查询；没有绑定小区的楼栋正常出现在全部楼栋结果中，小区列统一显示 `-`。
- 小区详情存在关联楼栋时显示“关联楼栋”卡片并列出关联楼栋；没有关联楼栋时不显示该卡片。
- 楼栋详情已绑定小区时显示“所属小区”信息；没有绑定小区时不显示该信息区域，不额外展示“非小区楼栋”标签。

### 删除流程

```text
点击删除
  -> 调用 delete-check
  -> 有关联资源：显示禁止删除弹窗和资源预览
  -> 无关联资源：显示二次确认
  -> 用户确认后调用 DELETE
  -> DELETE 成功：关闭弹窗并刷新列表
  -> DELETE 返回 409：原地切换成禁止删除状态并展示最新资源
```

禁止删除弹窗：

- 明确展示关联资源数量。
- 展示前 5 条资源名称。
- 提供“查看全部关联楼栋”或“查看全部关联房源”按钮。
- 不显示强制删除入口。
- 保留关闭按钮。

DELETE 返回 `409` 时，不显示普通“删除失败”消息。当前确认弹窗直接切换为禁止删除状态，使用响应中的最新资源信息；确认删除按钮移除。关闭弹窗后刷新当前列表。

### 快速跳转

楼栋列表支持 URL 参数：

```text
/property-rental/estates?view=buildings&estate_id=10
```

房源列表支持 URL 参数：

```text
/property-rental/houses?building_id=11
```

通过删除保护弹窗查看关联楼栋时，仍使用现有 `estate_id` 精确筛选。页面必须明确展示当前小区筛选条件，并允许用户清除筛选，避免跳转后只显示部分数据却缺少解释。

## 小程序与生成接口

后端 OpenAPI 变化后，重新生成管理端和小程序/H5 的 API 类型。所有 `estate_id` 和 `estate` 消费位置必须兼容空值。若小程序当前没有楼栋管理入口，也必须确保生成类型和现有页面通过类型检查。

## 数据迁移

现有楼栋全部保留当前小区绑定关系。迁移只完成以下结构调整：

- 将 `Building.estate` 改为可空。
- 替换楼栋唯一约束。
- 使用数据迁移对现有楼栋名称和地址执行相同的基础规范化；迁移前先检查规范化后是否产生冲突，发现冲突时中止迁移并输出待治理记录，不自动合并数据。

本次迁移不自动解绑任何楼栋，也不改变“默认项目 + 默认楼栋”的初始化数据和设置值。

## 错误处理

- 独立楼栋缺少地址：返回楼栋地址字段错误。
- 小区和楼栋跨组织绑定：按资源不存在返回 `404`，避免泄露其他组织资源。
- 唯一性冲突：返回名称或地址相关的业务错误。
- 删除存在关联资源：返回 `409 RESOURCE_IN_USE` 和最新资源摘要。
- 删除目标不存在：返回 `404`。
- 数据库 `PROTECT` 意外触发：转换为与资源占用一致的 `409` 响应，不返回服务端异常页面。

## 测试策略

### 后端

- 创建绑定小区的楼栋。
- 创建不绑定小区且地址完整的楼栋。
- 独立楼栋缺少地址时创建失败。
- 独立楼栋在同组织内名称和地址重复时失败。
- 不同地址允许创建同名独立楼栋。
- 楼栋绑定、解绑和跨小区迁移。
- 无地址楼栋不能解除小区绑定。
- 跨组织绑定小区被拒绝。
- 独立楼栋房源正常出现在房源、房东、带看和租约查询中。
- 删除检查在无关联资源时返回 `can_delete=true`。
- 小区有关联楼栋、楼栋有关联房源时返回正确资源摘要和跳转目标。
- 无关联资源时 DELETE 成功。
- DELETE 在检查后新增关联资源时返回 `409` 和最新资源摘要。
- 数据库 `PROTECT` 继续有效。

### 管理端

- 新建楼栋时可以不选小区，但独立楼栋必须填写地址。
- 解绑小区后正确展示独立楼栋。
- 楼栋列表不出现楼栋类型分类或筛选，绑定和未绑定小区的楼栋均可正常展示。
- 小区详情仅在存在关联楼栋时显示关联楼栋卡片。
- 楼栋详情仅在已绑定小区时显示所属小区信息。
- 独立楼栋标签不访问空的 `estate`。
- 删除操作先调用检查接口。
- 有关联资源时不调用 DELETE。
- 无关联资源时显示二次确认并调用 DELETE。
- DELETE 返回 `409` 时，确认弹窗原地切换为关联资源提示。
- 查看关联楼栋和房源时跳转到正确筛选页面。
- URL 筛选在页面上可见且可清除。
- 管理端和小程序生成类型通过类型检查。

## 验收标准

- 用户能够创建、编辑、查询和使用不绑定小区的独立楼栋。
- 独立楼栋进入房源、房东、带看和租约业务链后，与绑定小区的楼栋具有相同的数据可见性和操作能力。
- 独立楼栋之间可以同名，但同一组织下名称和地址组合不得重复。
- 房源仍必须绑定楼栋。
- 删除小区或楼栋前能够查看关联资源；存在关联资源时无法删除，并能快速跳转到已筛选资源列表。
- 删除检查与实际删除之间出现新关联资源时，DELETE 返回最新占用信息，前端原地切换为禁止删除状态。
- 所有租户隔离判断以楼栋组织为边界，不因小区为空而遗漏或越权访问数据。
