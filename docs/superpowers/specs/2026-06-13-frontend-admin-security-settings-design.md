# frontend_admin 安全设置页真实能力接入设计

## 背景

`frontend_admin` 的“账户设置 > 安全设置”当前仍是模板占位实现，列表中的“账户密码、密保手机、密保问题、备用邮箱、MFA 设备”均为静态文案和假按钮，没有接入项目现有的认证能力，也没有和 `django-allauth` 的 headless browser API 形成真实闭环。

本项目近期已经将管理端登录切换到标准 `allauth` 接口，并且后端已经具备以下基础能力：

- 基于 `allauth` 的浏览器端登录态与账户管理能力
- 基于 `allauth` 的邮箱验证与主邮箱切换能力
- 基于 `allauth` 的 MFA / TOTP / recovery codes 能力
- 当前用户资料读取能力
- 项目内已有的手机号标准化、占用检查与短信验证码能力

这意味着本次最合理的方向不是新造一套安全体系，而是让管理端安全设置页成为现有能力的真实前端入口。

## 目标

将 `frontend_admin` 的“安全设置”页改造为真实可用的账户安全页，完成以下闭环：

1. 使用真实接口展示当前用户的安全状态。
2. 去掉无后端能力支撑的“密保问题”项。
3. 提供可用的修改密码流程。
4. 提供可用的修改手机号流程，采用“验证新手机号验证码”的策略。
5. 提供可用的修改邮箱流程，基于 `allauth` 的邮箱管理与验证闭环。
6. 提供完整的 MFA 管理流程，至少覆盖状态展示、TOTP 绑定、恢复码状态、解绑能力。

## 非目标

本次设计明确不包含以下范围：

- 不改造“账号绑定”页签。
- 不改造“新消息通知”页签。
- 不改造“基本设置”页签。
- 不引入“密保问题”替代方案。
- 不承诺本期完成完整 passkey / WebAuthn 设备管理，除非实现前确认 `allauth` browser 端点已完整可用。
- 不新增独立的认证体系或绕开 `allauth` 的密码、邮箱、MFA 规则。
- 不做密码强度实时评分等增强功能。

## 用户体验定义

新版“安全设置”页仍保持列表式浏览体验，但每一行都对应真实状态和真实动作，而不是模板占位。

页面包含四项：

1. 账户密码
2. 密保手机
3. 邮箱地址
4. MFA 设备

每项展示三类信息：

- 标题
- 当前状态摘要
- 右侧操作入口

所有真实修改流程都在弹窗中完成，不在列表行内直接展开，避免误操作并降低页面复杂度。

## 页面范围

本次仅调整 `frontend_admin/src/pages/account/settings/components/security.tsx` 及其关联 service / types / tests。

页面最终展示项定义如下。

### 1. 账户密码

- 标题：`账户密码`
- 状态摘要：`已设置登录密码`
- 操作：`修改`

不再展示“当前密码强度：强”这类伪状态文案，因为当前后端并不提供真实的已存密码强度评估能力。

### 2. 密保手机

- 标题：`密保手机`
- 状态摘要：展示当前手机号脱敏结果；未绑定时显示 `未绑定手机号`
- 操作：`修改` 或 `绑定`

### 3. 邮箱地址

- 标题：`邮箱地址`
- 状态摘要：展示当前主邮箱脱敏结果；未设置时显示 `未绑定邮箱`
- 操作：`修改` 或 `绑定`

文案上不继续强调“备用邮箱”，因为本次前端只突出当前主邮箱和待验证的新邮箱，不做长期多邮箱管理中心的产品表达。

### 4. MFA 设备

- 标题：`MFA 设备`
- 状态摘要：根据真实认证器状态展示 `未启用`、`已启用 TOTP`、`已启用 TOTP 和恢复码` 等文案
- 操作：`绑定` 或 `管理`

## 总体架构

本次采用“前端优先直连 `allauth`，仅对缺失能力补最小自定义接口”的方案。

具体原则如下：

- 密码变更：优先复用 `allauth` 标准接口
- 邮箱管理：优先复用 `allauth` 标准接口
- MFA 管理：优先复用 `allauth` 标准接口；如缺少自助解绑能力，再补最小接口
- 手机号变更：补一组当前登录用户自助接口，复用项目现有短信与手机号服务逻辑

这样可以最大程度沿用项目现有认证边界，避免管理端和主站分别维护两套规则。

## 前端设计

### 状态来源

安全设置页的状态由两类数据组合而成：

1. `GET /api/users/me/`
2. `allauth` browser 账户管理接口

建议前端进入安全设置页时并行请求：

- 当前用户资料
- `GET /api/allauth/browser/v1/account/authenticators`

如果邮箱列表展示需要更细的状态，可额外请求邮箱管理接口。

### 列表与弹窗边界

列表本身只负责展示状态和打开对应弹窗，不在页面顶层维护复杂表单。

建议拆成四个独立对话框组件：

- `PasswordChangeModal`
- `PhoneChangeModal`
- `EmailChangeModal`
- `MfaManageModal`

每个对话框只负责一套流程，service 层负责接口调用与错误归一化。

### 脱敏规则

建议统一在前端做展示脱敏：

- 手机号：`138****8293`
- 邮箱：`ant***@sign.com` 或同等可读格式

若字段为空，展示 `未绑定` 类文案。

### 错误映射

管理端 service 层需要把 `allauth` 的错误结构和项目自定义接口错误结构统一成前端可消费格式，避免组件内部散落条件判断。

统一处理的错误类型至少包括：

- 字段校验错误
- 验证码错误或过期
- 邮箱或手机号已被占用
- 认证器状态冲突
- 通用提交失败

## 功能流程设计

### 修改密码

前端弹窗字段：

- 当前密码
- 新密码
- 确认新密码

交互规则：

1. 用户点击“修改”打开弹窗。
2. 提交时调用 `allauth` 的密码变更接口。
3. 成功后关闭弹窗并提示“密码已更新”。
4. 失败时优先显示字段错误，其次显示接口通用错误。

本次不额外设计密码复杂度评分器，直接遵循 Django / `allauth` 的密码校验结果。

### 修改手机号

用户已确认采用“只验证新手机号验证码，不要求当前密码”的策略。

前端弹窗字段建议为：

- 新手机号
- 验证码

并包含“发送验证码”按钮与倒计时。

交互规则：

1. 用户输入新手机号。
2. 点击“发送验证码”。
3. 前端调用手机号验证码发送接口。
4. 用户输入验证码并确认。
5. 前端调用手机号变更确认接口。
6. 成功后刷新 `me` 信息并更新列表展示。

### 修改邮箱

修改邮箱不应直接 `PATCH user.email`，而应遵循 `allauth` 的邮箱管理模型。

推荐交互：

1. 用户输入新邮箱。
2. 前端调用 `allauth` 新增邮箱接口。
3. 后端发送验证邮件。
4. 页面提示“验证邮件已发送”。
5. 用户完成邮箱验证后，前端将新邮箱设为 primary。
6. 页面刷新为新的主邮箱状态。

本次前端只需要突出两类信息：

- 当前主邮箱
- 待验证的新邮箱（如果存在）

不需要把 `allauth` 的全量邮箱管理能力完整做成复杂列表。

### MFA 管理

MFA 设备页签这次定义为完整管理，而非展示态。

本期至少覆盖以下能力：

1. 查看当前已启用的认证器
2. 启用 TOTP
3. 展示恢复码状态
4. 解绑已启用的 MFA 认证器

推荐流程：

1. 打开弹窗后请求 `GET /api/allauth/browser/v1/account/authenticators`
2. 如果未启用 TOTP，则提供“开始绑定”入口
3. 点击后拉取 TOTP 初始化信息，展示二维码和手动密钥
4. 用户输入 6 位验证码确认绑定
5. 成功后刷新认证器状态
6. 如果已启用恢复码，则显示“已生成恢复码”状态
7. 如果支持重置或重新生成恢复码，则在实现阶段确认端点后纳入

关于 passkey / WebAuthn：

- 配置上项目已声明支持
- 但仓库中暂未确认到管理端现成接入与测试闭环
- 因此本设计只把它视作能力探测项，不把它作为本期必须交付项

## 后端设计

### 已有能力直接复用

本次优先复用以下既有后端能力：

- `allauth` browser 密码变更能力
- `allauth` 邮箱新增、验证、设为主邮箱能力
- `allauth` MFA 认证器列表与 TOTP 激活能力
- 当前用户资料读取 `GET /api/users/me/`

### 新增手机号自助变更接口

建议补充一组当前登录用户自助接口：

- `POST /api/users/me/phone/change/request-code/`
- `POST /api/users/me/phone/change/confirm/`

职责定义：

`request-code`

- 校验手机号格式
- 校验手机号是否可用
- 发送验证码
- 返回成功状态与必要的节流信息

`confirm`

- 校验验证码
- 将手机号写入当前用户
- 标记 `phone_verified=True`
- 返回更新后的手机号信息

实现上应尽量复用项目已有的手机号标准化、占用冲突处理和短信发送逻辑，而不是新写一套手机号服务。

### 可能新增的 MFA 自助管理接口

如果实现阶段确认 `allauth` 缺少“当前用户自助删除某类 authenticator”的稳定 browser API，则建议补最小自助接口，例如：

- `DELETE /api/users/me/mfa/authenticators/{type}/`

职责仅限于当前登录用户删除自己的某类 MFA 认证器，不承担后台代管能力。

本接口和管理员已有的 `reset-mfa` 不同，不能直接复用管理员语义。

## 数据流

### 页面初始化

1. 用户进入“安全设置”页
2. 前端并行请求当前用户资料与 MFA 认证器列表
3. 前端计算手机、邮箱、MFA 摘要文案
4. 页面渲染四个真实安全项

### 手机号修改

1. 打开手机号弹窗
2. 输入新手机号
3. 请求发送验证码
4. 输入验证码并提交
5. 后端校验并写入新手机号
6. 前端刷新用户资料并关闭弹窗

### 邮箱修改

1. 打开邮箱弹窗
2. 输入新邮箱
3. 调用 `allauth` 新增邮箱接口
4. 邮件发送后提示用户完成验证
5. 验证完成后将该邮箱设为主邮箱
6. 刷新页面摘要

### TOTP 绑定

1. 打开 MFA 管理弹窗
2. 请求认证器列表
3. 若未启用 TOTP，则请求初始化信息
4. 展示二维码与密钥
5. 用户输入动态码确认
6. 成功后刷新认证器状态与恢复码状态

## 错误处理

所有安全相关动作都必须保留明确、可理解的业务反馈。

前端至少需要覆盖以下错误场景：

- 手机号已被占用
- 手机验证码错误
- 手机验证码过期
- 邮箱已被占用
- 邮箱验证未完成时不可设为主邮箱
- TOTP 已启用时重复启用
- 尝试解绑不存在的认证器
- 通用网络或服务异常

交互要求：

- 字段错误显示在字段附近
- 通用错误显示在弹窗顶部或提交区
- 提交失败后保留当前输入内容
- 验证码请求提供冷却倒计时和重复点击保护

## 测试设计

### 前端测试

建议覆盖以下内容：

1. 安全设置页根据真实数据展示四个安全项。
2. `密保问题` 已被移除。
3. 手机号和邮箱摘要按真实数据与空值状态切换。
4. 点击各项操作后打开对应弹窗。
5. service 层正确调用 `allauth` 接口与自定义手机号接口。
6. 修改密码成功后提示正确。
7. 手机号验证码流程成功后列表刷新。
8. 邮箱新增并设为主邮箱的流程能正确触发接口。
9. TOTP 绑定成功后页面状态刷新。

### 后端测试

建议覆盖以下内容：

1. 手机号验证码发送接口：未登录、格式错误、号码冲突、发送成功。
2. 手机号确认接口：验证码错误、验证码过期、确认成功、更新已验证状态。
3. 若新增自助 MFA 删除接口：未登录、认证器不存在、删除成功、删除后状态更新。

测试位置遵循仓库约定，放在 `tests/accounts/` 下。

## 实施顺序建议

1. 明确并验证管理端将使用的 `allauth` 密码、邮箱、MFA 端点
2. 补手机号自助变更接口与后端测试
3. 如有需要，补 MFA 自助解绑接口与后端测试
4. 改造 `frontend_admin` 安全设置 service / types
5. 改造安全设置列表与四个弹窗流程
6. 补前端测试
7. 做一次管理端联调，确认状态刷新与错误提示完整可用

## 风险与应对

### 风险 1：`allauth` 某些 browser 端点语义与预期不完全一致

应对：

- 实现前先用测试或本地调用确认具体请求方法与响应结构
- 前端 service 层做统一适配，不把端点细节泄露到组件中

### 风险 2：手机号变更若绕过现有逻辑，可能造成数据口径不一致

应对：

- 强制复用现有手机号标准化、占用检查和短信服务逻辑
- 不直接在视图函数中手写字段覆盖逻辑

### 风险 3：MFA 自助解绑若语义设计过大，容易和管理员接口混淆

应对：

- 仅补当前登录用户删除自己的认证器接口
- 不引入管理员代管语义

### 风险 4：邮箱流程是异步验证闭环，用户不一定在当前会话完成

应对：

- UI 明确展示“待验证邮箱”状态
- 页面每次进入都以服务端真实邮箱状态为准

## 验收标准

满足以下条件即可认为本次改造完成：

1. “安全设置”页不再显示“密保问题”。
2. `账户密码 / 密保手机 / 邮箱地址 / MFA 设备` 四项均展示真实状态。
3. 修改密码流程可真实提交并正确反馈错误。
4. 修改手机号流程可完成验证码发送、确认和状态刷新。
5. 修改邮箱流程可完成新增、验证后设主邮箱的闭环。
6. MFA 流程至少可完成 TOTP 绑定与真实状态展示。
7. 若本期纳入解绑，则解绑后状态能正确刷新。
8. 前后端测试覆盖新增行为，且不引入新的模板占位数据。
