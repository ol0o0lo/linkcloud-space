# 房表空置同步设计

**日期：** 2026-07-18
**状态：** 设计已确认，待用户复核

## 背景

日常运营会收到按楼栋分组的空房文本，例如：

```text
下元岗东街三巷1号
102复式大单间1380
202一房1750光线好
401一房1800无遮挡

上元岗西街50号
103一房 1450
104 单间 1250
```

每段第一行是楼栋地址，后续行是当前空置房源。系统需要识别楼栋、房号、房型、租金和描述标签，并将文本视为该楼栋当次的空置清单：清单内房源改为空置，清单外已有房源改为已租。

旧版 Uhome 使用“文本识别、批量查询、前端比对、批量更新”三个接口完成流程，并支持地址中英文数字变体。旧实现的问题是接口和解析规则分散、前端需要拼装 `houseNumSame`、`needAdd` 等过程状态、同步缺少原子性，且楼栋不存在时不能直接完成创建。本设计保留“预览后确认”的业务流程，收敛为一个双模式接口，并将全部差异计算放回后端。

## 目标

- 识别按空行分组的房表粘贴文本。
- 确定性匹配当前组织的已有楼栋，无法匹配时自动创建独立楼栋。
- 在预览中展示逐行解析、楼栋匹配和房源变更计划。
- 用户确认后同步创建或更新房源，并按完整清单更新整栋房态。
- 同步过程保持组织隔离、并发校验和整批事务原子性。
- 将租约与房态解耦，使房表同步可以在保留生效租约的同时强制修改房态。
- 通过组织设置控制清单外特殊房态是否强制改为已租。

## 非目标

- 不实现管理端粘贴页面；本次只交付后端接口、配置、迁移和后端测试。
- 不实现房东负责人、楼栋负责人、员工工作范围或相关管理页面。
- 不实现通用审计日志或房表导入历史。
- 不自动终止、创建或修改租约。
- 不使用地图地理编码或模糊地址算法自动合并楼栋。
- 不修改房东、媒体、发布资料或其他未出现在房表中的房源信息。

## 房态与租约解耦

当前 `Lease` 保存、删除或换房时会通过信号调用 `recalculate_house_status()`，按照生效租约自动修改 `House.status`。该行为与“租约是弱关系、房态独立维护”的业务定义冲突，本次移除：

- 租约生效、终止、删除和换房不再自动修改房态。
- 房态继续由房源编辑接口、房表同步等明确业务动作维护。
- 清单中出现的房源即使存在生效租约，也可以强制改为 `vacant`；租约保持原状。
- 移除仅为租约重算房态服务的信号和服务代码，并调整对应测试。

## 组织配置

新增组织级设置：

```text
property_rental.vacancy_sync_force_rented
```

- 类型为布尔值，默认 `false`。
- `false`：清单外的 `vacant` 改为 `rented`，已有 `rented` 保持不变，`renovating` 和 `locked` 保留。
- `true`：清单外所有启用房源统一改为 `rented`，包括 `renovating` 和 `locked`。
- 清单内房源始终改为 `vacant`，不受该配置影响。
- 停用房源不参与清单外同步，也不会被自动恢复。

设置继续使用现有 `DefaultSetting` / `OrganizationSetting` 体系，不增加新的配置模型。

## 单接口双模式

统一接口：

```http
POST /api/house/vacancy-sync/
```

请求结构：

```json
{
  "mode": "preview",
  "raw_text": "楼栋与房源文本",
  "building_overrides": [],
  "ignored_lines": [],
  "plan_hash": null
}
```

字段含义：

- `mode`：`preview` 或 `apply`。
- `raw_text`：原始粘贴文本，必填，最大 50KB。
- `building_overrides`：楼栋匹配歧义时由调用方按段落指定现有楼栋 ID。
- `ignored_lines`：用户明确忽略的错误行号。
- `plan_hash`：`apply` 模式必填，必须等于相同输入在 `preview` 模式下返回的值。

`preview` 只读，不写数据库；`apply` 在事务中重新执行相同解析和计划计算，通过 `plan_hash` 校验后提交。接口要求已选择组织，所有楼栋覆盖值必须属于当前组织。单次最多处理 1000 条有效房源。

## 文本解析

### 分段与行号

- 统一处理 `\n`、`\r\n`、首尾空白和仅含空格的空行。
- 两段楼栋数据由一个或多个空行分隔。
- 每段第一条非空行是楼栋地址，后续非空行是房源行。
- 响应保留原始全局行号与原始文本，便于页面定位错误。
- 同一地址重复出现为段落级错误，不隐式合并两个段落。

### 房源行

房源行识别以下信息：

- 房号：从行首到第一个可识别房型表达之间的非空标识；去除其内部空格后保存。这样 `202一房1750` 识别为房号 `202`，`2021房1厅1750` 也通过 `1房1厅` 的边界识别为房号 `202`。
- 房型：房号之后、租金之前的文本。
- 租金：房型之后的数字金额。
- 描述：房型中的修饰词以及租金后的剩余文本。

确认的房型规则：

- `单间`、`大单间`、`超级大单间`：1 房 0 厅。
- `一房`：1 房 1 厅。
- `二房`、`三房`等未写厅数的表达：对应房数，默认 1 厅。
- 明确写出“X房Y厅”时，以文本数量为准。
- 支持常用中文数字、财务中文数字和阿拉伯数字。
- 卫生间数量不在房表中推断，不覆盖已有值；新房源保持为空。

标签规则：

- `复式`保存为`复式`。
- `大单间`保存为`大单间`。
- `超级大单间`保存为`超级大单间`，不额外拆成`大单间`。
- `光线好`规范为`采光好`。
- `无遮挡`保存为`无遮挡`。
- 识别出的标签按顺序去重后与已有人工标签合并，不删除原有标签。

以下情况返回带行号的错误：

- 缺少房号、租金或可识别房型。
- 同一楼栋段落内重复房号。
- 房号、租金或房厅数量超出字段允许范围。
- 行文本无法完整解释为房源信息。

例如 `一房1750无遮挡` 缺少房号，必须在预览中报错。错误行默认阻止同步；用户可以修改原始文本，或将行号加入 `ignored_lines` 后重新预览。被忽略的错误行不参与任何房态计算。

## 楼栋匹配与创建

楼栋匹配只在当前组织内执行，按以下确定性顺序处理：

1. 规范化空白和常见标点后，地址完全相同。
2. 规范化后的楼栋名称完全相同。
3. 地址或名称的中文数字、阿拉伯数字变体完全相同，例如“三巷1号”与“3巷一号”。

匹配结果：

- 唯一匹配：自动关联现有楼栋。
- 多个匹配：返回候选楼栋并阻止同步，调用方通过 `building_overrides` 指定其中一个。
- 无匹配：计划创建独立楼栋，不绑定小区。

新建楼栋只要求输入地址：

- `name`自动使用规范化后的地址。
- `address`保存规范化后的地址。
- `floors`从最大有效房号推断：取房号开头连续数字，长度至少为 3 时去掉末两位作为楼层，例如 `102 → 1`、`602 → 6`、`1001 → 10`；其余情况不推断并使用内部默认值 `1`。
- 不要求用户补充名称、楼层或小区。

不使用包含匹配、编辑距离或其他模糊规则自动关联，以避免相邻门牌被错误合并。

## 预览计划

`preview` 响应包含：

- `can_apply`：是否满足同步条件。
- `plan_hash`：当前输入、覆盖选择、忽略行、组织配置和数据库目标状态的摘要。
- `summary`：楼栋、有效行、错误行、新建、更新、改空置、改已租和保留特殊状态的数量。
- `blocks`：每个楼栋段落的地址、匹配状态、候选楼栋、逐行解析和变更计划。
- `errors`：跨段落或请求级错误。

每栋楼的变更计划至少区分：

- `create_building`
- `create_houses`
- `update_houses`
- `mark_vacant`
- `mark_rented`
- `preserve_special_status`
- `inactive_conflicts`

若清单中的房号命中停用房源，返回 `inactive_conflicts` 并阻止同步；系统不自动恢复停用房源，也不另建同房号记录。

## 确认同步

`apply` 必须提交与预览相同的 `raw_text`、`building_overrides` 和 `ignored_lines`，并携带 `plan_hash`。服务端在一个 `transaction.atomic()` 中：

1. 重新解析文本并校验错误行。
2. 锁定计划涉及的已有楼栋和房源。
3. 读取当前组织配置并重新计算完整计划。
4. 当前计划摘要与 `plan_hash` 不一致时返回 `409 Conflict`，不写数据，要求重新预览。
5. 创建计划中的新楼栋。
6. 按 `(building, room_number)` 创建或更新清单内房源。
7. 更新清单外房源状态。
8. 返回实际写入结果。

清单内房源写入规则：

- 新房源写入房号、推断楼层、租金、房数、厅数、标签和 `vacant` 状态。
- 新房源使用模型默认的启用状态和草稿发布状态，房东为空。
- 已有房源更新租金、可识别房厅数量、推断楼层和合并标签，并强制设为 `vacant`。
- 不修改房东、面积、朝向、装修、图片、视频、公开描述、内部备注、扩展字段或发布状态。

清单外房源写入规则：

- 只处理当前楼栋的启用房源。
- 默认将 `vacant` 改为 `rented`，`rented`保持不变，`renovating`和`locked`保留。
- 组织配置开启时，将所有清单外启用房源改为`rented`。
- 停用房源始终忽略。

任一楼栋或房源写入失败时整批回滚，不返回部分成功。成功响应返回各楼栋创建和更新的对象 ID，以及各类实际变更数量。

## `plan_hash` 与并发

`plan_hash` 至少覆盖：

- 当前组织 ID。
- 规范化后的解析结果。
- `building_overrides`和`ignored_lines`。
- 组织配置值。
- 目标楼栋 ID、更新时间及相关房源 ID、房号、状态、更新时间和将被更新的字段值。

哈希只用于发现预览后数据发生变化，不作为授权凭据。`apply`仍需重新执行组织隔离、楼栋覆盖和数据校验。预览后若其他员工修改了相关楼栋、房源或配置，确认同步返回 `409`。

## 错误处理

- `400 Bad Request`：模式、请求结构、文本大小或数量限制错误。
- `404 Not Found`：楼栋覆盖值不存在于当前组织，对外不暴露跨组织对象。
- `409 Conflict`：`plan_hash`缺失、过期或当前数据已变化。
- `422 Unprocessable Entity`：文本解析错误、重复房号、楼栋匹配歧义、停用房源冲突或其他可修正业务错误。
- `500 Internal Server Error`：不可预期写入失败；事务完整回滚。

响应中的业务错误应携带稳定错误代码、行号或段落编号和中文说明，前端无需解析自由文本来定位问题。

## 代码边界

- `apps/house/vacancy_sync.py`：纯文本解析、地址变体、楼栋匹配、计划计算、哈希和事务同步。
- `apps/house/schemas.py`：双模式请求、逐行结果、候选楼栋、变更计划和响应 Schema。
- `apps/house/api.py`：HTTP 入口、组织选择和错误映射。
- `apps/house/services.py`及信号：移除租约房态重算职责；其余房源服务保持不变。
- `apps/settings`：注册默认配置并沿用组织覆盖读取逻辑。

解析器应保持为不访问数据库的纯函数；楼栋匹配和计划计算接收明确的组织与查询数据；写入集中在单一事务函数中。API 层不包含正则表达式或逐房源同步循环。

## 测试与验收

### 解析测试

- 完整解析用户提供的两栋示例。
- `一房1750无遮挡`返回缺少房号错误。
- 空格、多个空行、`\r\n`、首尾空白和描述位于租金前后的变体。
- 单间、大单间、超级大单间、一房、多房多厅和中文数字。
- 复式、采光好、无遮挡等标签规范化与去重。
- 缺租金、未知房型、重复房号和超限数据。

### 预览测试

- 地址、名称和中英文数字变体的唯一匹配。
- 匹配不到时返回新建楼栋计划。
- 多个候选时阻止同步，合法覆盖后可继续。
- 跨组织覆盖返回 404。
- 新建、更新、改空置、改已租和保留特殊房态的计划统计。
- 错误行被修正或明确忽略前 `can_apply=false`。
- 停用房源冲突。

### 同步测试

- 创建独立楼栋及房源。
- 已有房源只更新允许字段，并合并而不清空人工标签和资料。
- 清单内房源存在生效租约时仍改为空置，租约不变。
- 租约后续生效、终止、删除或换房不再自动修改房态。
- 默认配置保留装修中/封存，开启配置后强制改为已租。
- 清单外停用房源不变。
- 预览后相关数据或配置变化时返回 409。
- 任一写入失败时楼栋与房源全部回滚。
- 组织隔离、50KB 文本限制和 1000 条房源限制。

### 验收标准

- 一段真实房表文本可以通过同一接口先预览、再确认同步。
- 解析错误能准确定位到原始行，且不会产生部分写入。
- 楼栋不存在时无需补充额外信息即可创建并同步房源。
- 已有楼栋按完整空置清单准确更新房态和房源资料。
- 生效租约不阻止房源改为空置，也不会在之后自动覆盖房态。
- 特殊房态是否强制改已租由组织配置决定，默认安全保留。
- 全部相关后端测试通过，OpenAPI Schema 可正常生成。
