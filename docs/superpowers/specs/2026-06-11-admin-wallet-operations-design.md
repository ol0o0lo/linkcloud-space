# 钱包运营后台设计（一期）

日期：2026-06-11  
状态：已评审（待实现计划）

## 1. 背景与目标

当前钱包基础后端已经具备账户、流水、提现申请、审核、调账、代付、回调和重试能力，但 `frontend_admin` 运营后台尚未提供对应页面与操作入口，导致运营无法在后台完成实际管理动作。

本期目标是在 `frontend_admin` 中补齐最小可用的钱包运营后台闭环，使超级管理员能够完成以下工作：

- 查看用户钱包账户与余额概况
- 查看指定用户钱包流水
- 对指定用户执行管理员调账
- 查看提现申请列表
- 审核提现申请（通过 / 驳回）
- 对已通过提现发起微信提现
- 对失败提现执行重试

## 2. 范围与非范围

### 2.1 范围内

- `frontend_admin` 增加钱包运营菜单
- 钱包账户列表页
- 提现申请列表页
- 指定用户流水抽屉或详情区
- 管理员调账弹窗
- 提现审核、驳回、发起打款、失败重试操作
- 钱包 API client、类型定义与基础状态映射

### 2.2 范围外

- 主站 `frontend` 钱包页面
- 钱包专属仪表盘、趋势图、财务报表
- 导出 Excel、批量审核、批量打款
- 真实微信商户请求调试工具
- 普通管理员与更细粒度的钱包权限模型

## 3. 页面方案选型

### 3.1 备选方案

方案 A（推荐）：后台新增两个独立页面，“钱包账户”和“提现审核”。  
方案 B：把钱包信息塞进现有“用户管理”页面的扩展列和详情弹窗。  
方案 C：做一个大而全的钱包工作台页面，账户、流水、提现、调账全部堆在一起。

### 3.2 选型结论

采用方案 A。理由：

- 钱包账户管理和提现审核是两类运营动作，拆开后扫描效率更高
- 现有后台路由结构已经按业务域拆页面，新增两页最符合现有风格
- 比方案 C 更轻，比方案 B 更清晰，适合作为一期最小闭环

## 4. 信息架构

在 `管理` 菜单下新增两个入口：

- `钱包账户`
- `提现审核`

推荐排序：

- 用户管理
- 租户管理
- 团队管理
- 实名认证
- 访问控制
- 推广管理
- 钱包账户
- 提现审核
- 系统设置

这样可以保持“用户身份 / 裂变 / 钱包 / 系统设置”的运营链路连续。

## 5. 页面设计

### 5.1 钱包账户页

页面目标：给运营一个“看账户 + 看余额 + 查流水 + 做调账”的工作台。

页面内容建议：

- 统计卡片：
  - 钱包账户数
  - 可用余额总额
  - 冻结余额总额
  - 累计提现总额
- 账户列表表格：
  - 用户 ID
  - 用户名 / 邮箱 / 手机号
  - 可用余额
  - 冻结余额
  - 累计收入
  - 累计提现
  - 操作：`查看流水`、`调账`
- 流水抽屉：
  - 展示指定用户的 `WalletLedger`
  - 至少显示：流水类型、金额变化、变更后可用余额、变更后冻结余额、业务类型、备注、时间
- 调账弹窗：
  - 输入金额、幂等键、备注
  - 支持正负调账

### 5.2 提现审核页

页面目标：让运营从一个列表中完成“查看提现 -> 审核 -> 打款 -> 重试”。

页面内容建议：

- 统计卡片：
  - 全部提现单数
  - 待审核数
  - 打款中数
  - 失败数
- 筛选区：
  - 状态筛选
  - 用户关键词筛选
- 提现表格：
  - 提现单 ID
  - 用户信息
  - 提现金额 `amount`
  - 手续费 `fee_amount`
  - 到账金额 `net_amount`
  - 状态
  - 渠道（当前固定 `wechat`）
  - 提交时间
  - 审核时间
  - 操作
- 操作规则：
  - `pending_review`：显示 `通过`、`驳回`
  - `approved`：显示 `发起微信提现`
  - `failed`：显示 `重试`
  - 其他状态：只展示状态，不提供非法操作按钮

### 5.3 详情与展示策略

一期不单独做提现详情页，采用列表 + 弹窗 / 抽屉即可。

详情区建议展示：

- 用户信息
- 收款快照（仅脱敏字段）
- 审核信息
- 驳回原因
- 打款失败错误码 / 错误信息

## 7. API 对接口径

本期前端直接复用现有后端钱包接口：

### 7.1 钱包账户相关

- `GET /api/admin/wallet/accounts/`
- `GET /api/admin/wallet/accounts/{user_id}/ledger/`
- `POST /api/admin/wallet/adjustments/`

### 7.2 提现相关

- `GET /api/admin/wallet/withdrawals/`
- `POST /api/admin/wallet/withdrawals/{id}/review/`
- `POST /api/admin/wallet/withdrawals/{id}/payout/`
- `POST /api/internal/wallet/withdrawals/{id}/retry/`

说明：

- 前端本期不直接使用用户侧钱包 API
- 提现打款 provider 当前固定传 `wechat`
- 前端生成 `idempotency_key` / `out_trade_no` 的策略可以先采用时间戳 + 业务前缀的前端生成方式，后续如需收口再转后端统一生成

## 8. 交互规则

### 8.1 调账

- 调账金额允许正负
- 提交前必须填写备注
- 必须带幂等键
- 成功后刷新账户列表和当前流水抽屉

### 8.2 提现审核

- `通过` 操作：
  - 仅 `pending_review` 可点
  - 需要填写幂等键
- `驳回` 操作：
  - 仅 `pending_review` 可点
  - 需要填写驳回原因与幂等键

### 8.3 发起微信提现

- 仅 `approved` 可点
- 提交参数固定：
  - `provider = wechat`
  - `request_payload = {}` 或保留调试字段
  - `idempotency_key`
  - `out_trade_no`
- 成功后状态应切为 `processing` / 提现单切为 `paying`

### 8.4 重试

- 仅 `failed` 可点
- 重试时必须重新生成新的 `idempotency_key` 和 `out_trade_no`
- 重试成功后应刷新表格状态

## 9. 展示与安全边界

### 9.1 展示字段

- 后台可以展示提现金额、状态、错误码、错误信息、时间线
- 后台不展示完整微信收款标识，只显示脱敏后的 `masked_account`

### 9.2 日志与前端提示

- 成功操作统一 toast 提示
- 后端返回统一 `detail + code` 时，前端直接展示 `detail`
- 一期不做前端侧复杂错误码映射，只做最小提示

## 10. 测试与验收口径

一期验收以 6 条标准为准：

- 后台菜单能进入钱包账户页和提现审核页
- 钱包账户页能展示账户列表并查看指定用户流水
- 运营能在后台成功执行管理员调账
- 提现审核页能展示提现申请列表与状态
- 运营能在后台完成审核通过 / 驳回 / 发起微信提现 / 失败重试
- 页面操作后数据与状态刷新正确，不出现非法按钮

测试重点：

- 路由是否挂载成功
- 钱包 API client 是否正确处理分页响应
- 不同提现状态下按钮可见性是否正确
- 调账、审核、打款、重试成功后是否刷新列表
- 驳回原因、错误码、状态标签是否正确展示
