# 用户邀请注册裂变推广设计（一期）

日期：2026-06-09  
状态：已评审（已按一期范围实现）

## 1. 背景与目标

平台需要补齐基于“用户邀请注册”的裂变推广能力，用于记录邀请关系、跟踪被邀请人进度、支持人工审核奖励，并在审核通过后衔接钱包入账。

一期目标明确如下：

- 支持用户通过邀请链接或邀请码邀请新用户注册
- 新用户注册成功后生成有效邀请记录
- 被邀请人完成指定关键行为后，邀请记录进入待审核
- 管理员逐条审核邀请奖励，审核通过后触发钱包发奖
- 用户侧与管理端都能查看邀请记录与当前状态

## 2. 范围与非范围

### 2.1 范围内

- 裂变推广独立模块，不复用组织邀请业务语义
- 邀请方式支持链接与邀请码，首版主推分享链接
- 注册归因、关键行为达成、人工审核、发奖触发完整闭环
- 用户侧推广中心与管理端运营页面所需接口设计
- 奖励规则支持后台配置，但一期不做多活动体系

### 2.2 范围外

- 多活动并行运营
- 自动审核与自动发奖
- 多级分销、上下级层级返佣
- 邀请关系注册后变更或人工改绑
- 完整营销活动中心与活动日历能力

## 3. 方案选型

### 3.1 备选方案

方案 A（推荐）：新增独立 `referrals` 模块，单独管理邀请关系、达标、审核与发奖触发。  
方案 B：在现有 `organizations` 邀请能力上叠加推广语义与奖励状态。  
方案 C：先只做前后台页面，裂变规则与归因逻辑散落在注册和钱包模块中。

### 3.2 选型结论

采用方案 A。理由：

- “加入组织”与“邀请注册裂变”不是同一业务语义，混用会加重后续维护成本
- 裂变模块天然需要连接注册、业务事件、审核、钱包，独立模块更利于边界清晰
- 一期虽然不做多活动体系，但独立模块更便于后续扩展奖励规则与运营能力

## 4. 模块边界

一期新增独立模块：`apps/referrals/`。

模块职责如下：

- `referrals`：负责邀请入口、注册归因、关键行为达成、审核状态、发奖触发
- `accounts`：负责用户注册成功事件
- 具体业务模块：负责关键行为达成事件
- `wallet`：负责奖励入账，不负责邀请关系判定
- 管理后台：负责规则配置、记录查询、人工审核

说明：一期不引入 `ReferralCampaign` 多活动模型，而是采用“单套生效裂变规则”的轻量设计。

## 5. 核心模型边界

一期保留 4 个核心模型。

### 5.1 `ReferralRuleConfig`

用途：保存当前生效的一套裂变规则配置。  
负责内容：

- 关键行为类型
- 奖励是否开启
- 奖励发放对象（首版默认邀请人）
- 是否需要人工审核
- 邀请方式是否开放
- 用户侧展示级别

说明：它不是活动中心，只是一期唯一生效规则的配置入口。

### 5.2 `ReferralLink`

用途：保存用户的邀请码与分享链接载体。  
负责内容：

- 谁发起邀请
- 邀请码/分享标识如何承接注册归因
- 邀请来源是链接还是邀请码

### 5.3 `ReferralRecord`

用途：裂变推广主记录。  
负责内容：

- 邀请关系建立
- 注册成功
- 关键行为达成
- 进入待审核
- 审核结果
- 奖励发放结果

用户侧记录列表与管理端审核列表都以它为核心。

### 5.4 `ReferralRewardReview`

用途：管理员审核事实记录。  
负责内容：

- 审核人
- 审核动作（通过/拒绝）
- 审核备注
- 审核时间
- 与奖励发放动作的关联

## 6. API 规模与分组

一期建议总计 6 个对外接口。

### 6.1 用户侧接口（2）

- `GET /api/referrals/me/summary/` 推广中心总览
- `GET /api/referrals/me/records/` 我的邀请记录列表

### 6.2 管理端接口（4）

- `GET /api/admin/referrals/config/` 获取当前裂变规则配置
- `PATCH /api/admin/referrals/config/` 更新当前裂变规则配置
- `GET /api/admin/referrals/records/` 邀请记录与审核列表
- `POST /api/admin/referrals/records/{id}/review/` 逐条审核邀请奖励

说明：注册归因、关键行为达成与发奖动作在一期通过服务层与信号完成，不单独暴露为 HTTP 接口；同时不开放批量审核与邀请码刷新接口，优先保持接口收敛。

## 7. 业务规则

### 7.1 奖励触发规则

- 新用户注册成功后即可生成邀请记录
- 被邀请人完成指定关键行为后，邀请记录进入待审核
- 管理员审核通过后，系统才触发奖励发放
- 审核拒绝后，该邀请记录不发奖

### 7.2 奖励配置规则

- 奖励规则支持后台配置
- 一期默认固定现金奖励
- 一期默认奖励邀请人
- 后续可扩展为邀请人/被邀请人双边奖励，但不在本期开放

### 7.3 邀请方式规则

- 支持邀请链接与邀请码两种方式
- 首版用户侧主路径为分享链接
- 归因在注册成功时锁定，注册后不允许变更邀请人

### 7.4 隐私展示规则

- 用户侧默认展示脱敏后的被邀请人信息与当前进度
- 后台可查看完整审核所需信息，但应遵守最小必要展示

## 8. 状态流转

一期主链路建议如下：

`已归因 -> 已注册 -> 已达标 -> 待审核 -> 已通过 -> 已发奖`

异常支路如下：

- `待审核 -> 已拒绝`
- `已通过 -> 发奖失败`

状态设计原则：

- 用户侧能清楚看到当前进度，不暴露后台实现细节
- 后台能高效筛选“已注册”“已达标待审核”“已通过待发奖/发奖失败”
- 钱包仅消费“审核通过后触发发奖”这一明确动作

## 9. 异常场景

一期重点处理以下高风险场景：

- 重复归因：同一新用户只能锁定一条最终有效邀请关系
- 已注册用户填写邀请码：不成立邀请关系
- 关键行为重复触发：同一邀请记录不能重复进入待审核
- 审核重复点击：同一记录不能被重复审核推进
- 钱包入账失败：记录保持为“已通过但发奖失败/待补偿”，不回退待审核
- 隐私边界：用户侧仅显示脱敏信息

## 10. 测试与验收口径

一期验收以 5 条主标准为准：

- 用户通过邀请链接或邀请码完成注册后，系统能生成有效邀请记录
- 被邀请人完成预设关键行为后，邀请记录能稳定进入待审核状态
- 管理员可以筛选、查看并逐条审核邀请达标记录
- 审核通过后能触发钱包奖励发放，失败状态可见且可后续补偿
- 用户侧推广中心能看到邀请码/分享链接、邀请记录列表、当前进度与奖励结果

测试重点：

- 正常链路：归因成功 -> 注册成功 -> 达标 -> 审核通过 -> 发奖成功
- 拒绝链路：达标 -> 审核拒绝
- 幂等链路：重复归因、重复达标、重复审核、重复发奖触发
- 边界链路：老用户邀请码无效、用户侧信息脱敏正确
