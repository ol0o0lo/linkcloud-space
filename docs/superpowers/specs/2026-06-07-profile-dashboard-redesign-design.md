# 个人中心状态驾驶舱改版设计

## 背景

当前 `http://localhost:5999/profile` 对应的个人中心位于 `frontend_admin/apps/web-antdv-next/src/views/_core/profile/`，已经从旧的 `/accounts/*` 页面迁移到后台前端。现状是将 `总览 / 基本资料 / 安全 / 密码 / 通知` 纵向串联成一个设置页，虽然功能齐全，但整体仍偏“表单堆叠”，缺少进入页面后的身份感、当前账户上下文和状态优先级。

本次改版目标是推倒现有排版和交互壳层，重做为“身份优先的状态驾驶舱”，但不依赖新增后端领域模型，不先改动现有账号、安全、通知接口的业务能力。

## 设计目标

- 让用户进入 `/profile` 的第一感受从“设置页”变成“我的账户空间”。
- 首页优先展示身份信息与当前组织归属，而不是立即展示大段表单。
- 用摘要卡先说明状态，再进入下沉模块处理具体设置。
- 保留同页完成资料、安全、密码、通知管理的能力，不拆成多页流程。
- 兼容当前后台 Vben Admin、Ant Design Vue、移动端窄屏和暗色模式能力。

## 非目标

- 不重新设计账号体系、MFA、Passkey、通知偏好或组织模型本身。
- 不新增必须依赖的后端接口；若实现时有小型补充接口，仅作为可选优化。
- 不把个人中心改造成公开展示型个人主页。
- 不在本设计阶段直接实现页面代码。

## 设计结论

采用 `身份甲板` 方案作为新版 `/profile` 的整体结构。页面以“身份主舞台 + 状态摘要带 + 同页下沉模块”三层组织：

1. 身份主舞台：首先确认“我是谁、我正在以什么身份使用系统”。
2. 状态摘要带：用结论化卡片快速说明资料、安全、密码、通知状态。
3. 同页下沉模块：默认查看态，需要修改时局部进入编辑态，不再整页同时表单化。

这个结构最符合本次确定的三项前提：`状态驾驶舱`、`身份优先`、`同页下沉`。

## 页面结构

### 1. 身份主舞台

页面顶部使用一块高识别度身份区域，包含：

- 头像
- 显示姓名
- 用户名
- 手机号
- 邮箱
- 时区
- 当前组织名称
- 当前角色或归属描述
- 资料完整度 / 验证状态中的关键摘要

这一层的目标不是承载全部操作，而是让用户迅速确认当前账户上下文。这里允许放置少量高频动作：

- `编辑资料`
- `更换头像`
- `进入组织相关入口` 或 `切换组织入口`

顶部区域不放复杂的安全操作、密码表单或通知开关，避免主舞台退化成按钮墙。

### 2. 状态摘要带

身份区下方放置 4 张摘要卡：

- `资料完整度`
- `账户安全`
- `密码状态`
- `消息提醒`

每张卡只负责三个事情：

- 当前结论
- 一句解释
- 一个明确动作入口

摘要卡不承载复杂输入组件。示例表达方式：

- `资料已基本完善，还可补充头像与时区信息`
- `已开启验证器，尚未添加 Passkey`
- `登录密码已设置，可按需更新`
- `通知分类已启用 3 项邮件提醒`

这四张卡片本质上是现有数据的派生视图，不是新的独立数据源。

### 3. 轻锚点导航

在摘要带下方放一条轻量锚点导航：

- `资料`
- `安全`
- `密码`
- `通知`

它只负责平滑滚动到对应模块，不承担 tabs 切换职责。页面仍然是一个完整的单页驾驶舱，而不是被切碎的多标签设置页。

### 4. 同页下沉模块

页面下半区按固定顺序排列：

1. `个人资料`
2. `安全与登录`
3. `密码`
4. `通知偏好`

默认全部为查看态。进入某个模块编辑时，只展开当前模块，其余模块保持查看态或收起，避免一个页面同时出现多块编辑表单。

## 交互模型

### 查看态优先

新版个人中心默认优先展示摘要和查看态，不再使用灰底假输入框模拟“只读表单”。查看态使用信息块、徽标、状态标签和简短说明展示内容。

### 单模块编辑态

任一模块进入编辑时，遵守以下规则：

- 当前模块切换为编辑态
- 其他模块保持静态查看态
- 当前模块提供清晰的取消、保存、风险说明
- 保存成功后回到查看态并局部刷新

这样可以降低整页噪音，也更符合驾驶舱中“先看结论，再在局部处理问题”的节奏。

### 安全模块内部拆组

安全模块不再做成长内容平铺，至少拆成三组独立卡块：

- `验证器与恢复码`
- `Passkey`
- `第三方账号绑定`

每组单独展示状态、说明和操作入口。这样能保留现有安全能力的完整性，同时降低阅读和决策压力。

### 顶部快捷动作控制

顶部身份主舞台只保留 2 到 3 个高频动作，避免与下方模块抢焦点。复杂的高风险操作继续留在对应模块内部处理。

## 组件边界

实现时建议将当前 `_core/profile` 目录中的页面重新组织为更清晰的边界：

- `profile/index.vue`
  - 页面装配层，负责数据加载、锚点导航和模块状态协调。
- `profile/components/ProfileHero.vue`
  - 身份主舞台。
- `profile/components/ProfileStatusCards.vue`
  - 四张摘要卡。
- `profile/components/ProfileAnchorNav.vue`
  - 轻锚点导航。
- `profile/sections/ProfileBasicSection.vue`
  - 个人资料查看态与编辑态。
- `profile/sections/ProfileSecuritySection.vue`
  - 安全总模块，内部再组合验证器、恢复码、Passkey、第三方绑定子块。
- `profile/sections/ProfilePasswordSection.vue`
  - 密码模块。
- `profile/sections/ProfileNotificationSection.vue`
  - 通知偏好模块。

如果实现时不想大幅挪动文件，也至少要在逻辑上维持上述边界，避免 `index.vue` 继续承担过多展示与状态派生职责。

## 数据流设计

### 页面初始化数据

页面初始化并行获取以下四组数据：

- 当前用户资料
- 安全数据（验证器、恢复码、Passkey、第三方绑定）
- 通知偏好
- 当前组织与角色摘要

这些数据在页面顶层统一组织，然后分发到主舞台、摘要卡和下沉模块。若当前实现中组织与角色信息已经包含在用户上下文中，则直接复用，不额外请求。

### 摘要卡派生逻辑

摘要卡通过现有数据推导，不新增摘要接口。推荐派生规则：

- `资料完整度`
  - 由头像、姓名、手机号、邮箱、时区、当前组织上下文等字段生成完成度和缺口说明。
- `账户安全`
  - 由 TOTP、恢复码、Passkey 数量、第三方登录绑定状态推导。
- `密码状态`
  - 由“是否已有密码”和可变更性生成简洁说明。
- `消息提醒`
  - 由通知分类配置数量、开启渠道数量生成摘要。

派生逻辑应集中在单独的 helper 或 composable 中，避免散落在多个组件里重复判断。

## 视觉方向

### 总体气质

视觉方向强调 `稳、清晰、有身份感`，而不是高装饰性。页面需要明确脱离传统后台设置页的观感，但仍保持可信赖和可操作。

### 主舞台风格

顶部身份主舞台使用更强的视觉层次，例如：

- 浅色渐变背景
- 轻玻璃感或柔和纹理
- 更明确的头像、姓名和组织信息层级

重点是建立“这是我的账户空间”的第一感受，而不是做营销型 hero banner。

### 状态语言优先

页面文案优先使用结论和建议语气，而不是字段罗列语气。摘要卡和查看态都尽量表达“当前状态 + 下一步建议”，减少数据库详情页既视感。

### 模块节奏差异

页面从上到下形成明显节奏：

- 顶部：强身份主视觉
- 中部：轻快可扫描的摘要卡
- 下部：稳定、可信赖的操作模块

不同层级需要明显区分，避免整页所有卡片同质化。

### 移动端策略

移动端不保留复杂双栏。处理方式：

- 身份主舞台完整保留，但纵向堆叠
- 摘要卡改为 2 列或可横向滑动
- 下沉模块维持顺序展开
- 锚点导航保持可点击和清晰定位

移动端的目标是压缩布局而不丢掉身份感。

## 异常处理

### 局部失败，不整页白屏

各模块数据失败时局部降级：

- 资料失败只影响资料区
- 安全失败只影响安全区
- 通知失败只影响通知区

顶部身份主舞台优先保证可见，只要基础用户信息可用，就不应被其他模块失败拖垮。

### 错误反馈贴近操作点

编辑失败时，错误信息应出现在当前模块附近，而不是只依赖全局 message。局部错误优先使用模块内提示；全局 message 只作为补充。

### 高风险动作确认

以下操作继续保留二次确认，并明确影响范围：

- 关闭验证器
- 重置恢复码
- 删除或解绑 Passkey
- 解绑第三方账号

## 测试与验收

### 页面渲染

- 桌面端和移动端下，身份主舞台、摘要卡、锚点导航和下沉模块层级清晰。
- 不同用户状态下，摘要卡文案与状态显示正确。

### 交互流程

- 任一模块进入编辑态时，不影响其他模块的静态展示。
- 锚点导航能正确滚动到对应区域。
- 保存、取消、失败重试的反馈行为一致。

### 状态派生

- 资料完整度派生结果与字段实际状态一致。
- 安全摘要正确反映验证器、恢复码、Passkey、第三方绑定情况。
- 通知摘要正确反映分类与渠道开关结果。

### 回归建议

实现阶段至少运行：

- 个人中心相关前端类型检查与构建
- 现有账号、安全、通知接口相关测试
- 主路径的 UI 验证：进入页面、查看摘要、进入模块编辑、保存成功、失败反馈

## 实施边界与顺序建议

后续实现以“先重组页面壳层，再替换各模块表达”为原则：

1. 先搭建新的 `index` 页骨架、身份主舞台、摘要卡、锚点导航。
2. 再改造资料模块，确认查看态与编辑态模式稳定。
3. 再拆分安全模块内部结构。
4. 最后收敛密码与通知模块表现，并统一反馈与移动端细节。

这样能在保持接口稳定的前提下逐步完成改版，避免一次性重写整个页面导致验证困难。
