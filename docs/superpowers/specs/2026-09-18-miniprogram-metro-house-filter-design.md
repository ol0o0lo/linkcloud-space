# 小程序地铁找房筛选设计

**日期：** 2026-09-18  
**状态：** 设计已确认，已补充独立找房页筛选体验，待实施计划  
**适用范围：** Django 地铁基础数据、公开房源空间筛选、uni-app 小程序找房列表

## 1. 背景

小程序首页目前已经展示“地铁找房”和“地铁线路”入口，但实际行为只是向公开房源关键词搜索传入“地铁”。公开房源搜索并没有结构化的地铁城市、线路、站点或站点距离数据，因此无法让用户按线路和站点准确筛选房源。

项目已经使用 PostGIS 保存小区和楼栋位置，并具备附近半径过滤和距离排序能力。本设计在现有空间基础上增加可逐城市导入的地铁数据，将地铁作为公开房源列表的一项筛选条件，不新增独立房源结果页。

## 2. 目标

- 按城市逐步导入地铁线路、站点及站点坐标。
- 小程序先选择线路，再从该线路勾选一个或多个站点。
- 一次最多选择 5 个站点，支持跨线路选择。
- 空间搜索统一使用一个独立的范围条件，支持 500 米、1 公里、1.5 公里和 2 公里，默认 1 公里。
- 开启“附近”时围绕用户当前位置搜索；未开启“附近”但选择地铁站时，围绕所选站点搜索。
- 搜索命中任一所选站点周边的公开房源，并对重复命中的房源去重。
- 计算每套房源距离最近的所选站点，并支持按该距离排序。
- 搜索结果继续展示在现有公开房源列表中。
- 地铁数据整包校验、原子导入；成功立即生效，失败完全不生效。
- 对外导入文件和查询接口均使用“线路内嵌站点”的直观结构。
- 小程序将区域和地铁合并为三级级联条件，三列宽度约为 `1:3:6`。
- 首页“地铁找房”和“地铁线路”入口进入独立找房页后，自动打开并选中地铁筛选，而不是把“地铁”作为关键词。
- 独立找房页使用透明导航栏，导航内容仅保留返回、搜索输入和右侧全局地区入口。
- 按筛选复杂度选择交互容器：少量简单选项使用顶部悬浮气泡，复杂组合条件使用底部弹层。

## 3. 非目标

- 不引入新的独立视觉主题；配色、阴影、圆角和动效复用现有小程序主题变量，并在实现中按小屏可用空间微调具体尺寸。
- 不建设独立的地铁找房结果页或地铁地图页。
- 不计算真实步行路线、步行时间、换乘时间或通勤时间。
- 不保存地铁出入口、首末班时间、票价、列车时刻表和线路轨迹。
- 不预计算并持久化所有楼栋到所有站点的距离。
- 不一次性导入全国城市，按实际业务城市逐步增加数据。
- 不在运行搜索时临时调用外部地图服务查询地铁数据。
- 首期不维护行政区下的商圈或街道，区域模式第三级只展示“全区”。

## 4. 方案选择

采用“标准化关系模型、嵌套导入格式、PostGIS 实时空间查询”。

未选择城市整包 JSON 直接存储，因为换乘站会在多条线路中重复出现，难以保证站点坐标一致，也不利于数据库约束和空间查询。未选择预计算楼栋与站点距离表，因为当前最多查询 5 个站点，PostGIS 空间索引足以支撑首期规模，预计算会增加房源位置和地铁数据更新时的同步成本。

对外数据保持简单：每条线路直接包含其站点。数据库内部通过显式关联表表达线路与站点的多对多关系，以正确处理换乘站和线路内排序。

## 5. 领域模型

新增独立的 `apps.metro` 应用，避免将城市轨道交通主数据放入房源模型。

### 5.1 MetroCity

表示一个已导入的城市地铁数据集。

主要字段：

- `name`：城市名称，应与公开房源使用的标准城市名称一致，例如“深圳市”。
- `province`：省级名称。
- `data_version`：导入数据版本，例如 `2026-09`。
- `imported_at`：最近成功导入时间。

城市记录存在且数据导入成功，即可向小程序提供。不设计草稿、发布、审核等状态流转。

### 5.2 MetroLine

表示城市内的一条地铁线路。

主要字段：

- `city`：所属城市。
- `name`：展示名称，例如“1号线”。
- `color`：线路展示颜色。
- `sort_order`：线路在选择组件中的顺序。
- `is_loop`：是否为环线。
- `is_active`：是否仍对用户可选。

约束：同一城市内线路名称唯一，线路名称直接作为导入匹配键。

### 5.3 MetroStation

表示一个物理地铁站。换乘站只保存一条站点记录。

主要字段：

- `city`：所属城市。
- `name`：站点名称。
- `aliases`：可选别名列表，为后续站点搜索保留。
- `district`：行政区名称，可为空。
- `address`：站点地址，可为空。
- `location`：站点中心点，使用 PostGIS `PointField`。
- `is_active`：是否仍对用户可选。

数据库坐标统一使用 WGS84、SRID 4326，并建立 GiST 空间索引。对外导入文件必须声明坐标系，导入边界负责转换为 WGS84。

约束：同一城市内站点名称唯一，站点名称直接作为导入和查询匹配键。本设计明确不处理同一城市内两个不同物理站点重名的情况。

### 5.4 MetroLineStation

表示线路与站点的内部关联，不在导入格式和小程序接口中单独暴露。

主要字段：

- `line`：所属线路。
- `station`：关联站点。
- `sort_order`：站点在该线路内的展示顺序。
- `is_active`：该线路与站点关系是否仍有效。

约束：同一线路与站点组合唯一。线路和站点必须属于同一城市。

显式关联表不可省略，因为换乘站属于多条线路，且同一站点在不同线路中的顺序不同。该复杂度只存在于数据库内部，不影响导入数据和接口使用方式。

## 6. 地铁数据导入契约

每个城市使用一个完整 JSON 文件，数据按线路嵌套站点：

```json
{
  "schema_version": 1,
  "data_version": "2026-09",
  "coordinate_system": "gcj02",
  "city": {
    "name": "深圳市",
    "province": "广东省"
  },
  "lines": [
    {
      "name": "1号线",
      "color": "#00A651",
      "sort_order": 1,
      "is_loop": false,
      "stations": [
        {
          "name": "世界之窗",
          "aliases": [],
          "district": "南山区",
          "address": "",
          "longitude": 113.974,
          "latitude": 22.536,
          "sort_order": 12
        }
      ]
    }
  ]
}
```

换乘站需要在每条所属线路的 `stations` 中出现，并使用完全相同的站点名称。导入器按城市和站点名称合并为同一个 `MetroStation`，再分别创建线路关联。

同一站点名称在文件中重复出现时，坐标和城市级属性必须一致；不一致视为整包数据冲突，拒绝导入。`sort_order` 属于线路关联，允许在不同线路中不同。

### 6.1 导入校验

导入前至少校验：

- `schema_version`、`data_version`、城市名称和坐标系存在且受支持。
- 城市内线路名称唯一。
- 城市内相同站点名称指向一致的站点数据。
- 线路内站点不能重复。
- 经度和纬度完整、可解析且处于合法范围。
- 线路和站点名称不能为空。
- `sort_order` 为有效整数。
- 环线字段符合约定类型。

### 6.2 原子生效

不设计草稿和发布流程。一个城市的数据导入只有两种结果：

- 所有校验和数据库写入成功：整个城市的新数据在事务提交后立即生效。
- 任意校验或写入失败：整个事务回滚，继续使用此前成功导入的数据。

导入按完整城市名称、线路名称和站点名称更新或新增数据。新版本中缺失的旧线路、旧站点和旧关联在同一事务内标记为不活跃，不执行物理删除。线路或站点改名视为旧记录停用并新增记录；如需保留同一记录，需要在导入前统一名称。导入完成后输出新增、更新、停用和冲突数量，便于人工确认数据规模。

## 7. 地铁公开接口

遵循项目现有公开接口前缀，新增：

```http
GET /api/public/metro/cities/
GET /api/public/metro/cities/{city_name}/
```

城市列表只返回已经成功导入且至少存在一条有效线路和一个有效站点的城市。
响应返回 `province` 和 `name`；小程序使用完整城市名称匹配当前公开房源地区，不根据城市简称猜测。

城市详情直接返回适合小程序线路、站点选择的嵌套结构：

```json
{
  "name": "深圳市",
  "data_version": "2026-09",
  "lines": [
    {
      "name": "1号线",
      "color": "#00A651",
      "stations": [
        {
          "name": "世界之窗"
        }
      ]
    }
  ]
}
```

小程序只使用城市、线路和站点名称，不依赖数据库 ID 或内部编码。下拉选择不需要站点坐标，因此该接口不返回经纬度；坐标只在后端空间筛选中使用。城市详情可按 `data_version` 缓存，数据导入成功后使对应城市缓存失效。

## 8. 公开房源筛选

扩展现有接口：

```http
GET /api/public/houses/
```

新增查询参数：

- `metro_stations`：重复 query 参数表示多个站点名称，最多 5 个。
- `longitude`、`latitude`：用户当前位置，必须同时出现。
- `radius_m`：统一空间半径，允许 `500`、`1000`、`1500`、`2000`，默认 `1000`。
- `coordinate_system`：当前位置坐标系，当前位置请求继续使用 `gcj02`。
- `sort=distance_asc`：按当前空间搜索中心的最近距离排序。

示例：

```http
GET /api/public/houses/?city=深圳市&metro_stations=罗湖&metro_stations=国贸&radius_m=1000&sort=distance_asc&page=1&page_size=12
```

不增加 `spatial_mode` 参数。后端根据实际传入的空间中心判断查询模式：

```text
longitude + latitude
→ 用户当前位置附近搜索

city + metro_stations
→ 所选地铁站附近搜索

两者都没有
→ 普通条件搜索
```

### 8.1 参数约束

- 站点名称数量为 1 至 5 个，重复名称先去重。
- `metro_stations` 必须与完整的 `city` 参数一起传入。
- 所有站点必须是该城市内的有效站点；存在未知站点时返回参数错误，不静默忽略。
- 经度和纬度必须同时传入，不能只传一个。
- 当前位置与地铁站点两种空间中心不能同时传入；同时传入时返回 422，避免隐式优先级。
- 半径必须属于预设档位。
- `distance_asc` 必须存在当前位置或地铁站点空间中心。
- 单独传入 `radius_m` 不会开启空间筛选。

### 8.2 空间查询

房源继续继承 `House.building.location`，不新增房源坐标字段。没有楼栋坐标的房源不进入地铁筛选结果，也不根据地址文字推测坐标。

筛选过程：

1. 使用完整城市名称和站点名称查询有效地铁站，并读取其 WGS84 坐标。
2. 将查询限制在所选城市的有效公开房源。
3. 使用 PostGIS 空间索引筛选落入任一站点半径内的楼栋。
4. 对同时命中多个站点的房源去重。
5. 计算每套房源与所有已选站点之间的最短直线距离。
6. 解析产生最短距离的站点，作为该房源的最近地铁站。
7. 按请求的排序规则和现有分页规则返回结果。

当前位置和地铁站点搜索均使用球面直线距离，不表示真实步行路程。最多 5 个站点和最多 2 公里半径用于限制查询范围和保持稳定性能。当前阶段不增加楼栋与站点距离缓存表；只有执行计划或线上指标证明实时查询不足时再引入预计算。

### 8.3 响应字段

`PublicHouseListOut` 继续复用现有 `distance_m` 表示当前空间中心的最近直线距离，并增加仅在地铁筛选时有值的 `nearest_metro_station`：

```json
{
  "distance_m": 680,
  "nearest_metro_station": {
    "name": "世界之窗",
    "line_names": ["1号线", "2号线"]
  }
}
```

房源同时命中多个站点时，只返回距离最近的站点信息。换乘站的 `line_names` 返回该站当前有效线路名称。

## 9. 小程序筛选状态与流程

地铁是现有公开房源列表的一项筛选条件，不新增独立结果页。筛选状态至少包含：

```ts
interface PublicHouseMetroFilter {
  city: string
  selectedStationNames: string[]
}

interface PublicHouseSpatialRange {
  nearbyEnabled: boolean
  radiusM: 500 | 1000 | 1500 | 2000
}
```

当前正在浏览的线路只属于选择组件的临时状态，不作为后端筛选参数。

### 9.1 使用流程

1. 用户先通过现有地区能力确定具体城市。
2. 打开合并后的“区域 / 地铁”筛选。
3. 第一级以约 10% 宽度切换区域或地铁。
4. 区域模式第二级以约 30% 宽度展示全城和行政区，第三级以约 60% 宽度暂时只展示“全区”。
5. 地铁模式第二级展示线路，第三级展示当前线路的站点并允许多选。
6. 切换线路时保留已经勾选的其他线路站点。
7. 换乘站无论从哪条线路勾选，都只占用一个选择名额。
8. 达到 5 个站点后阻止继续勾选。
9. 点击确定后关闭三级筛选，并使用现有分页列表重新查询。

### 9.1.1 顶部下拉展开形态

“区域 / 地铁”使用紧贴房源列表顶部筛选栏的下拉覆盖层，不使用底部抽屉或底部弹层：

- 用户点击顶部“区域 / 地铁”筛选项后，面板从筛选栏下方向下展开，顶部与筛选栏底边对齐。
- 搜索栏、导航栏和顶部筛选栏保持可见，房源列表区域增加半透明遮罩，明确当前正在编辑筛选条件。
- 面板内部继续使用 `1:3:6` 的三级列宽；三列各自纵向滚动，不推动页面主体滚动。
- 面板最大高度受当前窗口可用高度约束，内容超出时仅滚动对应列；小屏设备至少保留操作区和安全区。
- “重置”和“查看房源 / 确定”固定在面板底部，不能随站点列表滚出可视区域。
- 点击遮罩、再次点击当前筛选项、点击其他顶部筛选项或完成确认时，面板向上收起。
- 切换到其他顶部筛选项时只允许一个下拉面板处于展开状态，避免多个遮罩和浮层叠加。
- 展开和收起只改变展示中的草稿；点击确认后才写入正式筛选并刷新房源列表，点击遮罩关闭则放弃本次未确认修改。

筛选摘要文案：

- 未选择站点：`地铁`
- 已选择站点：`地铁 · 3站`

房源卡片在地铁筛选生效时展示：`距世界之窗站 680 米`。

### 9.2 独立附近与范围条件

范围不放在区域 / 地铁三级面板内，而是现有筛选栏中的独立“附近”条件：

- 可选半径为 500 米、1 公里、1.5 公里和 2 公里，默认 1 公里。
- 开启附近时获取用户当前位置，请求发送经纬度和半径，不发送 `metro_stations`。
- 未开启附近且已经选择地铁站时，请求发送城市、站点名称列表和同一个半径。
- 未开启附近且没有选择地铁站时，不发送任何空间中心，执行普通条件搜索；半径只作为用户偏好保留。
- 前端保证当前位置和地铁站点不会同时发送，后端仍进行冲突校验。
- 开启附近不会丢弃用户已经选择的区域或地铁草稿，但这些条件在附近模式下不作为空间中心发送；关闭附近后可恢复使用。

### 9.3 地区联动

- 区域和地铁共享同一个三级筛选入口，并作为两种互斥的条件类型。
- 地铁筛选必须依附于具体城市，不在全国或城市不明确的状态下启用。
- 当前城市没有地铁数据时，显示“该城市暂未提供地铁筛选”。
- 用户切换城市后，自动清空旧城市的站点选择。
- 用户清空地区条件时，同时清空地铁筛选。
- 区域模式选中行政区时，第三列暂时固定为“全区”；以后准备商圈或街道数据后再扩展，不改变三级结构。

### 9.4 排序联动

首次应用附近或地铁筛选时默认使用 `distance_asc`。用户仍可以切换现有“最新发布”和“租金从低到高”等排序。空间中心变化后，如果当前仍是距离排序，则按新的中心重新计算。

区域 / 地铁使用顶部下拉覆盖层；具体视觉遵循 9.6 的统一规则并复用现有主题变量，线路色块只承担线路识别作用。

### 9.5 首页入口与默认展开

- `PublicHouseSearchPreset` 增加结构化的位置筛选入口参数，不再使用 `keyword: "地铁"` 表示地铁找房。
- 首页“地铁找房”和排行中的“地铁线路”统一跳转到独立找房页，并携带“打开位置筛选、默认地铁模式”的参数。
- 找房页先完成全局地区初始化，再将区域 / 地铁筛选草稿切换到地铁模式并展开面板，确保面板打开时能够立即加载当前城市线路。
- 自动展开只改变筛选草稿，不在用户选择站点前发送地铁房源请求；用户确认站点后再应用正式条件。
- 当前城市无地铁数据或城市未确定时仍然打开地铁面板，并在内容区显示对应的引导或空状态。

### 9.6 按复杂度分层的筛选容器

筛选容器不追求形式完全一致，而是保持视觉语言一致、交互复杂度匹配：

- “附近”这类只有少量固定选项的筛选，使用紧贴筛选项下方的悬浮气泡。气泡采用圆角卡片、柔和阴影、简短说明和一组可直接点击的选项；选择后可立即确认。
- “区域 / 地铁”虽然从顶部筛选项打开，但包含模式、线路和多站点三级选择，因此使用更大的顶部悬浮面板，并保留固定底部操作区。
- 租金范围、面积范围、户型和电梯等组合条件使用底部弹层。弹层显示顶部把手、简短说明、分组卡片和固定操作按钮，避免在小气泡内堆叠表单。
- 任意时刻只允许一个悬浮筛选或底部弹层打开。打开另一筛选前关闭当前筛选，避免遮罩、层级和草稿状态冲突。

统一视觉规则：

- 面板使用页面卡片背景、品牌柔色选中态和 24 至 32rpx 圆角。
- 标题、说明、选项和操作区使用固定的四级文字层级，避免不同面板字号和粗细跳变。
- 主操作使用品牌实色，次操作使用浅色或描边；底部按钮比例保持一致。
- 展开、切换和关闭使用约 180ms 的轻量动画，并遵守减少动态效果设置。
- 线路颜色只用于识别线路，不作为大面积背景色，保证整体界面和品牌色协调。

### 9.7 透明导航栏

- 独立找房页导航栏不显示页面标题，背景和阴影保持透明。
- 搜索输入框使用轻微半透明或页面柔色背景，保证在透明导航上仍有清晰边界。
- 全局地区入口位于搜索框右侧；返回按钮位于左侧，三者均避开微信胶囊区域。
- 页面正文不再重复展示搜索框，首个内容区直接进入快速筛选栏。

## 10. 错误和空状态

- 城市地铁数据加载失败：保留当前已选条件并提供重试，不静默清空。
- 城市没有地铁数据：禁用站点选择并展示说明。
- 选择超过 5 个站点：阻止本次勾选并提示“最多选择 5 个站点”。
- 后端发现站点已经失效：前端刷新城市地铁数据，移除失效站点并提示筛选已更新。
- 附近或地铁筛选无结果：保留筛选条件，提示扩大范围、调整站点或放宽其他条件。
- 缺少楼栋坐标：房源不进入结果，不使用小区名称或地址进行模糊替代。
- 快速修改筛选产生并发请求：只接受最后一次房源列表请求结果，复用现有分页请求抢占机制。

## 11. 测试范围

### 11.1 后端

- 同一换乘站在多条线路中合并为一个站点，并生成多条线路关联。
- 同名站点在多条线路中的坐标数据不一致时拒绝整个城市导入。
- 导入任一步失败时事务完全回滚，旧数据保持不变。
- GCJ-02 输入正确转换并以 WGS84 写入数据库。
- 多站点空间查询返回任一站点范围内的房源。
- 同一房源命中多个站点时只返回一次。
- 最近站点和最短距离计算正确。
- 站点名称数量、城市一致性、半径档位和排序参数校验正确。
- 当前位置、地铁站点和普通条件三种模式能够由参数正确推断。
- 同时传入当前位置和地铁站点时返回 422。
- 无楼栋坐标房源被排除。
- 新版本缺失的旧线路和站点被原子标记为不活跃。

### 11.2 小程序

- 切换线路后保留其他线路已选站点。
- 换乘站不会重复占用选择数量。
- 最多只能选择 5 个不同站点。
- 切换城市和清空地区时清空地铁条件。
- 正确生成重复的 `metro_stations`、统一半径、排序和分页参数。
- 开启附近时只发送当前位置，关闭附近时恢复地铁站点搜索。
- 重置区域 / 地铁筛选不会重置独立的范围偏好。
- 区域 / 地铁面板从顶部筛选栏下方向下展开，关闭后向上收起，且底部操作区始终可见。
- 房源卡片在响应包含最近地铁站时展示站名和现有 `distance_m`。
- 地铁数据失败、站点失效和无结果状态正确处理。
- 首页“地铁找房”和“地铁线路”进入后自动展开地铁模式，且不会把“地铁”写入关键词。
- 简单固定选项使用顶部悬浮气泡，复杂组合条件使用底部弹层，同一时刻只打开一个筛选容器。
- 独立找房页导航栏透明、无标题，搜索输入和右侧地区入口在微信胶囊安全区域内正常显示。

## 12. 验收标准

- 后端能够通过一个城市 JSON 文件完整导入线路、站点和坐标。
- 导入成功后数据立即可用；导入失败时线上原数据不发生变化。
- 小程序能够按线路浏览站点并跨线路选择最多 5 个站点。
- 区域 / 地铁三级面板从顶部筛选栏下方向下展开，不以底部弹层呈现，并能通过遮罩、再次点击筛选项或确认操作收起。
- 用户能够通过独立附近条件选择 500 米、1 公里、1.5 公里或 2 公里空间范围。
- 开启附近时围绕用户当前位置搜索；关闭附近并选择地铁站时围绕所选站点搜索。
- 现有公开房源列表只返回命中任一所选站点范围的房源。
- 重复命中的房源只展示一次，并能显示最近站点及直线距离。
- 地铁筛选能与现有城市、行政区、租金、户型等条件共同工作。
- 未导入地铁数据的城市不影响普通公开房源浏览。
- 不新增独立地铁房源结果页。
- 从首页地铁入口进入时，用户无需再次点击即可看到已切换到地铁模式的筛选面板。
- 附近、区域 / 地铁和综合筛选在视觉上使用统一圆角、间距、色彩和操作按钮层级，但根据复杂度采用悬浮气泡、大型顶部面板或底部弹层。
- 独立找房页导航栏保持透明且不显示标题，正文不重复展示搜索框。
