# 统一组织架构工作台设计

## 背景

当前空间治理能力分散在五类独立入口：

- 成员管理；
- 团队管理；
- 邀请管理；
- 员工分工；
- 权限管理。

这些页面共享同一组组织、团队和成员数据，但导航、选择状态和编辑入口彼此割裂。管理员需要在多个页面之间往返，才能确认一个成员的团队归属、访问角色和房源负责范围。

本设计将上述能力整合为统一的“组织架构”工作台。它沿用现有数据模型：一个组织包含多个平级团队，成员可以同时加入多个团队；不增加部门层级或团队父子关系。

## 目标

1. 用统一组织树表达组织、团队、成员、未分组成员和待处理邀请。
2. 在同一工作台中管理成员资料、团队归属、权限角色和房源分工。
3. 在团队上下文中管理团队资料、团队成员、团队级访问角色和成员分工概览。
4. 将角色定义能力整合为工作台顶部的“角色权限”标签，将角色分配放回成员或团队上下文。
5. 将现有邀请功能整合进工作台，不改变邀请业务规则。
6. 保留旧路由兼容性，并支持刷新、返回和深链接恢复当前上下文。
7. 复用现有后端模型，并补充组织树轻量读取与团队成员原子变更 API；不新增数据库迁移。

## 非目标

- 不增加嵌套部门或团队父子关系。
- 不让团队直接承担房源责任；房源分工仍归属于组织成员。
- 不为邀请预设团队；接受邀请后，新成员先进入未分组成员。
- 不改变房东范围、楼栋范围、小区范围的责任优先级。
- 不改变现有权限点、系统角色、组织角色和团队角色的生效语义。
- 不增加保存前的精确房源影响试算接口。
- 不顺带重构空间资料、套餐、通知或其他空间管理页面。

## 已有数据模型约束

### 组织与成员

- `OrganizationMember` 表达用户在当前组织中的成员关系。
- Owner 是组织治理身份，不通过普通成员表格行内开关修改。
- 移除组织成员是危险操作，会影响该成员的组织角色、团队关系和房源分工。

### 团队

- `Team` 直接属于组织。
- 团队之间平级，不存在 `parent` 字段。
- 团队与用户为多对多关系，因此成员可以同时属于多个团队。

### 房源分工

- 房源分工绑定 `OrganizationMember`。
- 生效优先级固定为：房东范围 → 楼栋范围 → 小区范围。
- 保存使用整体替换语义，三层均为空表示取消该成员全部负责范围。

### 邀请

- 支持邮箱、手机号和站内用户邀请。
- 可预设组织级访问角色，但不预设团队。
- 保留邀请详情、重发和取消能力。

## 信息架构

### 导航

空间管理菜单中的以下入口合并为一个“组织架构”入口：

- 成员；
- 邀请；
- 团队；
- 员工分工；
- 权限管理及其空间角色、空间授权、团队角色和团队授权子页。

推荐使用新的规范路由：

```text
/space/organization
```

旧路由继续可访问，并重定向到统一工作台的对应上下文：

| 旧路由 | 新上下文 |
| --- | --- |
| `/space/members` | 全部成员 |
| `/space/invitations` | 待加入 |
| `/space/teams` | 团队列表或首个可见团队 |
| `/space/responsibilities` | 全部成员，并进入房源分工入口 |
| `/space/access` 及角色定义子路由 | 角色权限，并恢复组织级或团队级角色范围 |
| `/space/access` 下的授权绑定子路由 | 全部成员、对应团队或成员的访问角色上下文 |

工作台使用查询参数保存当前节点和标签，例如：

```text
/space/organization?section=members&node=member:42&tab=responsibilities
/space/organization?section=members&node=team:7&tab=members
/space/organization?section=members&node=invites
/space/organization?section=roles&scope=organization
/space/organization?section=roles&scope=team&team=7
```

查询参数是可恢复的页面状态，不作为新的领域数据。

未携带可恢复状态时，默认进入 `section=members&node=all`，直接显示“组织成员 → 全部成员”，不以组织概览作为默认落点。

### 双栏上下文工作台

页面采用已确认的 A 方案：

- 页面顶部提供“组织成员”和“角色权限”两个一级标签；
- 左侧为统一组织树；
- “组织成员”中，右侧根据当前节点展示组织、团队、成员或邀请上下文；
- “角色权限”中，右侧根据组织或团队范围展示角色定义；角色绑定仍在成员或团队上下文完成；
- “组织成员”顶部保留一个主要动作“邀请成员”，“角色权限”的主要动作根据当前范围切换为“新建角色”；
- “新建团队”“添加已有用户”等动作根据当前上下文作为次级操作出现；“添加已有用户”不提供 Owner 开关，Owner 转移仍走空间资料页的受控流程。

业务页面继续使用项目共享 `PageContainer`，默认由面包屑表达位置，不重复创建第二套全局导航。

## 左侧组织树

组织树包含以下固定结构：

```text
当前组织
├── 全部成员
├── 待加入
├── 团队
│   ├── 团队 A
│   │   ├── 成员甲
│   │   └── 成员乙
│   └── 团队 B
└── 未分组成员
```

### 节点规则

- 组织节点显示当前空间名称。
- “全部成员”“待加入”“未分组成员”是系统节点，不能删除或重命名。
- 团队节点显示团队成员数量，并支持按需展开。
- 成员属于多个团队时，可以在多个团队节点下出现；所有节点引用同一个成员 ID。
- 点击任一成员节点都打开同一个成员详情。
- 团队成员按需展开，避免组织较大时一次渲染全部成员。
- 点击团队节点时按需加载该团队成员，并在右侧打开团队上下文。
- 全局搜索支持团队名称、成员姓名、用户名和邮箱，并将结果分为团队和员工两类。
- 点击团队搜索结果时选择该团队并按需加载成员；员工搜索结果按成员 ID 去重，每名员工只出现一次，同时展示其所属团队标签。
- 点击员工搜索结果时直接打开该成员详情，不要求先展开某个所属团队。
- 当前选中节点同时通过背景、文字和焦点状态表达，不能只依赖颜色。

### 大数据量策略

- “全部成员”节点只展示数量，右侧成员目录使用分页列表。
- 初始组织树只读取组织摘要、系统节点数量以及团队 ID、名称和成员数，不返回团队的完整 `member_details`。
- 团队节点展开或选中时通过分页接口加载该团队成员，不把全部成员复制到初始树数据中。
- 服务器搜索负责跨分页查找成员；前端不假设 `page_size=100` 能覆盖所有成员。

## 角色权限顶层标签

顶部“角色权限”用于定义角色能执行哪些操作，不承担面向某个员工的日常授权入口：

- 选择组织范围时，展示组织级系统角色和自定义角色；
- 选择团队范围时，展示该团队可用的团队级系统角色和自定义角色；
- 支持查看权限点、创建自定义角色、复制角色、修改自定义角色和删除未被绑定的自定义角色；
- 系统预置角色保持只读，沿用现有后端限制；
- 原“空间授权”和“团队授权”页面中的绑定操作分别迁移到成员“访问角色”和团队“团队角色”上下文；
- “角色权限”回答“这个角色能做什么”，“访问角色”回答“这个员工拥有哪些角色”。

角色权限标签仍保留左侧组织树。点击组织或团队节点切换角色定义范围；点击成员节点时切回“组织成员”，并打开该成员的“访问角色”标签，避免出现没有业务含义的“成员角色定义”。

## 右侧组织上下文

选择组织根节点时展示空间治理概览：

- 成员总数；
- Owner 数量；
- 团队数量；
- 未分组成员数量；
- 待处理邀请数量；
- 尚未配置房源分工的成员数量。

概览只展示可操作的治理信息，不增加装饰性图表。异常摘要可跳转到对应系统节点或成员列表筛选结果。

## 右侧成员上下文

成员上下文包含固定的身份标题和四个标签。

### 成员标题

首屏展示：

- 头像；
- 姓名；
- 用户名或邮箱；
- Owner 身份；
- 所属团队摘要；
- 已负责房源数量。

Owner 身份在此只读展示。Owner 转移继续使用空间资料页已有的受控流程。

### 成员资料

展示成员账号、加入时间、更新时间和空间身份。允许有权限的管理员执行移除成员操作。

移除确认必须说明：

- 成员将离开当前组织；
- 团队成员关系和组织、团队角色会失效；
- 该成员的房源分工会被清理；
- 操作结果不可通过当前界面直接恢复。

### 所属团队

- 展示成员当前加入的所有团队。
- 允许逐个将成员加入现有团队。
- 允许逐个从团队移除成员，但不会将成员移出组织。
- 候选团队只来自当前组织。
- 操作成功后刷新组织树中所有该成员出现的位置。

统一工作台不使用现有 PATCH 的成员集合整体替换能力来处理日常增删，因为两位管理员同时编辑时，后提交的完整集合可能覆盖先完成的修改。

后端新增团队成员原子加入和移除接口：

- 每次请求只表达一个成员加入或移出一个团队；
- 加入前验证该用户仍是当前组织成员；
- 加入已存在成员、移除已不存在成员时返回可安全重试的幂等结果；
- 操作在事务内完成，并继续执行现有团队成员管理权限校验；
- 现有 PATCH 整体成员集合能力为兼容旧调用保留，但新工作台不使用它。

界面仍采用“单个团队、单次动作”的交互，不提供一次勾选多个团队后批量保存的伪原子操作。

### 访问角色

- 展示组织级访问角色。
- 展示该成员在各团队中的团队级角色。
- 团队角色按团队分组，避免把多个团队的绑定混成一列。
- 权限不足时保持可读，但隐藏或禁用编辑动作并说明原因。

### 房源分工

继续遵守既有安全配置设计：

1. 房东范围优先级最高；
2. 楼栋范围仅作用于未命中房东范围的房源；
3. 小区范围仅作用于未命中前两层范围的房源。

每层展示：

- 编号与名称；
- 已选数量；
- 简短生效说明；
- 可搜索多选控件；
- “留空表示不在该层分配”的提示。

保存前打开核对弹窗，明确本次保存会整体替换现有分工。三层均为空时使用危险提示，说明将取消全部负责范围。

“查看当前负责房源”只展示已保存分工的当前结果。由于本次不新增试算 API，界面不得把未保存草稿描述为精确的生效预览。

## 右侧团队上下文

团队上下文包含以下标签：

### 团队资料

展示并编辑现有字段：

- 团队名称；
- 电话；
- 微信；
- 地址；
- 营业时间；
- 创建时间和更新时间。

### 团队成员

- 展示团队成员名册。
- 候选成员只能来自当前组织。
- 支持添加和移除团队成员。
- 点击成员直接切换到该成员上下文，不离开工作台。
- 从团队移除成员不会删除组织成员或个人房源分工。

### 团队角色

- 展示并管理团队成员的团队级角色绑定。
- 只有团队成员可以获得该团队角色。
- 成员被移出团队后，对应团队角色按既有后端约束失效或清理。

### 分工概览

团队不直接获得房源分工。概览只聚合团队成员：

- 成员负责房源合计；
- 已配置分工人数；
- 未配置分工人数；
- 成员的分工摘要。

“成员负责房源合计”按各成员现有 `responsible_house_count` 相加，必须明确标注为成员口径；不同成员负责范围可能重叠，因此不得把该数值描述为团队去重后的唯一覆盖房源数。

点击成员摘要进入该成员的“房源分工”标签。

### 删除团队

删除团队必须确认，并说明：

- 不会删除组织成员；
- 不会删除成员个人房源分工；
- 团队级角色绑定将失效；
- 团队资料不可通过当前界面恢复。

## 右侧邀请上下文

左侧系统节点“待加入”显示待处理邀请数量。选中后，右侧复用现有邀请管理能力。

### 邀请列表

展示：

- 邀请目标；
- 邀请方式；
- 预设组织权限；
- 发送时间；
- 等待状态；
- 详情、重发、取消操作。

### 新建邀请

顶部“邀请成员”打开统一邀请窗口，继续支持：

- 邮箱邀请；
- 手机号邀请；
- 站内用户邀请；
- 预设组织级访问角色。

邀请不预设团队。从团队节点发起邀请时，也不自动绑定当前团队。对方接受邀请后进入“未分组成员”，管理员再通过成员的“所属团队”标签分配团队。

原邀请路由重定向到 `node=invites`，公开邀请接受和拒绝页面不受本次改造影响。

### 邀请状态刷新

- 进入“待加入”节点时刷新邀请列表与数量；
- 浏览器页面重新获得焦点时刷新，覆盖邀请在其他标签页被接受或取消的情况；
- 创建、重发或取消成功后立即刷新列表与数量；
- 沿用现有 7 天过期规则和后端状态判断；
- 本次不增加 WebSocket 或其他实时推送能力。

## 组件边界

统一工作台应拆分为职责清晰的页面私有组件，避免将所有逻辑继续堆叠在单个文件中。

推荐边界：

- `OrganizationWorkspacePage`：路由状态、整体布局和节点切换；
- `OrganizationTreePanel`：组织树、搜索、展开和选中状态；
- `OrganizationOverviewPanel`：空间治理摘要；
- `RolePermissionPanel`：组织级和团队级角色定义；
- `MemberWorkspacePanel`：成员标题与四个标签；
- `TeamWorkspacePanel`：团队资料、成员、权限和分工概览；
- `InvitationWorkspacePanel`：邀请列表和邀请操作；
- `ResponsibilityEditor`：三级范围编辑和保存确认；
- `useUnsavedWorkspaceGuard`：统一处理未保存修改拦截；
- 路由状态解析工具：在 URL 与工作台节点之间转换。

这些名称是设计层面的边界建议，实施时可以遵循项目现有目录命名，但不得重新把不同上下文合并为一个超大组件。

## 数据流

### 初始加载

进入工作台后并行加载：

- 当前组织上下文；
- 不包含完整成员详情的团队摘要；
- 成员分页摘要；
- 邀请数量或邀请列表摘要。

成员访问角色、团队角色、房源分工和负责房源在选中具体节点后按需加载。

### 节点切换

1. 用户点击组织树节点。
2. 若当前上下文存在未保存修改，先显示保存或放弃确认。
3. 更新 URL 中的 `node` 和 `tab`。
4. 保留左树已展开状态。
5. 加载新上下文缺失的数据。

### 保存与刷新

- 成员治理操作只刷新成员详情与相关树节点。
- 团队成员原子加入或移除后，刷新团队成员分页、成员所属团队、组织树计数和该成员出现位置。
- 权限变更只刷新对应权限绑定。
- 房源分工保存后刷新成员分工摘要和当前负责房源。
- 邀请创建、重发或取消后刷新“待加入”数量和邀请列表。
- 避免任何局部保存触发整个页面白屏或完整树重载。

## 未保存修改保护

以下场景必须进入统一拦截流程：

- 切换组织树节点；
- 切换成员或团队标签；
- 浏览器返回或前进；
- 离开组织架构路由；
- 关闭移动端组织树 Drawer 不属于离开上下文，不触发提示。

提示提供“继续编辑”“放弃修改”以及在适用时的“保存并继续”。提交失败时保留输入，不执行原定导航。

## 加载、空状态与错误

### 加载

- 初次加载组织树使用结构化骨架或页面 loading。
- 右侧标签数据采用局部 loading，不锁定组织树。
- 保存只锁定当前表单与相关动作。

### 空状态

- 没有团队：说明可以新建团队，但成员仍可在未分组节点管理。
- 没有成员：提供邀请成员和添加已有用户入口。
- 没有邀请：说明当前没有待加入人员，并提供邀请入口。
- 成员未加入团队：在所属团队标签提供分配动作。
- 成员未配置房源分工：说明三层范围均为空，不伪装成请求失败。

### 错误

- 树加载失败显示可理解原因和重试动作。
- 右侧上下文失败不清空当前树与选择状态。
- 保存失败保留表单值，并允许重新提交。
- 节点已被其他操作删除时，回退到最近有效的父节点并提示原因。

## 权限

- 只展示当前用户有权查看的团队和治理信息。
- 无创建权限时隐藏或禁用邀请成员、新建团队和添加已有用户。
- 无成员管理权限时，成员资料保持只读，不能移除成员或调整团队。
- 无角色管理权限时，“角色权限”“访问角色”和“团队角色”保持可读但不可编辑。
- 无房源分工权限时，房源分工标签保持只读或不可进入编辑态。
- 危险操作始终使用明确确认，不因 Owner 身份省略。

## 响应式

### 桌面

- 左侧组织树保持稳定宽度，右侧内容自适应。
- 右侧复杂表格使用项目共享横向滚动策略。

### 中等宽度

- 缩窄组织树，但保留团队名称、成员名称和数量。
- 工具栏允许换行，不挤压主要动作。

### `≤768px`

- 组织树进入 Drawer，通过页面工具栏按钮打开。
- 右侧上下文改为单列。
- 标签允许横向滚动，但不能隐藏当前标签和保存动作。
- 表单、确认和危险操作仍可完整完成。

## 可访问性

- 组织树使用可表达展开、折叠、层级和选中状态的语义结构。
- 树、标签、表单和 Drawer 均可通过键盘操作。
- 当前节点、Owner、待加入、未配置等状态不能只依赖颜色。
- 纯图标按钮提供可访问名称和必要 Tooltip。
- 节点切换后将焦点移动到右侧上下文标题，避免键盘用户丢失位置。

## API 与数据库影响

本设计不要求新增数据库字段或迁移，但需要补充支撑统一工作台的轻量查询和原子变更接口。

初始实施复用现有接口：

- 组织成员列表、详情、添加、更新和移除；
- 团队列表、详情、创建、更新和删除；
- 组织级与团队级角色绑定；
- 邀请列表、创建、详情、重发和取消；
- 员工房源分工列表、整体替换和负责房源查询。

新增或扩展以下接口能力：

1. 组织导航摘要：返回当前组织、全部成员数、待加入数、未分组成员数以及可见团队的 ID、名称和成员数，不携带完整 `member_details`。
2. 团队成员分页查询：在选中或展开团队后按 `page`、`page_size` 和关键字读取成员，可通过新增团队成员列表端点或给现有组织成员列表增加 `team_id` 过滤实现。
3. 团队成员原子加入与移除：替代新工作台中的成员集合整体 PATCH，避免并发覆盖。
4. 组织全局搜索：返回分组的团队结果和按成员 ID 去重的员工结果；员工结果携带可见的所属团队 ID 与名称摘要，用于展示团队标签。

团队与成员的全局搜索继续由服务器跨分页执行。前端可以增加手写聚合适配器和查询 hooks；后端 OpenAPI schema 更新后重新生成服务代码，不手改生成的 OpenAPI 文件。

## 路由与兼容迁移

1. 新增统一组织架构路由和菜单项，默认进入“组织成员 → 全部成员”。
2. 将原成员、团队、邀请、员工分工和权限管理路由改为兼容重定向。
3. 内部跳转逐步改为新工作台深链接。
4. 不删除公开邀请接受与拒绝路由。
5. 原页面组件在本次工作中不做物理删除；兼容重定向稳定后，如需进一步整理，由人工确认并另行立项处理。

## 测试与验收

### 单元与组件测试

- 组织树能正确派生全部成员、团队成员、未分组成员和待加入数量。
- 初始组织树摘要不包含团队完整成员详情，展开团队后才分页加载成员。
- 多团队成员在多个节点出现，但共享同一成员标识。
- 默认路由进入“组织成员 → 全部成员”。
- URL 能恢复组织、团队、成员、邀请节点和当前标签。
- 搜索结果区分团队和员工；员工结果按成员 ID 去重并显示全部所属团队标签。
- 未保存修改拦截覆盖节点、标签和路由切换。
- 团队成员加入和移除使用原子接口，不会因并发提交完整成员集合而相互覆盖，也不会移除组织成员或房源分工。
- “角色权限”管理角色定义，“访问角色”和“团队角色”管理绑定关系。
- 团队删除确认准确说明影响。
- 邀请创建 payload 与现有邮箱、手机号、站内用户模式保持一致。
- 房源分工仍在确认后才发送整体替换请求。
- 三层范围均为空时显示取消全部分工的危险提示。

### 集成与浏览器验收

- 从原成员、团队、邀请和员工分工路由进入时，能够落到正确的新上下文。
- 从原权限管理及其子路由进入时，能够落到角色权限或对应授权上下文。
- 邀请创建、详情、重发、取消流程保持可用。
- 进入待加入、页面重新获得焦点及邀请操作完成后，邀请状态和数量会刷新。
- 新成员接受邀请后出现在未分组成员中。
- 团队成员增删后，团队、成员详情和组织树计数同步更新。
- 成员角色和团队角色在统一工作台中可正确查看和修改。
- 房源分工保存后，成员摘要和当前负责房源同步更新。
- 加载、空数据、失败、无权限和保存失败状态均有明确反馈。
- 在桌面、中等宽度和移动端完成邀请、团队成员调整、权限调整和房源分工核心流程。
- 键盘可以访问组织树、标签、表单、确认弹窗和 Drawer。

## 与现有设计和变更的关系

- `docs/superpowers/specs/2026-07-24-staff-responsibilities-safe-assignment-design.md` 中的三级优先级、整体替换确认和取消全部分工保护继续有效，并被纳入成员“房源分工”标签。
- 尚未完成的 `openspec/changes/revamp-space-member-management/proposal.md` 采用独立成员页且不调整导航，与本设计冲突。本设计确认后，后续若继续该 OpenSpec change，必须先将其更新为统一组织架构工作台，不应按旧提案独立实施。

## 最终决策摘要

- 采用双栏上下文工作台。
- 使用组织 → 平级团队 → 成员模型。
- 页面顶部使用“组织成员 / 角色权限”一级标签，默认显示全部组织成员。
- 合并成员、团队、邀请、员工分工和权限管理页面。
- 成员详情包含资料、所属团队、访问角色和房源分工。
- 团队详情包含资料、成员、团队角色和成员分工概览。
- 邀请保持现有功能，不预设团队。
- 全局搜索区分团队和员工，员工结果去重并显示所属团队。
- 邀请状态在进入节点、页面聚焦和操作成功后刷新，不增加实时推送。
- 不修改数据库模型；新增轻量组织导航、团队成员分页和原子加入/移除 API。
- 旧路由保留兼容重定向。
