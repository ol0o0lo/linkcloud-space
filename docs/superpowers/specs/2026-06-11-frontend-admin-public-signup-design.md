# frontend_admin 公开注册闭环设计

## 背景

当前 `frontend_admin` 已具备登录、验证码登录、用户态拉取和后台权限路由能力，但公开注册仍处于未完成状态：

- `/auth/register` 路由会直接重定向回登录页。
- `register.vue` 只有表单壳子，没有实际提交逻辑。
- `frontend_admin` 尚未接入注册成功后的 `verify_phone` 待处理流程。
- 邀请注册后端链路已存在，但 `frontend_admin` 还不能独立承接带 `invite_code` 的注册闭环。

同时，旧主站 `frontend/` 已不再作为注册承载端，一期目标是由 `frontend_admin` 独立完成公开自注册、手机号验证和邀请码归因闭环。

## 目标

在 `frontend_admin` 中补全一套可用的公开注册模块，使用户可以：

1. 通过 `/auth/register` 进入注册页。
2. 在带 `invite_code` 的 URL 下完成注册，并沿用现有后端归因链路。
3. 遇到 `verify_phone` 待处理流程时，继续留在 `frontend_admin` 完成手机号验证。
4. 注册成功后进入后台，不依赖旧主站页面跳转。

## 非目标

- 一期不接入 GitHub、微信等第三方注册。
- 一期不新增独立的注册成功页。
- 一期不改动后端邀请码归因规则、奖励规则或审核规则。
- 一期不复用旧主站 `frontend/` 的注册页面或交互。

## 方案选择

本次采用“在 `frontend_admin` 中新增独立公开注册模块”的方案。

原因：

- 不再依赖已弃用的旧前端。
- 避免把后台登录页强行扩展成复杂注册流，降低耦合。
- 后续若继续扩展活动落地页、品牌化注册入口或增长链路，这套模块更容易独立演进。

## 用户路径

### 路径一：普通公开注册

1. 用户访问 `/auth/register`。
2. 填写邮箱、手机号、密码、确认密码并提交。
3. 若注册已完成且会话已建立，前端拉取用户信息和权限后进入后台。
4. 若后端返回 `verify_phone` pending flow，前端跳转到 `/auth/verify-phone` 继续完成手机号验证。
5. 手机验证成功后，前端拉取用户信息和权限并进入后台。

### 路径二：带邀请码注册

1. 用户访问 `/auth/register?invite_code=XXXX`。
2. 页面展示邀请码提示，但不允许用户手动编辑邀请码。
3. 注册提交流程与普通公开注册一致。
4. 邀请码归因继续依赖后端已有 middleware + session + signal 链路。
5. 注册成功后自动生成邀请记录，后续关键行为、审核和发奖仍沿用现有裂变链路。

## 页面与路由设计

### 1. `/auth/login`

- 继续服务已注册用户登录。
- 打开“注册”入口，指向 `/auth/register`。
- 不把注册逻辑混入登录页。

### 2. `/auth/register`

职责：公开注册入口。

页面内容：

- 标题：创建账号。
- 说明：完成注册后即可进入后台；若账号需验证手机号，会继续下一步。
- 邀请提示：当 URL 带 `invite_code` 时展示“你正在通过邀请码 XXX 注册”。
- 表单字段：邮箱、手机号、密码、确认密码、同意协议。
- 辅助入口：已有账号，去登录。
- 不展示第三方注册入口。

行为：

- 提交时调用新的 `signupApi`。
- 保留当前 URL query，保证后端可以从请求链路中捕获 `invite_code`。
- 如果注册直接成功，进入后台。
- 如果返回 `verify_phone` pending flow，跳转到 `/auth/verify-phone`。

### 3. `/auth/verify-phone`

职责：完成注册后的手机号验证。

页面内容：

- 标题：验证手机号。
- 说明：验证码已发送到当前注册手机号。
- 当前手机号脱敏展示。
- 验证码输入框。
- 重发验证码按钮。
- 返回登录入口。

行为：

- 首次进入时允许用户输入验证码。
- 用户可执行重发验证码。
- 验证成功后直接拉取用户信息和权限并进入后台。
- 一期不增加中间成功页。

## 前端架构设计

### 新增或调整的文件职责

- `src/router/routes/core.ts`
  - 放开 `/auth/register` 路由。
  - 新增 `/auth/verify-phone` 路由。

- `src/views/_core/authentication/login.vue`
  - 打开注册入口展示。
  - 保持登录职责单一，不引入注册表单逻辑。

- `src/views/_core/authentication/register.vue`
  - 从空壳页面改造成真正的注册页。
  - 承担邀请码展示、表单校验、注册提交和注册结果分流。

- `src/views/_core/authentication/verify-phone.vue`
  - 新增手机号验证页。
  - 承担验证码输入、重发、验证成功后的后台进入。

- `src/api/django/auth.ts`
  - 新增 `signupApi`。
  - 抽出注册与登录共用的 flow 解析逻辑，统一识别 `verify_phone` 等 pending flow。

- `src/store/auth.ts`
  - 继续复用现有用户信息拉取和登录后进入后台的逻辑。
  - 不在 store 中承载过多注册页面状态，注册页状态以页面本地状态为主。

## 接口与状态流转

### 注册提交

- 前端调用 allauth signup 接口。
- 提交字段：`email`、`phone`、`password`。
- `invite_code` 不进入 body，由后端现有 middleware 从 URL / session 链路处理。

### 注册结果处理

#### 情况一：直接完成注册并建立会话

- 前端设置访问态。
- 拉取用户信息和 access codes。
- 进入 `redirect` 或默认后台首页。

#### 情况二：返回 `verify_phone` pending flow

- 前端不判定为失败。
- 跳转到 `/auth/verify-phone`。
- 保留 `redirect` 与 `invite_code` 参数。

### 手机验证

- 调用已有 `verifyPhoneApi` 完成验证码确认。
- 调用已有重发验证码能力完成 resend。
- 验证成功后拉取用户信息和 access codes，再进入后台。

## 邀请归因设计

邀请码归因不在 `frontend_admin` 前端新增业务判断，继续依赖已有后端机制：

1. 带 `invite_code` 的请求进入系统后由 middleware 捕获并写入 session。
2. 注册成功时由 `user_signed_up` signal 读取 session 并创建邀请记录。
3. 记录状态初始为 `REGISTERED`。
4. 后续关键行为、管理员审核和发奖沿用现有 referrals + wallet 链路。

这样可以保证：

- `frontend_admin` 注册页只是承接入口，不重复实现邀请码归因逻辑。
- 同一邀请码规则可同时服务推广页、后台、未来活动入口。

## 错误处理

### 注册页

- 字段校验错误：就地展示字段错误。
- allauth 返回业务错误：映射为表单或全局错误提示。
- 注册成功但用户信息拉取失败：提示重新登录，并回到登录页。

### 手机验证页

- 验证码错误：停留在当前页，允许重新输入。
- 重发失败：提示错误，但不清空已输入验证码。
- 验证成功后拉取用户信息失败：提示重新登录，并回到登录页。

## Query 参数约定

为了保证用户体验与归因链路完整，以下参数在注册与验证流程中持续保留：

- `invite_code`
  - 用于展示当前是通过邀请码注册。
  - 同时为后端归因链路提供原始请求上下文。

- `redirect`
  - 注册或验证完成后回到目标页面。
  - 若不存在则进入默认后台首页。

## 测试策略

### 单元测试

1. `register.vue`
   - 渲染表单字段。
   - 正确展示 `invite_code`。
   - 注册直接成功时进入后台。
   - 返回 `verify_phone` flow 时跳转验证页。
   - 正确展示字段错误与非字段错误。

2. `verify-phone.vue`
   - 提交验证码成功后进入后台。
   - 验证失败时留在当前页。
   - 重发验证码成功与失败提示正确。

3. `auth.ts`
   - `signupApi` 成功分支。
   - `verify_phone` pending flow 识别。
   - allauth 错误解析保持一致。

### 端到端测试

至少覆盖一条主路径：

1. 访问带 `invite_code` 的注册页。
2. 完成注册。
3. 完成手机号验证。
4. 成功进入后台。
5. 后台或推广页能看到对应邀请记录已建立。

## 实施边界

一期实现只覆盖“公开自注册闭环可用”，不扩展以下内容：

- 第三方注册。
- 多步注册向导。
- 邀请落地页视觉运营化。
- 注册成功营销弹层或奖励说明页。

## 风险与注意事项

1. `invite_code` 归因依赖 session，请确保注册和验证在同一浏览器会话内完成。
2. `frontend_admin` 当前登录流对额外 auth flow 的支持有限，注册侧实现时需把 `verify_phone` 明确视作正常分支，而不是异常。
3. 若注册成功后用户信息接口返回的角色或首页路径不完整，需要统一兜底到默认后台首页或登录页，避免进入空白页。
4. 登录页、注册页、验证页的 query 透传逻辑必须统一，否则容易在注册后丢失 `redirect` 或 `invite_code`。

## 验收标准

满足以下条件即可视为一期完成：

1. 用户可在 `frontend_admin` 访问真实可用的 `/auth/register` 页面。
2. 用户可在 `frontend_admin` 内完成注册后的手机号验证。
3. 带 `invite_code` 的注册能够沿用现有后端链路生成邀请记录。
4. 注册或验证成功后可直接进入后台。
5. 关键页面与 API 具备对应自动化测试覆盖。
