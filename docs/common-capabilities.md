# 系统通用能力文档规范

本文定义系统通用能力文档的存放位置、命名方式和基本内容。后续新增或重构通用能力文档时，应遵守本规范。

这里的“通用能力”是指能够被多个业务域复用，或者作为系统基础设施长期提供稳定契约的能力，例如通知、收藏、媒体、权限、租户上下文和配置。单一页面功能、一次性业务流程、零散工具函数以及只在某个业务内部使用的实现，不应作为通用能力沉淀。

## 1. 文档目录

通用能力规范和具体能力文档统一存放在 `docs/` 根目录：

```text
docs/
├── common-capabilities.md
├── <capability-name>-capability.md
└── ...
```

- `common-capabilities.md`：本规范。
- `<capability-name>-capability.md`：某项通用能力当前有效的设计、契约、实现和接入说明。
- 文件名使用小写英文和连字符，例如 `notification-capability.md`。
- 文档标题统一使用“`<能力名称>通用能力设计与实现`”。
- 一个能力原则上只维护一份主文档，避免将设计、接口和接入方式拆散到多份长期文档中。

阶段性设计稿和实施计划继续放在过程文档目录；需要长期保留的设计决策写入能力主文档的“设计思想与取舍”；只属于单一业务域的内容放在对应业务文档中。

现有文档不要求仅为调整目录而立即迁移。后续系统性补充或重写时，再逐步归入本目录并修正相关引用。

## 2. 通用能力判定

满足以下任一条件时，可以考虑沉淀为通用能力：

- 已经被多个业务域复用。
- 属于认证、权限、租户、存储、通知等系统基础能力，需要长期保持稳定契约。
- 对第三方服务或多种实现进行了统一隔离。

不应仅因为代码相似就提前抽象。无法说明能力边界、调用契约和非目标时，应继续保留在具体业务域内。

通用能力应使用含义明确的模块名称，不集中堆放到 `common`、`helpers` 或 `misc`。具体代码组织遵守 [后端开发规范](./backend-standards.md)。

## 3. 文档内容要求

能力文档重点说明当前有效实现。尚未实现的设想必须明确标记为“规划”，不得与现状混写。

| 章节 | 要求 | 说明 |
| --- | --- | --- |
| 能力概述 | 必需 | 说明解决的问题、当前状态和主要使用方 |
| 能力边界与非目标 | 必需 | 明确负责什么、不负责什么，以及与相关模块的分界 |
| 设计思想与取舍 | 必需 | 说明核心原则、当前方案及重要取舍 |
| 数据与状态 | 按需 | 说明核心实体、状态、约束和生命周期 |
| 接口与契约 | 必需 | 描述实际公开的内部入口、HTTP API、事件或扩展协议 |
| 实现结构与核心流程 | 必需 | 标明核心代码位置、职责和关键调用流程 |
| 接入方式 | 必需 | 给出接入步骤、最小示例和必要前置条件 |
| 限制、演进与相关文档 | 必需 | 说明当前限制、兼容要求，并链接相关资料 |

没有对应内容的可选章节或子章节可以省略，不需要为了结构完整而填写空内容。

## 4. 接口与契约

每项通用能力都应说明真实提供的公开入口，但不要求同时具备内部接口、HTTP API、事件和扩展协议，更不要求每项能力都提供 HTTP API。

| 接口类型 | 需要说明的内容 |
| --- | --- |
| 内部入口 | 函数、类、中间件、字段或其他公开入口的位置，以及输入、输出、异常和副作用 |
| HTTP API | 方法、路径、认证权限、请求响应和主要错误；具体规则遵守项目 API 规范 |
| 事件或异步任务 | 触发时机、数据契约、幂等、重试和失败处理 |
| 配置或扩展协议 | 配置项、扩展方式、注册位置、稳定标识和兼容要求 |

调用方应依赖公开契约，不直接修改能力内部模型或复制内部规则。只有存在多个实现、需要替换实现或需要隔离外部服务时，才增加抽象协议，避免为抽象而抽象。

## 5. 实现与接入说明

能力文档只需列出实际存在的核心代码位置，并说明各部分职责和依赖关系，不需要复制一套理想目录结构。

涉及状态流转或副作用时，应说明关键调用链、事务边界和失败行为。涉及认证、权限、多租户隔离或敏感信息时，应在对应接口或限制中明确说明。

接入说明至少包含：

1. 调用或注册步骤。
2. 最小可用示例。
3. 必要的权限、配置、迁移或客户端联动要求。

- 负责范围：

- 非目标：

## 3. 设计思想与取舍

- 核心原则：

## 4. 数据与状态

说明核心实体、状态、约束和生命周期。能力没有持久化数据时可省略本章。

## 5. 接口与契约

按实际情况描述内部入口、HTTP API、事件、异步任务、配置或扩展协议，包括输入输出、异常、副作用和权限要求。

## 7. 维护规则

- 能力的公开契约或核心行为发生变化时，应在同一次变更中更新能力文档。
- 文档中的路径、示例和返回结构必须与当前代码一致。
- 破坏兼容性的变更必须说明数据和调用方的迁移方式；重要决策应补充到“设计思想与取舍”。
- 同一个规则只保留一个权威说明，其他文档通过链接引用。

## 8. 评审检查清单

- [ ] 能够说明为什么它属于通用能力，而不是单一业务功能。
- [ ] 已明确能力边界和非目标。
- [ ] 已区分当前实现与未来规划。
- [ ] 已记录实际公开接口、异常和副作用。
- [ ] 已给出与当前代码一致的接入示例。
- [ ] 已说明限制、兼容要求并链接相关文档。
