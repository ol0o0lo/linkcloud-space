# 后台页面体验规范设计

## 背景

`frontend_admin/apps/web-antdv-next` 当前后台页面已经接入 Vben Admin、Ant Design Vue、Vben `Page` 容器和现有菜单/权限体系。现有业务页大多采用相似结构：顶部统计卡片、若干筛选或表单卡片、表格卡片。这种结构落地快，但容易让用户、租户、团队、实名审核、系统设置、通知中心等不同业务都看起来像同一套 CRUD 模板，缺少贴近真实使用场景的操作逻辑。

本设计先产出后台页面规范，不直接修改页面代码。后续实现应以此规范作为判断依据，避免继续复制“所有页面一个 grid 布局”的做法。

## 设计目标

- 页面结构先服务真实业务任务，再选择组件和布局。
- 兼容 Vben Admin 的整体风格、布局体系、暗色模式、菜单、权限路由和 Ant Design Vue 组件生态。
- 高频页面偏效率，低频或高风险页面偏上下文完整和误操作防护。
- 操作逻辑贴近业务，明确用户在操作前需要看什么、操作时要确认什么、操作后系统如何反馈。
- 形成未来新增后台页也可复用的判断规则，而不是只给当前页面做视觉调整。

## 非目标

- 不重做后台整体框架、菜单系统、权限路由或主题系统。
- 不引入一套脱离 Vben Admin 的独立视觉系统。
- 不在本设计阶段实现页面代码。
- 不把规范写成单纯的组件拼装手册。

## 总体原则

后台页面采用双层规范：

1. 任务分型层：先判断页面属于哪类业务任务，再决定页面结构、信息优先级、操作模式和风险提示。
2. Vben / Ant Design Vue 落地层：在既定页面结构下选择现有组件，保持项目后台风格一致。

页面不应默认套用“统计卡片 + 表格卡片”的固定模板。统计、卡片、表格、抽屉、弹窗都必须有明确业务目的。卡片只用于承载明确模块，不能为了排版把整页拆成多排同质卡片。

## 页面任务分型

### 账号运维台

适用页面：用户管理、团队管理。

目标是快速定位对象并处理账号状态、权限、成员关系等运维动作。页面应优先保证扫描、筛选、批量处理和对象详情查看效率。

推荐结构：

- 主工作区使用紧凑列表或表格。
- 搜索、状态筛选、角色筛选、批量动作位于表格工具栏附近。
- 复杂对象详情和编辑优先使用右侧详情面板或 `Drawer`。
- 顶部统计只保留与当前筛选结果直接相关的少量状态，不铺满页面。

业务操作要求：

- 禁用账号、授予管理员、授予超级管理员、重置 MFA、强制退出、解绑手机号、解绑微信、移除成员等动作必须展示影响范围并二次确认。
- 编辑动作不能只从字段角度呈现，应突出业务后果，例如“该用户将失去后台访问能力”。
- 操作成功后刷新当前列表状态，并保持用户所在筛选上下文。

### 组织工作台

适用页面：租户管理。

租户页的核心不是多张表，而是当前租户上下文。页面应围绕“当前正在管理哪个租户”组织成员、邀请、容量、账单资料和切换操作。

推荐结构：

- 页面顶部或侧栏突出当前租户名称、标识、主租户状态和容量摘要。
- 主工作区按成员、邀请、容量、账单资料等业务域组织，可使用 tabs 或分区。
- 租户列表用于切换当前操作上下文，不应和当前租户成员/邀请混成普通并列表格。
- 右侧或局部上下文区展示当前租户限制、待处理邀请、容量风险等信息。

业务操作要求：

- 切换租户前后都要明确提示“下方管理对象会随当前租户变化”。
- 添加成员、设置 owner、移除成员、发送/撤销邀请应围绕当前租户展示，避免用户误以为是全局操作。
- 容量限制和成员上限应出现在执行相关动作的附近。

### 审核队列

适用页面：实名认证。

实名页面应像审核工作台，而不是普通列表。核心任务是处理待审记录，并在详情中做出通过或驳回判断。

推荐结构：

- 主视图优先展示待审队列，可提供状态、时间、关键词等筛选。
- 详情区展示身份信息、认证材料、风险提示、提交时间、历史处理记录和审核结论。
- 详情可以使用右侧面板、抽屉或队列 + 详情的双栏结构。
- 审核动作固定在详情区域底部或明确操作区。

业务操作要求：

- 通过和驳回是核心动作，不应隐藏在普通表格操作中。
- 驳回必须提供原因输入或原因选择。
- 高风险或信息不完整时展示明确提示。
- 处理成功后可自动切到下一条待审记录，提升审核效率。

### 配置中心

适用页面：系统设置。

设置页不应是 Key/Value 表格堆叠。核心任务是理解配置项的作用、当前值来源、覆盖状态和影响范围，然后安全编辑。

推荐结构：

- 按配置域分组，例如租户设置、个人偏好、通知偏好。
- 每个设置项展示当前值、默认值、覆盖状态、说明和影响范围。
- 复杂设置项使用详情编辑或分组表单，避免把所有值都塞入普通输入框。
- 没有当前租户时，租户级设置应展示清晰空态和下一步操作。

业务操作要求：

- 恢复默认必须提示会移除当前覆盖值。
- 租户级设置要说明影响当前租户的所有成员或相关行为。
- 个人设置要说明只影响当前管理员。
- 通知偏好应和通知中心及 Vben 顶栏通知入口保持一致。

### 消息处理台

适用页面：通知中心。

通知中心要配合 Vben Admin 既有通知入口和顶部未读提醒使用。完整通知页负责更强的筛选、批量处理、详情追踪和关联对象跳转，不另起一套割裂的消息系统。

推荐结构：

- 顶栏通知入口用于快速看到未读和最近消息。
- 通知中心页面提供未读、全部、分类、重要程度等筛选。
- 列表重点突出未读状态、消息类别、时间和关联对象。
- 详情可使用抽屉或侧栏，展示完整内容和跳转入口。

业务操作要求：

- 支持批量标记已读和单条标记已读。
- 重要通知应有更强视觉优先级，但仍保持 Vben 风格。
- 关联到租户、团队、用户、审核记录等对象时，应提供可跳转入口。
- 统计只服务处理效率，不做装饰性卡片。

### 数据概览台

适用页面：Dashboard、Overview、Analytics。

Dashboard 保留概览属性，但不应堆砌模板化图表。每个模块必须回答一个运营或管理问题。

推荐结构：

- 指标与趋势图围绕活跃、注册、组织增长、审核积压、系统异常等问题组织。
- 图表旁边提供解释、异常提示或跳转入口。
- 视觉层级可以比运维页更丰富，但仍要避免装饰性图表。

业务操作要求：

- 指标必须可解释，并能指向后续操作页面。
- 异常或待处理事项要提供入口，而不是只显示数字。

## Vben / Ant Design Vue 落地规则

- 页面容器继续使用 Vben `Page`，保留当前布局、菜单、权限路由和暗色模式能力。
- 高频列表可使用 Ant Design Vue `Table` 或项目已接入的 Vben/Vxe Grid，但表格只作为主工作区，不再默认包在多层卡片中。
- 复杂对象详情和编辑优先使用 `Drawer`、右侧详情面板或详情区域；短表单和确认类操作使用 `Modal`。
- 设置项组件按数据类型选择：布尔值使用 `Switch`，枚举使用 `Select`，数字使用 `InputNumber`，长文本使用 `Textarea`，复杂 JSON 使用更适合结构化编辑的输入方式。
- 主操作应固定在页面标题区、表格工具栏、详情面板底部或抽屉 footer，不应散落在多个卡片角落。
- 危险操作统一使用二次确认，并说明影响范围、对象名称和不可逆后果。
- 空态要说明下一步业务动作，例如“请先选择租户”“暂无待审记录”“当前没有通知分类配置”。
- 加载失败要提供重试入口。
- 页面文案以业务动作和后果为主，不用组件术语解释页面功能。

## 后续实施边界

后续进入实现时，建议按风险和收益分批：

1. 设置页和通知页：先修正最明显的 Key/Value 表格和通知处理体验，风险较低。
2. 租户页和实名页：重塑业务工作台和审核队列，能明显改善真实使用体验。
3. 用户页和团队页：强化高频运维效率和高风险操作确认，需更谨慎验证。
4. Dashboard：在真实指标和可行动入口明确后再调整，避免先做展示型图表。

每次实现应只改一个页面类型或一组强相关页面，避免一次性重写整个后台。

## 测试与验收建议

- 视觉验收：桌面和窄屏下页面无文字溢出、按钮挤压、信息重叠。
- 业务验收：每个页面能说清楚主任务、主对象、主操作和高风险操作。
- 交互验收：危险动作有影响范围确认，成功后状态刷新并保留用户上下文。
- 兼容验收：保留 Vben Admin 布局、菜单、主题和 Ant Design Vue 组件风格。
- 回归验收：实现阶段按页面运行前端类型检查、构建和必要的后端 API 测试。
